# Precis — 2026-09-06

## Key points from the day

### `resetStats` closes out the point-buy reset button, and verifying it caught two bugs along the way

`resetStats` puts every point-buy stat back to its starting value of 10, zeroes what's been spent, and reseeds each
stat's next-point cost, so the point-buy screen's reset button has something to call. Verifying it against the C
original found two problems: the point total it hands back was going nowhere, because C communicates the reset total
through a pointer the port has no equivalent for, and the increment-cost lookup was reading a different stat's value
than the one it was pricing. Both are fixed now — the total comes back as a return value instead of an out-parameter,
and the cost lookup reads each stat's own freshly-reset value. Seven tests cover the stat loop against leftover values a
caller's map might carry in, the sentinel guard, the return value regardless of what was passed in, and the
`updateDisplay` guard's two downstream calls, so the reset button has a working implementation ready to be wired up
without carrying either bug into its first caller.

### `buyStat` closes out the point-buy screen's buy button, alongside its own private result type

`buyStat` spends a single point-buy point raising one stat, the buy button `resetStats` was ported alongside earlier
today. Verifying it against the C original found a stat choice outside the valid range was indexed into the stat enum
before that range was ever checked, so a malformed choice threw instead of answering the same "nothing spent" result C
gives for the same input. The choice is now validated before it indexes anything, so out-of-range input degrades the way
C's does rather than crashing. Thirteen tests cover the ordinary purchase, every flavour of invalid choice, a stat
already at the cap, a mismatched cost, too few points, the one point where the port deliberately parts from C rather
than following it past the end of an array, and the `updateDisplay` guard's call order — which turned out to be the
opposite of `resetStats`'s own, since C's two functions do it differently — so the buy button now has a working
implementation with the same "nothing wired up yet" status as the reset button.

### `sellStat` closes out the point-buy screen's sell button, catching a bug the first verify pass alone didn't clear

`sellStat` refunds a single point-buy point by lowering one stat, the mirror of the buy button ported earlier today. The
first verify pass found the stat was never actually lowered, so a sale refunded points without touching the value it
claimed to be selling, and the increment-cost refresh read the stat's value from before that missing decrement rather
than after, which would have read past the end of `birthStatCosts` once the decrement was restored. Both are fixed now —
the stat drops first, and the cost refresh reads its new, lower value, landing back inside the table even at the top of
the range. Eight tests cover the ordinary sale, the floor guard that stops a stat falling below 10, the boundary that
used to misread past the cost table, and the `updateDisplay` guard's call order, so the point-buy screen's three
buttons — reset, buy and sell — are all now ported and waiting on the same wiring.
