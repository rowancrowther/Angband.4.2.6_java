# Precis — 2026-10-09

## Key points from the day

### `ObjPropertyType.fromValue` and `ObjectPropertyAssembler.assemble` checked against `parse_object_property_type` in `obj-init.c`

`fromValue` turns the `type:` token of an object property into its category, and `assemble` uses it to pick the table the `code:` resolves against. Because the lookup walked every constant, the placeholder tokens for `OBJ_PROPERTY_NONE` (empty) and `OBJ_PROPERTY_MAX` ("max") resolved to real categories, where C rejects both as an invalid property. `fromValue` now returns null for both and the assembler reports an empty type as "has no type", matching C's missing-type error. `ObjPropertyTypeTest` and `ObjectPropertyAssemblerTypeTest` pin the seven real tokens, the two placeholders and the near-misses ("resist", "Stat"), and show a bad record leaving its neighbours intact. The Javadoc on the enum, its constants and its fields now says which tokens a data file can name, so later work on object-property data can rely on the category never being NONE or MAX.

### `Monster.java` checked against the `struct monster` predicates, flag macros and timed-effect entry points in C

`Monster` carries the ports of `monster_is_unique`, `monster_is_visible`, `monster_is_obvious`, `mflag_on`/`mflag_off`, `mon_clear_timed`, `mon_dec_timed` and `update_smart_learn`. Most had only a short block, and one Javadoc block cited a C line number, named the wrong class as the live caller of `updateSmartLearn`, and wrongly said the constructor can call `updateCached` before its fields are assigned. Every one matched the C, so the pass was documentation and tests: the class, the `monIndex` field, the constructor and every accessor now carry a block naming the C function, the wrong claims are corrected, and `MonsterPredicatesTest` and `MonsterTimedTest` pin the shapechange cases of `isUnique`, the `isObvious` truth table, and the values `clearTimed` and `decrementTimed` hand to `setTimed`. Later work on `mon_set_timed` can build on those two tests, which already fix what its callers must pass.

### `ObjectBase.java` checked against `struct object_base` and the `object_base` parser in `obj-init.c`

`ObjectBase` is the per-tval record of display colour, hated elements, break chance and stack size that every object kind inherits from. The class has no behaviour beyond its constructor, which matched C's record after `parse_object_base_name`, but its Javadoc claimed an "unset" value of `-1` for break chance and stack size that can never occur, because the grammar folds the file-wide defaults into every record. The class, every field, the constructor and each accessor now carry a block naming the C field, the "`-1`" claim is gone, and the blocks record that the `flags` set is always empty, that the element map is sparse, and that the kind flags are stored by reference. `ObjectBaseTest` pins the constructor and checks all 34 shipped bases against an independent reading of `object_base.txt`, so later work on object kinds can rely on those inherited values.

### `MessageTag.getTag` checked against `msg_tag_lookup` and `msg_tag_t` in `obj-util.c`

`MessageTag` names the four braced tags a custom message can carry, and `getTag` is the prefix lookup that `ItemObject.printCustomMessage` uses to read them. The lookup and the constant order already matched C, but the `{name}` constant was documented as the object's "full description" when C describes it under `ODESC_PREFIX | ODESC_BASE`, and the constants and the `size` field had no blocks of their own. Every constant and the field now carry a block that names what C does for it, the `{name}` claim is corrected, and `MessageTagTest` gains a check that the constants keep C's order. Later work on the message printer can rely on those blocks, and on `size` being unused.

### `TerrainRegistry.lookupTrap` and `getTrapMax` checked against `lookup_trap` in `trap.c` and `finish_parse_trap` in `init.c`

`TerrainRegistry` holds the terrain features and trap kinds that C keeps in `f_info`, `trap_info` and `z_info->trap_max`, and `lookupTrap` is the description search every named-trap caller goes through. The scan began at the first kind, where C begins at index 1, so the real `no trap` kind from the head of `trap.txt` could be returned for an empty or partial description, and `trapMax` was never assigned, so `getTrapMax` always returned 0. `lookupTrap` now skips `trapKindIndex` 0, `setTrapInfo` sets `trapMax` to the list size, and `TrapKind.lookupTrap` delegates to the registry copy so there is one search instead of two. `TerrainRegistryTest` pins the count, the read-only views and the feature lookup, `TrapKindTest` gains the index-0 cases, and the `SquareTrapAndDoorTest` fixture now opens with a `no trap` kind as the shipped data does. Later work on `pick_trap` and `place_trap` can use `getTrapMax` as the bound C's `z_info->trap_max` gives.

### `PlayerProperty.viewAbilities`, `classHasAbility` and `raceHasAbility` checked against `view_abilities`, `class_has_ability` and `race_has_ability` in `player-properties.c`

`PlayerProperty` is the Java port of `struct player_ability`, and these three methods decide which abilities the "Race and class abilities" menu lists and under which heading. The first version built each copy from the wrong object's fields and labelled the race list as class abilities, and the heading field was typed as the `PF_*` player-flag enum, which has no class or race member. `group` is now a `PlayerFlagType` that starts at `PLAYER_FLAG_NONE`, `viewAbilities` copies each matching entry before setting the group on the copy as C's `memcpy` does, and `value` is an `int` so the race's resistance level is compared for exact equality. `PlayerPropertyAbilityTest` pins both `has_ability` functions, including the element branch and the unrecognized types, and the stale `PlayerAbility` class and its test are gone. The menu port can take the list `viewAbilities` builds, and the registry entries can be trusted to stay at `NONE`.

### `PlayerOverExertion.java` checked against the `PY_EXERT_*` enum in `player-util.h`

`PlayerOverExertion` names the eight penalties `player_over_exert` can inflict, which C stores as single bits so a caller can OR several together. The constants and their order already matched C, and `GameWorld.java` already builds the bloodlust combination of HP, CUT and SLOW from them, so the pass was documentation and tests. The enum and every constant now carry a block that gives the C value, the message and the effect each one has in `player_over_exert`, and records that a `Flag` stands in for the bit mask. `PlayerOverExertionTest` pins the nine names, their order, the position of each bit and the combined-flag behaviour, so the port of `player_over_exert` can rely on the constants without re-reading `player-util.h`.

### `BlowEffectType.getFromString` checked against the `effect_type` strings in `mon-blows.h`, `mon-init.c` and `blow_color` in `mon-lore.c`

`BlowEffectType` names the seven kinds of player attribute that can protect against a monster blow, which C stores as a bare string and compares with `streq`. The seven spellings, including the hyphenated `eat-food` and `eat-light` against the underscored `all_sustains`, already matched both the shipped `blow_effects.txt` and every branch of `blow_color`, so the pass was documentation and tests. The class, each constant, the field, the constructor and both methods now carry a block naming what `blow_color` does for that type, and the class block records that a missing `effect-type:` means a null type rather than a constant. `BlowEffectTypeTest` pins the seven spellings, the case, hyphen and whitespace near-misses, and that all 22 `effect-type:` lines in the shipped file resolve. Later work on the lore colour port can read each constant's block as the specification of its protection test.

### `RuneGroup.java` checked against `rune_group_text[]` in `ui-knowledge.c` and `enum rune_variety` in `obj-knowledge.h`

`RuneGroup` names the seven headings the rune browser files runes under, and each `RuneVariety` record points at one. The seven strings and their order already matched C, but the constants and the field had no blocks, and the class block implied that the enum's own order decides how the browser groups runes. The class, every constant, the field, the constructor and `getName` now carry a block naming the C variety and the record that holds it, and the class block records that C's trailing `NULL` entry is not ported and that no Java code reads an ordinal. `RuneGroupTest` pins the seven headings, their order, the ordinals against `enum rune_variety`, and `getName` against the constant identifier. Later work on the rune browser can take the headings from `getName` without re-reading `ui-knowledge.c`.

## Things not to drop

- `ObjectPropertyAssembler.java`: the `default` branch of the category `switch` can no longer be reached, and if it ever were it would add the record with a null index rather than dropping it.
- `ObjectBaseAssembler.java`: a non-`HATES_` token is resolved only as an `ObjectKindFlag`, so an `OF_` or `IGNORE_` token in `object_base.txt` is a soft error where C accepts it; the shipped file uses neither.
- `TrapAssembler.java`: `index` now advances only for kept records, so a record dropped on a soft error shifts every later `trapKindIndex` down by one , where C aborts on a bad record; `TerrainDataLoader.loadTraps` now stops the load if the first kind is not `no trap`, so only a later dropped record is tolerated.
- `PlayerProperty.java`: `do_cmd_abilities`, `textui_view_ability_menu` and the `view_ability_menu` call have no Java port yet. Until the call is restored `viewAbilities` builds its list and discards it, so its class-then-race grouping and the double listing of an ability both have are untested.
- `PlayerPropertyAssembler.java`: the class Javadoc still cites C line numbers (`init.c`, `z-util.c`) in the `finish_parse_player_prop` and `my_strcap` references; `PlayerProperty.PlayerPropertyValue` has no use left in `src/main`.
- `BlowEffectReaderTest.java`: the lash-type fallback comment cites a C line number for `mon-init.c`; it should name the file and `parse_eff_lash_type` instead.
- `PlayerUtils.java`: `overExert` is still a stub with no player parameter, so the bloodlust call in `GameWorld.java` and every other caller currently does nothing.
