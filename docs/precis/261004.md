# Precis — 2026-10-04

## Key points from the day

### `SustainStat` checked against `sustain_flag()` in `obj-properties.c`

C has no sustain type: `sustain_flag()` turns a stat index into the index of its sustain object flag by adding one, and
returns -1 outside 0 to 4. `SustainStat` is the Java enum standing in for that, and nothing yet calls it. Worked through
all five real stats and both sentinels, it matches C for every valid input; the out-of-range answer is `null`
where C gives -1, a change of representation no C caller can reach. The class, field, constructor and three methods now
carry Javadoc naming `sustain_flag()`, and the new `SustainStatTest` pins every stat, both bounds and the alignment with
`ObjectFlag`. The later ports of `obj-knowledge.c`, `obj-info.c` and the stat effect handlers can call it in place of
`sustain_flag()`.

### `ItemObject.modMessage` checked against `mod_message()` in `obj-knowledge.c`

`mod_message()` prints the line for a modifier the player has just learned by using an item, chosen by which modifier it
is and the sign of the item's value. The Java `modMessage` matched every string and sign test, but it read the item's
`modifiers` field directly, so an item whose map was `null` threw where C's zeroed array stays silent. It now reads each
value through `getModifierValue`, which treats a `null` map or an absent entry as zero. The method, its field and the
class now carry Javadoc naming `mod_message()`, and the new `ItemObjectModMessageTest` pins every message, both signs,
zero, the null map and the silent modifiers. The learn-by-use path in `PlayerKnowledge` can call it without guarding the
map.

### `PlayerKnowledge.cursesFindModifiers` checked against `object_curses_find_modifiers()` in `obj-knowledge.c`

`object_curses_find_modifiers()` runs when an item is worn: for each curse the item carries, it learns every modifier
the curse confers, and the curse's own rune with it. The Java first learned a modifier only when the player already knew
it, and dereferenced a missing map entry for every registry curse the item did not carry, so it threw or, once patched,
learned curses the item never had. It now skips a curse the item lacks, or carries at power zero, exactly as C skips a
zero-power slot, and tests `!modifierIsKnown` as C does. The method now carries Javadoc naming
`object_curses_find_modifiers()`, and the new `PlayerCursesFindModifiersTest` pins the found and not-found paths,
including the absent-curse case. The wear-time caller `objectLearnOnWield` can now hand it any item without a guard for
curses the item lacks.

### `PlayerKnowledge.objectLearnOnWield` checked against `object_learn_on_wield()` in `obj-knowledge.c`

`object_learn_on_wield()` runs the first time an item is worn: it learns the flags and modifiers that are obvious on
wielding, lets the item's curses reveal themselves, and finally searches for curses on every element the player can
already read. The Java tested the flag the wrong way round, so unknown flags were never learned and known ones were
announced again, ran everything inside the loop over stats, and omitted the element loop altogether. It now matches C
clause for clause; the method, the class note and the logger field carry Javadoc naming `object_learn_on_wield()`, and
the new `PlayerKnowledgeObjectLearnOnWieldTest` pins the flag and modifier paths, the once-only marker, each curse route
and the element loop. `PlayerBirthWieldAllTest` now gives its player a knowledge object and an object-property list,
which the corrected method always reads, so wielding the starting kit at birth can no longer pass for the wrong reason.

### `PlayerKnowledge.learnFlag` and the rest of `obj-knowledge.c` checked against C

`player_learn_flag()` learns a flag rune and then re-derives every object's known copy, which is how an object that has
just gained `OF_FRAGILE` in `uncurse_object()` shows it to a player who already knows the rune. The Java stopped after
`learnRune`, so a known rune left the object's known copy stale; every other method in the file matched C. `learnFlag`
now ends with `updateObjectKnowledge`, and the new `PlayerKnowledgeLearnFlagTest` pins the known-rune, new-rune and
no-rune paths and the number of inventory signals. Every Javadoc block in the file now carries a 261004 stamp, no C line
numbers, and corrected notes on curse kinds, trailing updates and autoinscription, so the uncursing code can call
`learnFlag` without a guard.

### `Curse.isFullyKnown` checked against `object_fully_known()` in `obj-knowledge.c`

`object_fully_known()` asks whether the runes and the effect of an object are all known, and the port runs it on a curse
as C does, because C's curse objects carry a real kind. The Java demanded an entry for every modifier in
`knownModifiers`, sentinels included, so a curse that had never been through `knowObject` was never fully known, which
broke five curse tests. The loop now skips the two sentinels and reads both sides with a default of zero, as C reads a
zeroed array. The full suite is green, and the curse-side `knowObject` can rely on `isFullyKnown` for a curse that
confers nothing.

### `Curse.hasStandardToH` checked against `object_has_standard_to_h()` in `obj-knowledge.c`

`object_has_standard_to_h()` says whether an object's to-hit is the unremarkable one for its kind, and C's null-kind
hack at the head of it was assumed to apply to curse objects. It does not, because `write_curse_kinds()` gives them a
kind, so for a curse the answer is `to_h == 0`, which is exactly what the Java already did. The Javadoc on
`hasStandardToH` and
`isFullyKnown` now says so, `PlayerKnowledge.learnRune` is package-private again, and the new `CurseIsFullyKnownTest`
pins the three real curses with a to-hit and every comparison in the fully-known checklist, including the identity test
on the effect. The curse-side `knowObject` can now be read as a straight port with no recorded divergence.
