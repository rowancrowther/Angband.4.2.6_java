# Precis — 2026-10-12

## Key points from the day

### `PlayerOptionTypes.java` checked against the option type enum in `option.h`, `option_type_name` in `option.c` and the type column of `list-options.h`

`PlayerOptionTypes` names the five option categories, and C uses each category's number as its options-menu page number. The constants had been declared in a different order from C, so `ordinal()` did not equal the C value, although nothing in Java depended on it yet. You reordered them to C's order, which made every comparison pass, and the class, each constant, the field, the constructor and `getName()` now carry Javadoc recording why the order must not change and which C constants (`OP_MAX`, `OPT_PAGE_MAX`, `OPT_PAGE_BIRTH`) have no Java equivalent. `PlayerOptionTypesTest` pins the ordinals, the names, the page boundary and the contents of each page against the C table. The later options-menu port can take the page index straight from `ordinal()` or from an explicit page list, and the test will catch any reordering.

### `GameInputHolder.java` checked against the `get_*_hook` pointers in `game-input.c` and their assignment in `textui_input_init()`

`GameInputHolder` is the Java stand-in for C's family of hook pointers, which all start `NULL` and are assigned together by the text front-end. Every middle-layer request for a direction, item, quantity or yes/no answer goes through it, so an unset or `null` holder would break all of them. The holder starts as a `DefaultGameInput`, which matches the unset-pointer fall-backs, rejects `null`, and `resetInstance()` is the equivalent of clearing the pointers. The class, fields, constructor and methods now carry Javadoc recording the two deliberate differences from C (the hooks swap as one object, and `null` is refused), and `GameInputHolderTest` pins the start-up state, the fall-backs, install, replace, reset and the `null` rejection. A front-end or test fake that overrides one hook extends `DefaultGameInput`, as the C tests override only `panel_contains_hook`.

### `ObjectFlag.java` checked against the object flag enum in `obj-properties.h` and `list-object-flags.h`

`ObjectFlag` is the Java form of C's `OF_*` list, whose order is the savefile layout and whose first five entries must stay in stat order for `sustain_flag()`. All 38 flags, their order, their display labels and both sentinels already matched C, so nothing in the code changed. Every constant now carries a one-line description, and the class and field Javadoc record that `OF_BLESSED` has a six-character label where C's header promises five. `ObjectFlagTest` gained a label-length check and a `Stats` to `SustainStat` to `ObjectFlag` chain check that pins all three orders to the stat-plus-one rule. The object-flag bitset and `OF_SIZE`-style helpers can build on this enum, and a five-column display must truncate `" Bless"` itself.

### `ObjectKindFlag.java` checked against `list-kind-flags.h` and `grab_element_flag` in `obj-init.c`

`ObjectKindFlag` is the Java form of C's `KF_*` list, which controls ego-item generation, artifact kinds, name display and launcher ammunition. It carried four extra `KF_IGNORE_*` constants that C does not have, because C turns `IGNORE_FIRE` and its siblings into element info, so every `IGNORE_` token in `object.txt` was stored as a kind flag instead and `KF_MAX` was 19 where C's is 15. You removed the four constants and made `ItemObjectAssembler` set `EL_INFO_IGNORE` on the kind's own element info, and the class, each constant, the field, the constructor and `getFlag()` now carry Javadoc naming the C function that reads each flag. `ObjectKindFlagTest` pins the 16 names, their order and the absence of any ignore constant, and `ItemObjectReaderTest` gained loader cases for ignore, kind-flag and bad-token handling. The object-base and any later kind loader must route `IGNORE_` and `HATES_` tokens to element info rather than to this enum.

### `Quark.java` checked against `quark_add`, `quark_str`, `quarks_init` and `quarks_free` in `z-quark.c`

`Quark` is the Java form of C's string-interning table, where an integer handle stands in for text such as an inscription. `add` always stored a new entry, whereas `quark_add` returns the existing handle when the text is already held, so any caller comparing handles would have seen equal inscriptions as different. You made `add` scan for an exact match before allocating, and the class, fields and every method now carry Javadoc recording the dedup rule, the reserved handle 0 and the accepted size deviation. `QuarkTest` replaced its test that pinned the old behaviour with cases for repeated text, handle sequence after a repeat, case and length near-misses, and a match after a merge. The inscription, ignore and savefile ports can now compare handles directly, as the C callers do.

### `ClassMagic.java` checked against `struct class_magic` in `player.h`, `spell_by_index` in `player-spell.c` and the magic parsing in `init.c`

`ClassMagic` is the Java form of a class's spellcasting profile, and the books it holds form one flattened spell-index space that queued spell commands store and replay. The behaviour already matched C, including the out-of-range and empty-book cases, but the Javadoc called `spellWeight` the weight of the spellbooks and `numBooks` the declared count, and every `ClassMagic` call in the tests still passed the removed `numBooks` argument. You had dropped that argument so the count comes from the book list, which is what C's `num_books` ends up as; the class, fields, constructor and methods now carry Javadoc recording that and the armour-allowance meaning of `spellWeight`, and the test call sites were updated. `ClassMagicTest` gained boundary, empty-book, round-trip and zero-filled-sentinel cases derived from `spell_by_index` and the `sidx` numbering. Later spell-casting ports can rely on `indexOfSpell` and `spellByIndex` being exact inverses across book boundaries.

### `CurseData.java` checked against `struct curse_data` in `object.h` and its readers in `decrease_timeouts`, `curses_are_equal`, `copy_curses` and `append_object_curse`

`CurseData` is the Java form of a curse's per-object power and timeout, and C wraps no behaviour around the struct itself. Both fields, the decrement, the unclamped countdown and the power-only equality already matched C, so no code changed. Two Javadoc claims were wrong: `setPower` said setting zero removes a curse, when C's `remove_object_curse` also clears the timeout and `ItemObject.removeCurse` deletes the map entry, and `equals` said `cursesAreEqual` is a plain `Map.equals`, when it walks the curse registry. The class, fields and every method now carry Javadoc naming the C reader of each field, and `CurseDataTest` gained constructor, power-versus-timeout, countdown and zero-power-versus-absent cases. Anything that compares curse maps with `Map.equals` should expect the stricter answer than C gives.

### `PlayerHistoryEntry.java` checked against `struct history_entry` in `player.h`, `parse_history_chart` and `parse_history_phrase` in `init.c` and `get_history` in `player-birth.c`

`PlayerHistoryEntry` is the Java form of one weighted line of backstory, holding a cumulative roll threshold and a phrase. The class matched C, including the hoist of the successor to the chart, but the repo's copy of `history.txt` had lost the trailing space on all 149 phrases that carry one in C, so `get_history` would have run the words of every biography together, and `HistoryReaderTest` had pinned the stripped text. You restored the file from C's copy with its `record-count:165` header, and the class, fields, constructor and getters now carry Javadoc recording the threshold rule and why the spacing is data. `PlayerHistoryEntryTest` pins the round trip, the draw-by-draw picks for chart 1, the 1-100 range, the 149/16 spacing split and that every unspaced phrase ends a chain, and `HistoryReaderTest` now expects the trailing space. Anything that edits or regenerates `history.txt` must keep trailing whitespace, and the test will fail if it is lost.

### `ArgumentChoice.java` checked against the `choice` member of `union cmd_arg_data` and `cmd_set_arg_choice`, `cmd_get_arg_choice` and `cmd_copy` in `cmd-core.c`

## Things not to drop

- `Quark.java` `merge` leaves a gap in the handles (the other table's handle 1 lands at the highest handle plus 2) and does not deduplicate text held by both tables. It has no C counterpart, so decide what it is for before any caller uses it.
- `Quark.java` `merge`, `size` and `containsText` throw a bare `NullPointerException` on an uninitialized table, without the logged message that `add` and `getQuark` give.
- `ObjectBaseAssembler.java` does not handle `IGNORE_` tokens, which C's `parse_object_base_flags` sends through `grab_element_flag`; they would be rejected as invalid flags. `object_base.txt` has none today, so this is dormant.
- `ItemObjectAssembler.java` does not handle `HATES_` tokens on an object kind, which C's `parse_object_flags` accepts. `object.txt` has none today, so this is dormant.
- The options-menu or `init_options` port needs a Java stand-in for C's `OPT_PAGE_MAX`, which is defined as `OP_SCORE` and so only works because of the type order; use an explicit page list (interface, birth, cheat) in whichever class holds `option_page`, not a constant on `PlayerOptionTypes`.
- `ClassMagicAssembler.java` now rejects more `book:` lines than declared, as C's `parse_class_book` does, but a book dropped for its own fault also drops the whole `magic:` record, so one typo reports two errors and the class loads as a non-caster.
- Decide whether any error in parsing should be fatal: C quits on every parse error (`run_parser` in `datafile.c`, `lookup_realm` in `player.c`), while the Java loaders collect soft errors and carry on, which is deliberate for now.
- `HistoryGrammar.g4` takes exactly one `phrase:` line per `chart:` line, where C's `parse_history_phrase` appends repeated phrase lines and accepts a chart line with none. The shipped `history.txt` has neither, so this is dormant.
- `ArgumentString.java` and `ArgumentTarget.java` have no Javadoc on `type()` and `copy()` and no dated provenance line on the class.
- `Command.java` `getDirection` rejects only `DirectionEnum.DIR_NONE`, but C's `cmd_get_direction` rejects the value 5, which is also `DIR_TARGET`; a stored `DIR_TARGET` (what `DirectionEnum.fromKey(5)` returns) would be accepted as a real direction in Java and re-prompted in C.
- `Command.java` `setArgDirection` and `getArgDirection` accept a `null` direction, and the read then throws from `Optional.of`; C's int has no such state.
- `Command.java` `getArgItem` throws from `Optional.of` when the stored item is `null`, but C stores `NULL` under `"original_item"` in `cmd-wizard.c` and `cmd_get_arg_item` returns `CMD_OK` with it; the wizard-command port must settle how a null item reads back.
