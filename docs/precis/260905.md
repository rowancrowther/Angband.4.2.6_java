# Precis — 2026-09-05

## Key points from the day

### `wieldAll` closes out character birth, and its tests flushed out a `Pile` bug along the way

`wieldAll` is the last step of birth: once the starting kit is bought and carried, it wears whatever fits before play
begins. Verifying it against the C original turned up an off-by-one in the slot-bounds check, and writing the tests for
it separately turned up a bug in `Pile`'s bulk-insert that made the stack-split branch throw on every call. Both are
fixed now: the bounds check excludes the one-past-the-end value the slot lookup's own fallback can return, and the pile
merge clears an item's ownership before reinserting it rather than tripping its own integrity guard. The method is
Javadoc'd and has six tests covering the ordinary wear, both skip branches, a same-scan occupancy race, and the
split-and-carry-over case the `Pile` fix depends on. Both regressions now have a test standing over them, so a repeat of
either shows up as a red build rather than a birth-time crash.

### `setIgnoreFlag` gives `ObjectKind` a generic setter for either ignore bit

`setIgnoreFlag` is the write-side counterpart to the existing `hasIgnoreFlag`: one flag-typed setter standing in for C's
`kind_ignore_when_aware` and `kind_ignore_when_unaware`, which are each a single flag hardcoded into an otherwise
identical function. Nothing downstream had to change — the existing boolean setters and the `ObjectIgnore` wrappers keep
working alongside it. The port itself is a one-line delegation to `Flag.on`, verified to match C's `|=` bit-set exactly,
including that setting an already-set flag is a no-op rather than an error. Its Javadoc also records that the C
functions' `player->upkeep->notice` side effect is deliberately left to the caller, so that responsibility isn't lost
when the `ObjectIgnore` wrappers are finished.

### `ObjectIgnore.kindIgnoreWhenAware` closes out the pairing `setIgnoreFlag` set up

`kindIgnoreWhenAware` is the wrapper `setIgnoreFlag`'s Javadoc was written to point at: it sets the aware-ignore bit and
then raises `PN_IGNORE` on the player's upkeep, so the two lines of
`kind_ignore_when_aware` land as one call again instead of being split across a generic bit-setter and a caller that
remembers the notice flag itself. Nothing downstream changes — the existing
`ObjectKind.setIgnoredAware` keeps serving the one caller that already raises `PN_IGNORE` on its own account. Verified
against the C original, Javadoc'd, and covered by five tests spanning a fresh kind, the sibling flag staying untouched,
and the flag already being set. Any future caller reaching for C's `kind_ignore_when_aware` now has a single method that
does exactly what the name says, rather than having to reconstruct the pairing from two places.

### `autoinscribePack` walks the gear so `applyAutoinscription` doesn't have to be called by hand

`autoinscribePack` is the loop C's `autoinscribe_pack` puts around `apply_autoinscription`: every item the player
carries gets one call, forward, in gear order. It is the first caller of
`applyAutoinscription` other than a test, so it is also the first place the guards that method already had are exercised
together across more than one item at once. The port is a single
`while` over the gear's iterator with no branching of its own, verified to match C's `obj->next`
walk and covered by five tests establishing that an empty gear does nothing, that every item is visited rather than just
the first, and that one item failing a guard has no bearing on the next. Autoinscription on pickup and on rest now has a
real entry point to be wired to, rather than a function that only a test had ever called.

### `autoinscribeGround` needed a bounds guard C's `square_object` already had

`autoinscribeGround` is `autoinscribePack`'s twin for the floor: the port of C's
`autoinscribe_ground`, walking the square beneath the player instead of the gear. A first pass missed that C's starting
point, `square_object`, answers `NULL` for a grid outside the level, so its loop simply never runs; the equivalent Java
call chained straight through to a `null` square instead, which would have crashed the first time this ran against an
out-of-bounds player position. The fix adds the same bounds check up front and returns early, matching C's silent no-op
exactly. Along the way, testing it turned up a more interesting fact worth recording: a floor item can never receive a
kind-level autoinscription through this path, because `applyAutoinscription`'s own
"is it carried" guard is never true for something on the ground — only the rune side, which runs before that guard, ever
reaches a floor item. Five tests now cover the empty square, the guard that keeps kind notes off the floor, the rune
notes that do land, multiple floor items being visited, and the out-of-bounds case. Anything that later calls this on
the player's square inherits both the crash fix and a test that would catch a regression of either.

### `playerOutfit` closes out birth's outfitting, and testing it found a crash in `ItemObject`'s bare constructor

`playerOutfit` gives a freshly-born character their starting knowledge and starting kit: the obvious object properties,
the class's rolled equipment gated and excluded by birth options, and a final pass through `wieldAll` and
`updateObjectKnowledge`. Verifying it against the C original caught a dangling-else in the exclusion-option logic that
silently dropped every non-negated exclusion regardless of the option's own value, and writing tests for the corrected
method then surfaced a second, unrelated crash: the bare `ItemObject` constructor left several flag and collection
fields uninitialised, so the method's own known-item shadow threw the moment it was marked assessed. Both are fixed
now — the exclusion logic reads the option correctly in all four cases, and the constructor leaves every collection
ready to use without needing a full data-file build first. Twelve tests cover the obvious-knowledge fields, the
flag-property loop, the starting-kit gating, all four exclusion cases, the gold clamp and the missing-kind guard, so
birth can hand out a starting kit without either bug recurring.
