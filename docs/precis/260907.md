# Precis — 2026-09-07

## Key points from the day

### `setFullName` gives the character name a real write path, closing out the read/write pair
`getFullName` has been waiting on since yesterday

`setFullName` writes the character's full name, the port's counterpart to the read half `getFullName` got documented
yesterday. Until today the field had no writer outside test reflection, so neither half of the pair could be exercised
through real code; along the way, the first attempt at reproducing C's fixed-buffer truncation turned out to crash on
any ordinary short name, since it sliced to a fixed length instead of bounding the slice by whatever the input actually
was. The fix bounds the cut by the shorter of the input's own length and the buffer's cap, so both short and long names
come through without exception. Seven tests now cover the accessor pair end to end, including the exact length at which
C's buffer starts truncating, and `PlayerBirth`'s quickstart roller-restore path has a real name writer behind it
instead of a dead field.

### `Birther.copy()` and `PlayerBirth.LoadRollerData` verified against C's raw struct assignment and
`load_roller_data`, catching two divergences before they shipped

`Birther.copy()` and `PlayerBirth.LoadRollerData` are the port of C's raw struct assignment `*prev_player = temp`
and `load_roller_data`, the other half of the roller's undo alongside yesterday's `saveRollerData`. The first
verification pass found both wrong: `copy()` had the copy depth backwards, deep-copying race and class instead of
sharing them while aliasing the stat map instead of copying it, and `LoadRollerData` reassigned a local variable to a
new `Birther` instead of mutating the caller's own object in place, which would have silently broken the one real C
caller's swap between two rolls. Both were fixed, then documented and covered by a new test suite exercising the null,
two-object and same-object-swap cases the aliasing contract depends on. The roller's undo and the quickstart restore now
have a verified round trip to build the birth screen's back button on.

### Six older test files fixed after a full suite run turned up failures unrelated to today's own changes

A full `./gradlew test` run surfaced two dozen failures across `PlayerBirthGetMoneyTest`, `PlayerBirthBuyStatTest`,
`PlayerBirthResetStatsTest`, `PlayerBirthRecalculateStatsTest`, `PlayerBirthSellStatTest` and
`PlayerBirthPlayerInitTest`, none of them touching anything worked on today. All six shared one stale assumption:
their reflection helpers for `Player`'s gold fields were written for `int` and never updated once `au`/`auBirth`
widened to `long`, so reading the field back threw instead of asserting anything. Each helper's `getInt` became
`getLong`, and the couple of call sites reading the raw boxed value do the same unboxing as `long` now. The suite runs
clean end to end again, so a green result going forward means the whole codebase, not just whatever a change happened to
touch.

### `PlayerBirth.doBirthReset` ported, wiring the birth screen's full reset together

`doBirthReset` is what the birth screen's reset button calls: it re-applies any quickstart snapshot, rebuilds the
derived character fields, drops the depth back to town and recalculates every bonus. The method arrived with a return
type left over from an earlier draft and no return statement on any path, which would have kept the whole file from
compiling; once you brought the signature back to `void` to match the C original, verification found the four steps
already in the right order and behind the right guard, so nothing else needed changing. A new test suite now pins the
compound quickstart guard from both edges and the trailing depth-reset/heal pair, so the birth screen's reset has a
verified base to build the rest of the screen's commands out from.

### `GameWorld.setCharacterDungeon` documented and covered, completing the flag's accessor pair

`setCharacterDungeon` is the write half of the `character_dungeon` flag, sitting alongside `hasCharacterDungeon`
which was documented back on the 20th. C never gathers the flag's assignments behind one function, so several of the
birth, save-load and level-generation subsystems this port is working through will eventually route through this one

exactly, so the pass was pure documentation and testing rather than a fix. The flag's read and write sides are now both
documented and both covered, ready for whichever subsystem starts calling the setter for real.

### `PlayerBirth.intToRoman` fixed, documented and tested, closing out the dynastic-suffix pair alongside `romanToInt`

`intToRoman` builds the Roman-numeral suffix `doCmdBirthInit` appends when a character name is reused, the write half of
the pair `romanToInt` already covers. Verification found the greedy symbol-table walk used a strict comparison where C's
uses an inclusive one, so no exact match to a symbol's own value was ever consumed; since the smallest symbol is worth
one, every positive input eventually ran the table out and returned nothing at all, silently breaking every dynastic
suffix rather than just the odd one. Rowan brought the comparison in line with C's own inclusive test. A new test suite
pins the exact-match boundary that broke it alongside the ordinary composite cases, and the suffix-incrementing path now
has a verified numeral builder behind it.

### `PlayerClass.getClassFromIndex` and `PlayerRace.getRaceFromIndex` ported, giving a class/race lookup by position

Both methods are the port of C's `player_id2class` and `player_id2race`, which linear-search a linked list for the node
matching a requested id. Neither had a caller yet, so nothing downstream was broken, but the first pass found each
method's bounds check only guarded the upper end: a negative index fell through to a raw list read and would have thrown
where C's unsigned id type just fails the search and returns nothing. Rowan added the missing lower bound to both. Two
new test suites now pin the boundary — first index, last index, past-the-end and negative — for each, so whichever
birth-screen command ends up choosing a class or race by position has a verified lookup to call.

### `PlayerBirthStateRegistry`'s `prev`/`quickstartPrev` pair fixed, closing a null-snapshot trap the same day
`doCmdBirthInit` was wired into it

`prev` and `quickstartPrev` are the two roll snapshots C's own birth-state comment groups alongside the fields
documented earlier today, added to the registry alongside a guard on the reset method so it only ever builds its maps
once. Wiring `doCmdBirthInit` straight to the registry's quickstart accessors in the same pass exposed a real gap: the
snapshot fields defaulted to a bare `null` with no backfill, so the first quickstart birth of a run would have thrown
partway through saving the roller data. The fix has both getters lazily backfill a fresh snapshot instead, whose zeroed
age matches the exact sentinel the C original's own comment already relies on to mean "nothing stored yet".
`doCmdBirthInit`'s test suite - broken by the same wiring change, since it had been reaching into fields that moved -
and a matching new suite for the registry's pair both cover the fix now, so the birth screen's quickstart path has a
verified snapshot underneath it instead of a trap waiting for the next caller.
