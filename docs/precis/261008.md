# Precis — 2026-10-08

## Key points from the day

### `EgoItem.egoHasIgnoreType` checked against `ego_has_ignore_type` in `obj-ignore.c`

`egoHasIgnoreType` answers whether an ignore category is valid for an ego by walking the kinds it may apply to and the
`qualityMapping` table. It had no Javadoc, and the table it reads, `ObjectInfo.qualityMapping`, and the `possItems`
field it walks were undocumented or described wrongly. The check found no difference from C, with all 37 table rows in
C's order and the same case-sensitive substring match against the kind's name. `EgoHasIgnoreTypeTest` pins the
empty-identifier rows, the named identifiers, the Bow/Crossbow case split and the dragon-armour groups against figures
worked from C. Whatever ports the options menu next can rely on this function to offer the same categories for each ego
as C does.

### `ItemObject.isKnownArtifact` and `ObjectUtils.objIsKnownArtifact` checked against `object_is_known_artifact` and
`obj_is_known_artifact`

C has two known-artifact tests, one reading only the known half (`obj-knowledge.c`) and one that also requires the real
object to be an artifact (`obj-util.c`), and `isArtifact` equals neither. The first check found `objIsKnownArtifact`
declared as an instance method on a class with no instances; you made it static and both then matched C clause for
clause. `KnownArtifactTest` pins the one input where the two disagree (a known half with an artifact on a real object
with none), and the Javadoc on both methods and on the `artifact` and `known` fields says which C function each stands
for. The sites that need these tests, `object_desc` and `compare_items` among them, can now be ported without reaching
for `isArtifact`; the known half still has no artifact setter, so `object_touch` has to add one.

### `ItemObject.applyCurseAttributes` and `ItemObject.objectWeightOne` checked against `apply_curse_attributes` and

`object_weight_one`

`applyCurseAttributes` folds the active curses into a scratch copy for the curse pricing, and `objectWeightOne` gives
the weight of one item once its curses have had their say. Both already matched C, but the `objectWeightOne` Javadoc
still said the curse map keeps insertion order and is sorted first, which stopped being true when the map became a
`TreeMap`. The Javadoc on both methods and on the `toHit` and `toDam` fields now says the order comes from
`CURSE_ORDER`, and four new tests pin the two cases C's numbering could split: curse index 0 as the held-back curse and
as an active weight curse, since C's loop starts at 1 and the port numbers from 0. The curse pricing and every weight
and burden caller can rely on both methods agreeing with C on ordering, saturation and the resistance merge.

### `ItemObject.objectValue`, `objectKindName` and `objDescNameFormat` checked against `object_value`,
`object_kind_name`

and `obj_desc_name_format`

`objectValue` prices a stack by what the player knows, `objectKindName` builds a kind's bare name, and
`objDescNameFormat` expands the `&`, `~`, `|x|y|` and `#` markers in a name template. You had widened all three to
`public`, as in C, which left the `objectValue` Javadoc still calling it private. All three match C apart from the
divergences already recorded on `objDescNameFormat`, so only the Javadoc changed, and the class and `logger` blocks now
say the methods are public and where the template errors are logged. `ItemObjectNameAndValueVisibilityTest` pins the
linkage, which the reflection in the older tests would not notice losing. The store code can call `objectValue`
directly, and the ignore menus and `object_desc` can reach the flavour, `#` and plural paths that only the unit tests
exercise today.
