# Precis — 2026-10-10

## Key points from the day

### `MonsterFlag.java` checked against `struct monster_flag` in `monster.h` and `monster_flag_table[]` in `mon-util.c`

`MonsterFlag` in `monsters/` was the Java copy of the struct that holds an `RF_` index, an `RFT_` category and a lore description. It had three private fields and no constructor or accessors, nothing used it, and its name clashed with the `MFLAG_*` enum in `monsters/enums/`. `MonsterRaceFlag` already carries all 85 rows of `list-mon-race-flags.h` in C's order, so you deleted the stub and the enum now stands in for the struct. The class, field, constructor and accessor blocks of `MonsterRaceFlag` now say which struct member each one is, that the constant is the index, and that the `RF_MAX` terminator row has no counterpart. `MonsterRaceFlagTableTest` pins every row of the C table by index, category and description, so later work on the lore masks can rely on `getCategory` and `getDescription` returning C's `type` and `desc`.

### `ObjectRandart.artifactSetDataNew` checked against `artifact_set_data_new()` in `obj-randart.c`

`ObjectRandart` is the home of the random-artifact generator, and `artifactSetDataNew` is the only method in it that is ported so far; `doRandart`, `storeBasePower` and `artifactPower` are chapter 7 stubs. The class had no Javadoc, and the method's block quoted a C line number that the next stamp in `obj-randart.c` would have made wrong. The wrapper hands back `new ArtifactSetData()`, whose constructor sets the six start and increment values and zero-fills every map, which is what C's `mem_zalloc` calls and six hand-set assignments do. `ObjectRandart` now has a class block that names the stubs, and the method block names the C file and function instead of a line. `ObjectRandartArtifactSetDataNewTest` already pins the defaults, the zeroed maps and the unloaded-registry failure, so the chapter 7 functions can build on a set of statistics known to start empty.

### `ObjectUtils.java` checked against the gear, flavour, prep and knowledge helpers in `obj-gear.c`, `obj-util.c`, `obj-make.c`, `obj-slays.c`, `obj-curse.c` and `obj-knowledge.c`

`ObjectUtils` is the landing spot for the free-standing object helpers: pack combining and quiver capacity, slot and label lookups, flavour set-up, `object_prep`, the slay, brand and curse merges, and the flag and element knowledge checks. Four routines in it, `packOverflow`, `equipLearnAfterTime`, `objectDesc` and `doCurseEffect`, are still stubs, and the rest had been ported and documented in earlier passes. Every ported routine was walked against its C original and none differs beyond the divergences the Javadoc already records, so no code changed. Two Javadoc blocks, `flavourAssignRandom` and `copyCurses`, had run-on sentences and were reworded with their provenance lines refreshed. The existing `ObjectUtils*Test` classes and the gear, slot, quiver and known-artifact tests already cover every ported routine, so the file can be treated as settled while the four stubs wait for their chapters.

### `GameConstants.java` checked against `struct angband_constants` in `init.h`, `init_game_constants` and `pl[]` in `init.c`, and the static tables in `obj-power.c`

`GameConstants` holds the `constants.txt` scalars behind its accessors, the `init` pipeline that runs every loader, and the `archery`, `flag_sets` and `element_sets` tables built at the end of `init`. Every accessor reads the component that matches its `z_info` field and each table row matches C figure for figure, but the Javadoc was thin: five accessor blocks named the wrong `constants.txt` label, `loadGameConstants` was described as a soft failure when it throws, and several blocks cited C line numbers. The file was documented in full, so each accessor now names its `z_info` field, the dead members and the load-order differences from C are stated, and the line numbers are gone, with no code changed. `GameConstantsInitTablesTest` now pins the header constants, the scalars as they stand in C's `constants.txt` and the three tables, so a parser that files a label under the wrong component fails a test.

### `Slay.java` checked against `struct slay` in `object.h` and `same_monsters_slain` in `obj-slays.c`

`Slay` is the Java copy of one `slay.txt` record: its code, name, verbs, race flag or base, two multipliers and a power rating. It also carries `sameMonsterSlain`, the rune-grouping test that `ObjectUtils` and the knowledge code rely on. Every field maps to a member of the C struct, the extra `monsterType` and `monsterLevel` split and the `copy`, `equals` and `hashCode` methods are documented as the port's own, and the single `==` on the base reference gives the same answer as C's four hand-written null cases. No code or Javadoc needed to change, because the blocks already name the C file and function and every claim in them held when re-read. `SlayTest` and `SlayEqualsTest` already cover the full truth table of `same_monsters_slain` and the equality contract, so `Slay` can be treated as settled.

### `MagicBook.java` checked against `struct class_book` in `player.h` and `parse_class_book`, `parse_class_spell` and `write_book_kind` in `init.c`

`MagicBook` is the Java copy of one spellbook in a class's `magic.books`: its tval, sval, dungeon flag, realm and spells. The fields that C keeps on the book all match, but the Javadoc did not say that the name, graphics and loot properties are the port's own copies, and the field block claimed a book could carry no glyph when the assembler always supplies one. Ten test fixtures also still called an eleven-argument constructor from before the spell count was derived from the spell list, so the test tree did not compile. The class, field, constructor and accessor blocks now state which C member each one is and where the sval lookup differs from `write_book_kind`, and the fixtures were moved to the ten-argument constructor with real spell lists. `MagicBookTest` now pins the spell count and the one-based, per-tval sval numbering, so the class loader and the `canBrowse` matching can rely on both.

### `MonsterBase.java` checked against `struct monster_base` in `monster.h` and `parse_mon_base_*` in `mon-init.c`

`MonsterBase` is the Java copy of one `monster_base.txt` template: its name, glyph, pain set, inherited race flags and `desc:` text, which every `MonsterRace`, slay, pit and summon refers to by name. It had Javadoc on the class and fields but none of it said which C member each one stood for, and nothing tested it. Every field matches the C struct; C's single `text` member is held twice, as `inGameName` and `description`, and C's `next` link is replaced by the list in `MonsterRegistry`. The class, field, constructor, `toString` and accessor blocks now record both divergences and that `pain` and `description` have no accessors yet. `MonsterBaseTest` pins all 56 records of the C data file by glyph, pain set and text, and the OR-ing of repeated `flags:` lines, and it caught a corrupted `desc:Elemental` line in `lib/gamedata/monster_base.txt`, now fixed.

### `FlavourKind.java` checked against `parse_flavor_kind` and `parse_flavor_flavor` in `init.c`

`FlavourKind` is the Java grouping of one `kind:` block of `flavor.txt`: its tval, its glyph and the flavours that disguise that type. C has no such type, because it copies the tval and glyph onto every `struct flavor` and chains them all into one list built newest-first. The constructor stores the tval and glyph once, tells each flavour who owns it, and keeps the flavours in reverse file order, which gives the same list order within a type as C's head insertion, and the three `ObjectUtils` passes only ever compare flavours of one type. The class, field, constructor and accessor blocks now say which C values each one stands for, that the glyph is a `char` where C holds a `wchar_t`, and that the list is hidden but the flavours inside it stay writable. `FlavourKindTest` pins the reversal, the ownership links, the copy of the caller's list and the read-only view, so the random-assignment pass can rely on a draw of zero landing on the last file entry as it does in C.

### `PlayerBody.java` checked against `struct player_body` in `player.h`, `player_embody` in `player-birth.c`, `equipped_item_slot` in `player-calcs.c` and `object_is_equipped`, `equipped_item_by_slot_name` and `slot_by_name` in `obj-gear.c`

### `Core.java` checked against `play_game` in `ui-game.c`

`Core` is the middle end's thread body: `gameLoop` builds the engine, registers the handlers, runs the data load and then blocks on the core's inbox, and `handleChannelOutput` decides what each front-end message does. It has no C class to match, and `gameLoop` is only the skeleton of `play_game`, so the mode switch, `start_game`, the player-alive loop and `close_game` are later chapters. The behaviour that exists matches the shutdown order C relies on, and the `true` that `loadGameConstants` returns means a stop was handled mid-load with `STOPPED` already sent. The class, field and method blocks now say that the load calls `handleChannelOutput` too, what each message does today, and what of `play_game` is missing, and a code comment that called the inner lifecycle switch compile-time exhaustive was corrected. `CoreHandleChannelOutputTest` runs the method inline and pins the verdict and the reply for every message kind, which `CoreTest` could not do because it never gets past the load.

### `MonTimedFlags.java` checked against the `MON_TMD_FLG_*` defines in `mon-timed.h` and their use in `does_resist` and `mon_set_timed` in `mon-timed.c`

### `PlayerOptions.java` checked against `options_init_defaults`, `options_restore_custom`, `options_restore_maintainer` and `options_init_cheat` in `option.c`

`PlayerOptions` is the Java copy of `struct player_options`: the on/off option flags plus the hitpoint warning, movement delay, delay factor and name suffix, and the four `option.c` functions that reset and restore them. The first version of `restoreCustom` returned `false` for a clean file, never matched a name, stopped at the first bad line and reported nothing to the player, so a player's customized defaults never reached `initDefaults`. `restoreCustom` now trims each line, matches whole names on the right page, sends a message for every line it rejects, skips it and carries on, and returns `true` unless the file cannot be read. The class, field, constructor and method blocks now say which C member each one is, that the "0 to 9" in C's struct comment is stale for the delay factor, and where the messages differ from C's wording, with the C line numbers gone. `PlayerOptionsRestoreCustomTest` and the new `PlayerOptionsInitDefaultsTest` pin the file format C writes, every line C rejects, and the BIRTH and INTERFACE page rules, so the options menu can later call the restore functions and rely on C's results.

## Things not to drop


- `mon-util.c`: `describe_race_flag` and `create_mon_flag_mask` have no Java port yet. Both read the flag table, `mon-lore.c` builds its masks through `create_mon_flag_mask`, and `describe_race_flag` returns an empty string for an out-of-range flag where `getDescription` does no range check.
- `SlayAssembler.java`: a `slay.txt` record with neither `race-flag` nor `base` is rejected, where C's `parse_slay_race_flag` and `parse_slay_base` accept it and only forbid naming both.
- `ClassSpellBookAssembler.java`: the graphics and properties of a book are applied only when its kind is first created, where C's `parse_class_book_graphics` and `parse_class_book_properties` rewrite the shared kind each time a class lists the book.
- `PlayerBody.java`: the constructor pushes the slot count to the character sheet for every body built, including each `body.txt` template and each `copy()`, where C reads `player->body.count` on demand; `Player.java` pushes it again after the race body is set, so the constructor push is redundant and leaves the sheet holding the last template built until then.
- `GameState.java`: `initGameState` is an empty method that nothing calls, and its Javadoc already says it can be deleted.
- `PlayerBirth.java`: the birth code calls `initBrands`, `initSlays` and `initCurses` on a new `KnownObject`, whose constructor already calls them.
- `Player.java`: about eighty Javadoc blocks still quote C line numbers, which go stale as soon as a function is stamped.
- `PlayerOptions.java`: `restoreCustom` and `restoreMaintainer` are private, where C's `ui-options.c` calls both from the options menu, so they need widening when that menu is ported.
- `PlayerOptions.java`: `lazymoveDelay`, `delayFactor` and `nameSuffix` have no accessors, and `option_set` and `options_save_custom` are not ported yet.
