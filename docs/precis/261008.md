# Precis — 2026-10-08

## Key points from the day

### `EgoItem.egoHasIgnoreType` checked against `ego_has_ignore_type` in `obj-ignore.c`

`egoHasIgnoreType` answers whether an ignore category is valid for an ego by walking the kinds it may apply to and the
`qualityMapping` table. It had no Javadoc, and the table it reads, `ObjectInfo.qualityMapping`, and the `possItems`
field it walks were undocumented or described wrongly. The check found no difference from C, with all 37 table rows in
C's order and the same case-sensitive substring match against the kind's name. `EgoHasIgnoreTypeTest` pins the
empty-identifier rows, the named identifiers, the Bow/Crossbow case split and the dragon-armour groups against figures
worked from C. Whatever ports the options menu next can rely on this function to offer the same categories for each ego
as C does.

### `ItemObject.isKnownArtifact` and `ObjectUtils.objIsKnownArtifact` checked against `object_is_known_artifact` and
`obj_is_known_artifact`

C has two known-artifact tests, one reading only the known half (`obj-knowledge.c`) and one that also requires the real
object to be an artifact (`obj-util.c`), and `isArtifact` equals neither. The first check found `objIsKnownArtifact`
declared as an instance method on a class with no instances; you made it static and both then matched C clause for
clause. `KnownArtifactTest` pins the one input where the two disagree (a known half with an artifact on a real object
with none), and the Javadoc on both methods and on the `artifact` and `known` fields says which C function each stands
for. The sites that need these tests, `object_desc` and `compare_items` among them, can now be ported without reaching
for `isArtifact`; the known half still has no artifact setter, so `object_touch` has to add one.

### `ItemObject.applyCurseAttributes` and `ItemObject.objectWeightOne` checked against `apply_curse_attributes` and

`object_weight_one`

`applyCurseAttributes` folds the active curses into a scratch copy for the curse pricing, and `objectWeightOne` gives
the weight of one item once its curses have had their say. Both already matched C, but the `objectWeightOne` Javadoc
still said the curse map keeps insertion order and is sorted first, which stopped being true when the map became a
`TreeMap`. The Javadoc on both methods and on the `toHit` and `toDam` fields now says the order comes from
`CURSE_ORDER`, and four new tests pin the two cases C's numbering could split: curse index 0 as the held-back curse and
as an active weight curse, since C's loop starts at 1 and the port numbers from 0. The curse pricing and every weight
and burden caller can rely on both methods agreeing with C on ordering, saturation and the resistance merge.

### `ItemObject.objectValue`, `objectKindName` and `objDescNameFormat` checked against `object_value`,
`object_kind_name`

and `obj_desc_name_format`

`objectValue` prices a stack by what the player knows, `objectKindName` builds a kind's bare name, and
`objDescNameFormat` expands the `&`, `~`, `|x|y|` and `#` markers in a name template. You had widened all three to
`public`, as in C, which left the `objectValue` Javadoc still calling it private. All three match C apart from the
divergences already recorded on `objDescNameFormat`, so only the Javadoc changed, and the class and `logger` blocks now
say the methods are public and where the template errors are logged. `ItemObjectNameAndValueVisibilityTest` pins the
linkage, which the reflection in the older tests would not notice losing. The store code can call `objectValue`
directly, and the ignore menus and `object_desc` can reach the flavour, `#` and plural paths that only the unit tests
exercise today.

### `Artifact` checked against `struct artifact` in `object.h` and `copy_artifact_data` in `obj-make.c`

`Artifact` is the port of C's artifact definition, and `copy()` makes an independent one. `copy()` set the activation and
its message to null, so a copy lost the activation that C hands to every object built from the artifact, and
`ArtifactAccessorsTest` already failed on it with a `NullPointerException`. You fixed both arms; the activation is now
copied when present and the message passed through, and `ArtifactCopyActivationTest` pins the present, absent and null
cases, the recharge time and the fresh upkeep. Anything that copies an artifact can now rely on the copy activating the
same way as the original, and the class, every field and every method carry Javadoc that names the C field each one
stands for.

### `Player` checked against `struct player` and the functions in `player.c`

`Player` is the port of `struct player` and of the functions in `player.c` that act on it: `player_stat_inc`,
`player_stat_dec`, `adjust_level`, `player_exp_gain`, `player_exp_lose`, `player_flags`, `player_flags_timed` and
`player_is_shapechanged`, with `wipe` standing in for the `memset` in `player_init`. All of them already matched C, so no
code changed, but several Javadoc blocks were wrong: `setPlayerHistory` described the background-text setter,
`getHitDie` and `setHitDie` gave C's hit die the wrong width, `getAU` and the birth-gold pair called a `long` an `int`,
`getShape` said nothing assigns a shape, and `isShapeChanged` credited C with a null guard it does not have. The fix was
a comment-only pass that rewrote those blocks and gave every declaration a stamped block, with `PlayerWipeTest` and
`PlayerKnowsBrandSlayTest` added for `wipe`, `playerKnowsBrand` and `playerKnowsSlay`, which had no tests. The null-shape
guard in `isShapeChanged` is now recorded as a deliberate divergence, and `wipe` is pinned to C's zero state before
`playerInit` builds on it.

### `RuneVariety` checked against `rune_name`, `rune_desc` and `rune_group_text` in `obj-knowledge.c` and `ui-knowledge.c`

### `ObjectRegistry` checked against `lookup_kind`, `lookup_sval`, `lookup_curse`, `lookup_obj_property`, `findact` and `max_runes`

`ObjectRegistry` holds the object-domain lists, the kind index, the `obj-power.h` constants and the power tables, and
answers the lookups that C does by walking arrays. Every lookup matched C, as did all 25 constants, `abilityPower` and
the kind numbering, but the Javadoc had no provenance stamps on any field or method, `loadUnknownKinds` had no block at

nothing on the shipped data). `ObjectRegistryCReferenceTest` pins the constants, the "stats count as mods" rule in
`lookupObjectProperty`, the sentinel kinds, the rune count and the number-or-name edges against figures worked from C.
The registry's contract can now be read from its Javadoc without opening C.

### `Curse` checked against `struct curse` in `object.h` and `modify_weight_for_curse` in `obj-curse.c`

`Curse` is the port of C's curse definition, and `modifyWeightForCurse` is the one function on it: it applies a curse's
weight change to an item, as a percentage or a flat addend, clamped to C's `int16_t` range. It already matched C on every
branch, boundary and rounding step, so no code changed. The Javadoc was wrong about how the index is assigned (C builds
its list by prepending, so its slot 1 is the last curse in `curse.txt`, and the assembler reverses to match), left
`setIndex` undocumented, and did not say the constructor rejects an empty name or that `canAfflict` matches by identity.
A comment-only pass fixed those blocks, and `CurseIndexAndRoundingTest` adds the 3276650 and 3276649 products that sit
on the 50 remainder just under the ceiling, and `setIndex`. Anything comparing a curse index with a C-derived number now
has the offset of one and the reversed order stated in one place.

## Things not to drop

- `PlayerTimedAssembler` does not reject a `lower-bound:` outside 0 to 32767, as C's parser does; a negative or oversized
  bound reaches `PlayerTimedEffect` unchecked.

- `PlayerBirth.playerInit` still says in its Javadoc that nothing calls it, but `doCmdBirthReset` does.
- `PlayerUtils.restingIsSpecial` is a stub that always answers `false`, so `Player.isResting` only counts a positive
  resting counter.
- `PlayerBirth.playerInit` hands the registry's own first race and class to `setRace` and `setClass` rather than copies,
  which those setters document as the normal expectation.
- `ChestTrap.java` Javadoc cites C line numbers (the class block and the `level` field).
- `ChestTrapTest.java` class Javadoc cites C line numbers for `struct chest_trap`, `chest_traps` and the pval doubling.
