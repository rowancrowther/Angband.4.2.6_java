# Precis — 2026-09-10

## Key points from the day

### `Region.cols()` and `Region.rows()` documented and covered

These two getters expose a region's own width and height - the extent every clip check in `put`, `erase`, and `clear`
is measured against, distinct from the grid it draws into - with no C original behind them, since `Region` itself is new
architecture rather than a port; the nearest C struct, `region` in `ui-output.h`, exposes its fields directly with no
accessor functions at all. They're the last uncovered members of `Region`, which the rest of the day's UI panel work
already leans on for its clip contract. Verification found nothing to fix, so the work was Javadoc plus two new cases in
the existing `RegionTest` suite, one pinning the ordinary read against a region deliberately smaller than its grid in
both dimensions, and one checking `cols()` and `rows()` are not transposed. With this, `Region`'s public surface is now
documented and covered end to end.

### `Term.prt`/`cPrt`/`putstr`/`addstr`, `TermWin`'s cursor getters, and
`TermScreenHook`'s text hooks documented and covered

These close out the string-output family alongside `cPutStr`/`putStr`: `prt`/`cPrt` clear a row before writing to it,
`putstr`/`addstr` write with an explicit maximum length and report how much of it actually fit, and the `TermWin`
getters and `TermScreenHook` methods underneath are what both families call into. Verification turned up two real bugs
before `addstr` could be trusted - an unassigned field that null-pointered on every call, and a missing edge-of-screen
clip that let the cursor run past the terminal width - plus a knock-on issue in how `putstr` reported a truncated write
back to its caller, which took two further rounds to bring in line with the C original. The fix ported `Term_addstr`'s
overflow clip and cursor-unusable bookkeeping faithfully and had `putstr` propagate that result exactly rather than
collapsing it to a flat success or failure. The whole `Term_putstr`/`Term_addstr`/`prt`/`c_prt` family now has matching
behaviour and test coverage, so any later caller that checks `putstr`'s return value for a truncation count can trust
what it gets back.

### `CellGrid.getCells()` documented and covered

This accessor hands a grid's cells out as a plain array, for `Window`'s Swing boundary, which needs a raw
`[row][col]` array rather than a `CellGrid` to pass to `JPanelArea.setChars`. Like the rest of `CellGrid`, it has no C
original to check against - it's new architecture, not a port - so verification instead traced the one call site and
confirmed the aliasing `clone()` introduces is safe there today, since it only ever runs against a `Frame`'s
already-copied, never-rewritten grid. The Javadoc records that the safety is the caller's discipline rather than a
guarantee of the method's own, and three new `CellGridTest` cases pin down the ordinary read, the outer array's
independence, and the row-sharing behaviour itself. Any future caller reaching for this method against a still-mutating
grid should reach for `copy()` instead, or the aliasing hazard becomes live.

### `Term.clearFrom` and `TermScreenHook.erase` documented and covered

`clearFrom` blanks a terminal from a given row down to the bottom, and `TermScreenHook.erase` is the boundary beneath it
that each row's blank actually goes through - together the Java port of C's `clear_from` and its
`Term_erase` call. Verification found both already matching the C original clause for clause, including the loop bound
against the terminal's own stored height and the oversized column count that the boundary clips down to each row's real
width, so the work was Javadoc plus a new `TermClearFromTest` covering the ordinary clear, both height boundaries, and a
negative starting row. Every screen that clears its own tail before redrawing - birth, options, and the rest - now has a
verified, tested `clearFrom` underneath it, so a later caller can trust it leaves rows above the given one untouched
rather than checking by hand.
