# Precis — 2026-09-22

## Key points from the day

### UIEntryAssembler completes the shared ui_entry registry pipeline

`UIEntryAssembler` was the piece of the `ui_entry.txt`/`ui_entry_base.txt` shared-registry pipeline left open after
260920's pass — turning each `ui_entry.txt` record into a `UIEntry` and folding it into the same list
`UIEntryBaseAssembler` already seeds, covering both the override path (the thirteen `resist_ui_compact_0<TAG>`
specialisations) and the `parameter:stat`/`parameter:element` fan-out.

With it landed, the whole seven-file group — `UIEntry`, `UIEntryBase`, `EmbryonicCategoryReferencies`,
`UIDataLoader`, `UIEntryBaseAssembler`, `UIEntryAssembler` and their tests — is Javadoc'd and covered by C-derived unit
tests, closing the two stage-1 findings 260920 had left open against `UIEntry.java`/`UIEntryAssembler.java`.

This `/port` pass re-verified all seven files against `ui-entry.c` this turn and confirmed the existing Javadoc and test
suites are current and the full suite is green, rather than writing anything new.

One known divergence remains, flagged in `UIEntryAssembler`'s own Javadoc and carried below — a latent
priority-threading bug unreached by shipped data. The player- and object-property loaders that resolve `bindui`
targets against these entries are the natural next piece.

## Things not to drop

- `UIEntryAssembler.java`'s `buildCategories`/`assemble` (and the `default_priority` it feeds into
  `parseEachEntry`'s create path) don't reproduce `parse_entry_priority`'s split in C (`ui-entry.c:2139-2191`): when a
  record's `priority:` line has no category before it, C sets the record's own `default_priority`; when a category
  *does* precede it, C leaves `default_priority` at 0 and attaches the priority to that category only. Java always does
  both — the same value lands on the record's own priority *and* the preceding category — so any category listed *after*
  the
  `priority:` line would wrongly inherit the earlier category's priority instead of 0. Documented on
  `buildCategories`, `assemble` and `parseEachEntry` in `UIEntryAssembler.java` (260922). Latent, not live: no shipped
  `ui_entry.txt` record has a `category:` line before a `priority:` line — including the 13 `resist_ui_compact_0<TAG>`
  records that exercise the *override* path (`docs/precis/260920.md`,
  "Correction: the create path is not the common case"), none of which carries a `priority:` line at all. Not fixed;
  Rowan's to decide whether it's worth fixing ahead of the data ever needing it.
