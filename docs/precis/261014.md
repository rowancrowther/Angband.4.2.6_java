# Precis — 2026-10-14

## Key points from the day

### `QuestAssembler.assemble` checked against `parse_quest_level`, `parse_quest_race`, `parse_quest_number` and `finish_parse_quest` in `player-quest.c`

`QuestAssembler` turns the raw `quest.txt` records into `Quest` objects, doing the work of C's four `parse_quest_*` handlers and the index numbering in `finish_parse_quest`. It already matched C on the level wrapping to a byte, the leading-`-` rejection, the race lookup, the unsigned-then-int number and the file-order index, but the 261013 rework had left `QuestReaderTest` expecting the old soft errors, so three of its tests failed. The class and `assemble` Javadoc now record that C saturates an oversized level at `ULONG_MAX`, that the exceptions are not caught on the way to `GameConstants`, and that a dropped record skips its later checks. A new `QuestAssemblerTest` pins the level wrapping at 255, 256 and the 2^31 and 2^32 boundaries, the negative-integer aborts, the check order, the three documented divergences and index contiguity against C's behaviour, and `QuestReaderTest` now expects the throw for an unknown race and the kept level 255 for 99999999999. A later change to the integer handling or the check order will show up in those tests.

### `WorldReaderTest` and `WorldRegistryTest` updated for the `"None"` neighbour text

`World` now carries the file's `"None"` text for the town's previous level and the deepest level's next level, where the assembler used to turn it into `null`. Three tests still expected `null` and failed against your change. They now expect `"None"`, and the `WorldReaderTest` class comment says the same. The `WorldAssembler` and `World` Javadoc, which still said the sentinel became `null`, now say it is kept as text and that `WorldDataLoader` is where it is tested.

### `WorldDataLoader` checked against `world_parser`, `projection_parser` and `quests_parser`

`WorldDataLoader` reads `world.txt`, `projection.txt` and `quest.txt` into `WorldRegistry`, standing in for the three C parsers that `init_arrays` runs for them. Its Javadoc still said `loadProjections` logged and returned on a parse error, that `loadQuests` swallowed an unreadable file and that `loadWorld` rethrew an `IOException`, although all three already throw a `RuntimeException` naming the file, as C's `quit()` does, and the class and the logger had no mention of the C parsers at all. The class, the logger and the three methods now record that single rule, the C parsers each one stands in for, the level reference check from `finish_parse_world` (exact and case-sensitive, `"None"` standing where C holds `NULL`) and the element count that `ProjectionAssembler` makes in place of `finish_parse_projection`. A new `WorldDataLoaderTest` pins the 128 levels, the 56 projections with the 25 elements first and the two quests numbered from 0 against C's data, every branch of the level reference check, a missing file for each loader, the 24-element projection file and a reload replacing rather than appending. A change to how a failed load is handled, or to the order the three lists are installed in, will show up in that test.

### `DungeonRegistry` checked against the `cave_profiles`, `room_templates` and `vaults` globals in `generate.c`

`DungeonRegistry` holds the profiles, room templates and vaults that `DungeonLoader` installs, standing in for the three globals that C's `finish_parse_*` functions assign. The behaviour matched, but the Javadoc said all three lists were in file order, when C's `room_templates` and `vaults` are prepended and so run in reverse file order (your `addFirst` change in the assemblers already matches), and the tests still expected file order, so five failed. The class, fields and setters now record the order of each list, the missing getters and the C readers they wait for, and a new `DungeonRegistryTest` pins identity storage, replacement, `null` unloading, independence and the reverse room order; `DungeonLoaderTest`, `RoomProfileReaderTest` and `VaultReaderTest` now expect C's order. Whoever ports `random_room_template` and `random_vault` can rely on the same order for a given random sequence.

### `DefaultGameInput` checked against the absent-hook paths of `game-input.c`

`DefaultGameInput` is the `GameInput` that `GameInputHolder` installs until a front-end replaces it, standing in for every C wrapper in `game-input.c` whose `*_hook` pointer is still `NULL`. It already matched C throughout, but its method Javadoc was a generic "always aborts" that named neither the C function nor the value C returns, and the class and `logger` field were not covered by it. The class, field and every method now record the C wrapper, the `false`, `0` or `-1` it returns and how that becomes an empty `Optional`, and a new `DefaultGameInputTest` walks all fifteen hooks, including the `-2` or `-1` split of `get_effect_from_list`, the two `true` fall-backs and the inherited `confirmDebug`. A real front-end or a test fake can now override one hook knowing exactly what the others fall back to.

### `MagicSpell` checked against `struct class_spell` and `parse_class_spell`

`MagicSpell` is the Java form of C's `class_spell`, one spell with its name, text, effects, realm and four casting figures. It matched C on every member except the realm, which was missing although the class comment claimed it, until your `realm` field and `setRealm` in `ClassSpellBookAssembler` made it match C's copy of `book->realm`. The class, every field and the constructor and both methods now carry Javadoc, recording that `sidx` and `bidx` are deliberately not stored, that the realm is `null` until the book assembler sets it, and that the constructor takes fail before mana where the data file and the struct take mana before fail. A new `MagicSpellTest` pins that argument order against Magic Missile, Light Room and Phase Door in `class.txt`, the realm lifecycle and the assembler's handling of a malformed scalar. Whoever ports `spell_chance` can add the realm getter knowing the field is already filled.

### `MonsterFriends` checked against `struct monster_friends`, `parse_monster_friends` and the friends half of `finish_parse_monster`

`MonsterFriends` is the Java form of one `friends:` line of `monster.txt`: a companion's name, the race it resolves to, its group role, its chance and its dice. It matched C on every member, on the member default for a missing role, and on `lookup_monster`'s equal-then-contained rule through `setRace`, so the file needed no code change. The class, logger, six fields, constructor, `setRace` and `getName` now carry Javadoc, recording that `race` is `null` until `resolveFriends` runs, that a failed `setRace` nulls it even on a resolved entry, that the list order differs from C's reverse chain, and which C readers (`place_new_monster`, `lore_append_friends`) are still to come. A new `MonsterFriendsTest` pins the five stored values against Bullroarer's and Wormtongue's real lines, the 0 and 100 chances, and every `lookup_monster` branch: exact, case-insensitive, first substring, a later exact match beating an earlier substring, one-way containment, the empty name, the unknown name and the unloaded registry. Whoever ports `place_new_monster` can read the entry knowing how its race gets filled.

### `MonTimed` checked against the `effects[]` table in `mon-timed.c` and `list-mon-timed.h`

`MonTimed` holds the rules for each monster timed effect: whether it gets a save, how it stacks, the race flag that grants immunity, the longest it can run and its three messages. All eleven rows of the header matched their constants, so the file needed no code change, but the class comment called the cap a "scaling value" and the fields and constants had no Javadoc of their own. The class, all twelve constants, the seven fields and the constructor now record the C column each one is, the Java-only `MON_TMD_NONE` lead that makes ordinals one higher than C's, that `MON_TMD_MAX` is only a count, and that nothing outside the enum can read the columns yet. A new `MonTimedTest` reads the private columns by reflection and pins them against every header row, the three stacking groups, the two long-running effects, the message gaps and the `monster_effect_level` boundaries for the caps of 50 and 10000. Whoever ports `mon_set_timed`, `mon_inc_timed` and `does_resist` can add getters knowing the table behind them is exact.

### `MonsterReaderTest` updated for the removed friends chance bound

`MonsterAssembler` no longer rejects a `friends:` chance above 100, which is what C's `parse_monster_friends` does, since it reads an unsigned value with no upper bound. The old test, which expected 200 to be reported and the record dropped, failed against your change. It is now `aFriendChanceAboveOneHundredIsKeptAsWritten` and expects 101 and 200 to be stored unchanged with no error. The full suite is green again.

## Things not to drop

- `PlayerQuest.java`, `TrapKind.java` and `ChunkUtils.java` import `DungeonRegistry` without using it.
- `DungeonRegistry.java`: the `logger` field is declared and never used.
- `WorldDataLoader.java`: the three loaders read only the gamedata directory, where C's `parse_file` tries a customised copy in the user directory first.
- `QuestGrammar.g4`: `(quest)+` needs at least one quest, so a `quest.txt` holding only its `record-count:` header is a syntax error, where C's `finish_parse_quest` loads an empty list with `quest_max` of 0; `WorldDataLoaderTest.emptyQuestFile` pins the current throw and should be flipped if the grammar changes.
- `DefaultGameInput.java`: the `logger` field is declared and never used.
- `MagicSpell.java`: no getter reads `realm`, `level`, `mana`, `fail`, `exp`, `effects` or `spellDescription` yet, so `spell_chance` and `spell_cast` have nothing to call.
- `MonsterFriends.java`: no getter reads `race`, `role`, `percentChance`, `numberDice` or `numberSides` yet, so `place_new_monster` and `lore_append_friends` have nothing to call.
- `MonsterAssembler.java`: a friends or friends-base die that `Random.parseStr` returns `null` for is reported as an error but the entry is still built, so `numberDie.getDice()` would throw a `NullPointerException`; the `FRIEND_DICE` token probably stops it reaching there.
- `MonsterAssembler.java`: a friends-base chance above 100 is still rejected, where C's `parse_monster_friends_base` accepts any unsigned value (it only ever behaves as 100).
- `MonTimedStack.java`: `MTS_MAX` is documented as a count sentinel and the class comment leaves out the "take the larger" rule, but `MonTimed` uses it as C's `STACK_MAX` for six effects.
- `EffectAssembler.java`: the `EST_MON_TMD` case uses `valueOf("MON_TMD_" + value)`, so `NONE` and `MAX` resolve as effects, where C's `mon_timed_name_to_idx` stops below `MON_TMD_MAX` and has no `NONE`.
- `MonTimed.java`: no getter reads any of its seven columns yet, so `mon_set_timed`, `mon_inc_timed`, `does_resist` and `monster_effect_level` have nothing to call.
