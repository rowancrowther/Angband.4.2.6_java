# Precis — 2026-09-16

## Key points from the day

### `BitwiseOrCombiner` verified and documented

`BitwiseOrCombiner` - the `BITWISE_OR` row of the character-sheet value combiner table, folding contributions with a
bitwise union of their bits - was checked against C's `simple_combine_init`, `bitwise_or_combine_accum_help`/
`bitwise_or_combine_accum`, `dummy_combine_finish`, and `bitwise_or_vec` (`ui-entry-combiner.c`) this session. Every
clause matched: the sentinel-handling order in the accumulator helper, the plain `|=` union with no saturation clamp
(unlike `ADD`'s), and the `n`-bounded loop in the one-shot form; no discrepancy turned up. The class already carried
thorough prose, but its `state` field had no Javadoc at all and none of its blocks carried the house-style provenance
stamp, so this pass added the field's doc and stamped every existing block instead of leaving them half-documented.
`CombinerTest`'s existing `BitwiseOr` nest already exercises every branch found in verification, so no new test file was
needed; the full project suite is green. This is the second of the nine `combiners` implementations to carry the
provenance stamp, alongside `AddCombiner`, `Combiner`, and `UIEntryCombinerState`.

`init`, the no-op `accum` that leaves later contributions untouched, the pass-through `finish`, and the `n`-bounded
one-shot form that reads only element zero; no discrepancy turned up. The class already carried thorough prose, but its

the field's doc and stamped every existing block instead of leaving them half-documented. `CombinerTest`'s existing
`Positional` nest already exercises both the incremental and one-shot paths, so no new test file was needed; the full
project suite is green. This is the third of the nine `combiners` implementations to carry the provenance stamp,
alongside `AddCombiner`, `BitwiseOrCombiner`, `Combiner`, and `UIEntryCombinerState`.

`UNKNOWN` contribution alone, filling an absent accumulator, replacing an `UNKNOWN` accumulator, and failing to disturb

is the fifth of the nine `combiners` implementations to carry the provenance stamp, alongside `AddCombiner`,

### `SwingUI.JPanelArea.put(char)` and `put(String)` verified and documented, with two bugs found and fixed

`JPanelArea`'s two `put` overloads - the front end's port of C's `Term_putch` and `Term_putstr` - were checked against
`Term_gotoxy`, `Term_addch` and `Term_addstr` (`ui-term.c`) this session. The string form's handling of a negative
starting column disagreed with C - it drew the string's trailing characters instead of declining the whole write, which
is what a failed `Term_gotoxy` does - and the panel's font was being silently overwritten by the constructor after
`init()` had already installed the correctly-measured one; both were fixed in the working tree, and the char form's
Javadoc, which wrongly claimed an out-of-range write throws, was rewritten to describe the actual silent-decline
behaviour instead. The `logger` and `screen` fields, previously undocumented, also got Javadoc naming what actually
reads them. Nine new tests cover both overloads' bounds and clipping behaviour at every edge `Term_gotoxy` checks,
derived from the C source rather than the Java code, and the full project suite is green - closing out the last of
`SwingUI.java`'s missing field Javadoc from `docs/no_low_javadoc.md`.

### `Colour` verified and documented

`Colour`, the runtime palette holder behind every character drawn on screen, was checked against C's
`angband_color_table` and its sizing constants `MAX_COLORS`/`BASIC_COLORS` (`z-color.c`, `z-color.h`) this session. All
29 named RGB triples matched their C rows exactly, as did `maxColours` and `basicColours`; no discrepancy turned up. The
class carried a decent class comment but was missing Javadoc on the `colourTable` field and on `getColour`
entirely, and no block carried the house-style provenance stamp, so this pass filled both gaps and noted, as a design
aside, that C keeps no separate copy of its compiled-in defaults the way `originalColours` does here. A new
`ColourTest` pins every basic colour's RGB value against the C source directly, plus the first/last-row boundaries and
re-`init()` safety, and the full project suite is green - this is the first Javadoc pass over the `colour` package.

### `MonsterRaceCycler` fixed, documented, and tested

`MonsterRaceCycler`, the per-race colour-cycle lookup that animated monsters check before falling back to `FlickerTable`
and then their static colour, was checked against C's `visuals_color_cycles_by_race` table and its
`visuals_cycler_set_cycle_for_race`/`visuals_cycler_get_attr_for_race` accessors this session. Three rounds of
verification each turned up a real mismatch - a value type that stored a whole cycle table per race instead of one
resolved cycle, an uncallable frame-lookup method, and a fix for that which reset the shared cache on every call - each
reported and fixed in turn until the fourth pass matched C's behaviour clause for clause, including its null guards and
its "unresolved cycle stores nothing" rule. The class, its field, and every method now carry full Javadoc naming the C
cross-reference and the deliberate divergences (name-keyed `HashMap` instead of C's manually-grown `ridx` array, `null`
instead of the `BASIC_COLORS` sentinel). A new `MonsterRaceCyclerTest` covers the ordinary wraparound path, the
single-step boundary, both null guards, re-registration, and the raw accessor, all derived from the C source; the full
project suite is green - this is the first test coverage for the `colour` package's cycling primitives.
