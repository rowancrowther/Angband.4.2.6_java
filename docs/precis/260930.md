# Precis — 2026-09-30

## Key points from the day

### Javadoc, tests and stamps for the whole of `Chunk.java`

The whole of `Chunk.java` went through the port pass against `cave-square.c`, `cave-view.c`, `cave.c`, `cave-map.c`,
`mon-make.c`, `obj-pile.c` and `game-world.c`, leaving out the block waiting on Chapter 6. It found four divergences:
`Feature.isRock` answered C's granite question where four `Square` predicates needed the `TF_ROCK` flag, a new chunk
started with every grid lit and occupied, `Square.trapTimeout` stopped at the first trap, and `objectDelete` left the
object in its pile. Until they were fixed, permanent walls, rubble and secret doors failed `isPerm`, `isRubble` and
`isSecretDoor`, which fed `squareChangeable`, `squareIsDiggable` and `squareIsStrongWall`. Rowan added
`Feature.fullRock`, zeroed the constructor's squares, fixed the timeout scan and made `objectDelete` excise the object
from its owning pile, and the Javadoc for `caveMonster`, `objectDelete`, `resetNoise` and `getNoise` now matches the
code. `SquareTerrainClassTest` runs fourteen terrains from `terrain.txt` through six rock predicates against C's
definitions, the pile and construction cases are pinned, and two `ChunkSquareForgetTest` cases that predated the
per-chunk current level were updated. `resetNoise` is now a stub with its C-derived test disabled, so its port only
needs that test enabled.

### `ClockwiseDirectionLoop`, the ring behind `clockwise_ddd[]` and `clockwise_grid[]`

`ClockwiseDirectionLoop` is the Java form of the two clockwise direction arrays in `cave.c`, which the `MOVE_ATTACK` and
`SWEEP` effect handlers walk to turn a heading or scan the eight neighbours. It had no callers yet, but it could never
have worked: the cursor was never set, and the singleton could not be reached from outside the class. Rowan built the
ring once as a static field and gave each `new ClockwiseDirectionLoop()` its own cursor starting at north, so the ring
matches the C arrays entry for entry, centre included, and any number of loops run without affecting each other. Future
callers create a loop wherever C would hold an index, and must skip the centre entry that C's modulus-eight walk never
reaches.

### `Feature`, the Java form of `struct feature` and its `feat_is_*` predicates

`Feature` holds one `terrain.txt` record and answers the `feat_is_*` questions from `cave-square.c`, with the mimic and
the permanent-wall tests that `map_info` in `cave-map.c` makes. Checking it found that `getMimic` returned nothing for
every feature without a mimic, that the assembler defaulted the mimic to `FEAT_NONE` so every feature looked like a
mimic, that `shopNum` was never filled in, and that both hallucination rolls in `GridData` tested the wrong thing, so
stairs and shops were excluded, or nothing was. Rowan made `getMimic` return the feature itself when there is no mimic,
left the assembler's mimic `null`, numbered the shops from 1 in the assembler as `finish_parse_feat` does, and split the
permanent tests into `isPermanent` (the `FEAT_PERM` code) and `isFullPermanent` (`PERMANENT` with `ROCK`). `FeatureTest`
pins each predicate, the stair, door and rock distinctions, the two permanent tests and the mimic resolution against C,
and the twelve test call sites now pass the new `shopNum` argument. `featureIndex` is deprecated in favour of
`code.ordinal()`, and `Feature.equals` compares `Flag` objects by identity because `Flag` has no `equals`, so its
value-equality test is disabled until that is fixed.

### `KeypadDirectionLoop`, the ring behind `ddgrid_ddd[]`

`KeypadDirectionLoop` is the Java form of the `ddd` direction table in `cave.c`, which many of the cave routines walk to
visit a grid's eight neighbours. It had no callers yet, but it could never have worked: the ring was built into local
variables and the shared static cursor was never set, so the first read threw. Rowan made the ring a static field built
once, started the cursor at south, and gave each `new KeypadDirectionLoop()` its own cursor, as with the clockwise
sibling. Future callers create a loop wherever C holds an index into `ddgrid_ddd[]`, and must skip the ninth (centre)
entry when they want only the eight compass directions.

### `Loc`, the Java form of `struct loc` and its coordinate helpers

`Loc` ports `struct loc` with `loc_eq`, `loc_is_zero`, `loc_sum`, `loc_diff`, `loc_offset`, `rand_loc`, `next_grid`,
`motion_dir` and `distance`, all of which the rest of the port calls constantly. Every method already matched its C
original, so no behaviour changed. The class, its fields, the builder and every method now carry Javadoc that names the
C function, and the `next_grid` note now cites `cave.c` where it is defined instead of the header. `LocTest` already
pins each method against hand-worked C values, including `distance`'s shift rounding and `motionDir` on both axes, and
it passes. Future ports can treat `Loc` as settled and build on it.

### `PointSet`, the Java form of `struct point_set` and its four utility functions

`PointSet` ports `point_set_new`, `add_to_point_set`, `point_set_size` and `point_set_contains` from `z-type.c`, the
grid collection that targeting builds. Every method already matched its C original, so no behaviour changed, but the

### `Square`, the Java form of `struct square` and the `square_*` predicates

`Square` ports the per-grid predicates of `cave-square.c` together with the trap scans and door-lock test from `trap.c`,
which the rest of the cave code calls constantly. Checking it found that `trapSpecific` matched trap kinds by
description text and `trapTimeout` compared its argument with the trap's list position, where C compares the kind index
in both. Kinds that share a description, such as three of the dart traps, could not be told apart, and a timeout asked
for by kind index would have read the wrong trap, although every current caller was safe by luck. Rowan changed both to
compare
`TrapKind.getTrapKindIndex()`, and the class, its fields and every method now carry Javadoc naming the C function and
the flags it tests. `SquareTrapAndDoorTest` pins the trap scans, the lock and door-state predicates and the trap vetoes
on
`isEmpty` and `isArrivable` against `cave-square.c` and `trap.c`, using two kinds with one description and different
indexes, and the suite passes. Future trap and door ports can rely on kind-index matching, and note that `setFeature` is
a bare assignment that skips the bookkeeping of C's `square_set_feat`.

### `Trap`, the Java form of `struct trap`

`Trap` is a live trap on one grid, holding its kind, location, power, timeout and per-trap flags. It carried a
`trapIndex` field documented as a list position although the C `t_idx` it ported is the kind index, which
`TrapKind.getTrapKindIndex()` already supplies. Rowan removed the field and its unused getter, and the class, its fields
and every accessor now carry Javadoc that maps each C field across, including the two with no Java field (`t_idx`
and the `next` link). `TrapTest` pins the accessors, the per-trap flag lookup and the timeout countdown against
`trap.h` and `game-world.c`, and the suite passes. Callers must guard `decrementTimeout` with a positive-timeout test as
C does, since Java's `int` goes negative where C's `uint8_t` would wrap.

### `TrapKind`, the Java form of `struct trap_kind` and `lookup_trap`

`TrapKind` holds one `trap.txt` record and ports `lookup_trap` from `trap.c`, which finds a kind from its short
description. Checking it found that `lookupTrap` returned `null` for an empty string where C's substring match returns
the first named kind, and the same guard was duplicated in `TerrainRegistry`. Rowan removed the guard from both copies,
and the class, its fields and its methods now carry Javadoc naming the C function and the exact-then-close matching
order. `TrapKindTest` pins exact, close, case-insensitive, unnamed-slot, empty-string and empty-table lookups against a
slice of `trap.txt`, and the suite passes. Callers can treat the two `lookupTrap` copies as equivalent, and a later
tidy-up can drop one.

### `BuilderType`, the Java form of `cave_builders[]`

`BuilderType` is the enum standing in for the `cave_builders[]` table in `generate.c`, which `list-dun-profiles.h`
expands into name and function-pointer pairs so a profile record can pick its level builder by name. It matched the C
table entry for entry, but its class Javadoc claimed the declaration order was the order profiles are tried in, when C
only searches the table by name. That claim is corrected, the constructor, `getName` and `build` are documented against
`parse_profile_name`, and `BuilderTypeTest` pins the nine names, their order, the space in `hard centre` and the
exact-match lookup. Future work on the profile parser can look a name up on the enum and treat a miss as
`PARSE_ERROR_NO_BUILDER_FOUND`.

### `DirectionEnum`, the Java form of `ddx`, `ddy`, `ddgrid` and `ddd`

`DirectionEnum` folds the direction tables of `cave.c` and the `DIR_*` constants of `cave.h` into one enum. Every offset
and keypad key matched C, and the only differences are that `DIR_TARGET` and `DIR_NONE` are separate constants where C
gives both the value 5, and that the neighbour ring omits C's centre entry. The class, constants, fields and methods now
carry Javadoc recording both differences, and `DirectionEnumTest` gained a check of `surroundingDirections` against C's
`ddd` order and `ddgrid_ddd` offsets. Callers that go through `fromKey` should expect key 5 to come back as
`DIR_TARGET`, never `DIR_NONE`.

### `RoomFlags`, the Java form of `list-room-flags.h` and the `room_flags[]` name table

### `SquareEnum`, the Java form of `list-square-flags.h` and the `SQUARE_*` enum in `cave.h`

`SquareEnum` is the enum of per-grid flags that `cave.h` builds by expanding the `SQUARE()` lines of

### `TerrainFlags`, the Java form of `list-terrain.h` and the `FEAT_*` enum in `cave.h`

`TerrainFlags` is the enum of terrain types that `cave.h` builds from the `FEAT()` lines of `list-terrain.h`, with

### `RoomType`, the Java form of `room_builders[]` and its three accessors

`RoomType` is the enum that replaces the `room_builders[]` table in `generate.c`, carrying each room's name, size caps

it is in C, and the assemblers can rely on the caps without a second check.

## Things not to drop

- `Feature.equals` and `hashCode` treat `flags` and `resistFlag` by identity, because `Flag` defines no `equals` or
  `hashCode`; `FeatureTest` has a disabled spec that expects value equality.
- `TerrainFeatureAssembler` does not set the C `store_max` that `finish_parse_feat` derives from the shop count.

- `Chunk.resetNoise` is a stub waiting on Chapter 4, and its disabled spec in `ChunkGeometryTest` expects C's behaviour
  of zeroing the interior and leaving the border ring alone.
