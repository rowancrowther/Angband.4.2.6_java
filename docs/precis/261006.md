# Precis — 2026-10-06

## Key points from the day

### `CurseSource` checked against the curse pass of `calc_bonuses()` in `player-calcs.c`

`CurseSource` is the port-only wrapper that lets `calcBonuses` walk a worn item's curses with the same loop body as the
item, standing in for C's `obj = curses[index].obj`. Its code already matched C on every accessor, so no code changed,
but its Javadoc claimed a curse's known object is blank and that curses contribute only modifiers under `knownOnly`,
which is wrong because `write_curse_kinds()` and `player_know_object()` fill it from the player's rune knowledge. The
class, field, constructor and every method now describe the real behaviour with no C line numbers, and
`BonusSourceTest` gained cases for learned and unlearned combat runes, known resistances and the learned-flags subset.
Later work on `calcBonuses` can rely on a curse's `known*` answers behaving like an item's.

### `GameWorld` checked against every function in `game-world.c`

`GameWorld` is the home of the game clock and the per-turn passes: `run_game_loop`, `process_player`, `process_world`,
`process_player_cleanup`, `on_new_level`, `on_leave_level`, `decrease_timeouts`, `make_noise`, `update_scent`,
`recharge_objects`, `recharged_notice`, `play_ambient_sound`, `is_daytime` and `turn_energy`. Every one already matched
C once calls into stubs are set aside, so no code changed, but two blocks still called fully written methods stubs, the
day-count getter had no comment, and several blocks carried C line numbers. The class, fields, constructor and every
method now describe what they do, name the stub boundaries they sit on and cite C by file and function only, and
`GameWorldTest` pins the clock arithmetic, the world pass, the cleanup flags, the noise and scent grids and the
scheduling of the loop against figures derived from C. Later chapters can fill in the monster turn, level generation and
player upkeep behind these methods knowing the scheduling around them is already tested.

### `GameState` checked against the globals it stands in for and `target_okay()` in `target.c`

`GameState` holds the port's copies of the C globals `turn`, `player`, `cave`, `seed_flavor` and `character_generated`,
plus a day-count forwarder to `GameWorld` and a command-queue slot with no C counterpart. `resetTurnForNewPlayer` set
the clock to 0 where `player_init()` in `player-birth.c` sets it to 1, and nothing called it because `PlayerBirth`
already writes 1 through `setTurn`, so the method was removed and every remaining accessor matched C. The class, every
field and every method now carry Javadoc that names the C global and the function that reads or writes it with no C line
numbers, a stale claim that `initGameState` still runs at start-up was corrected, and the new `GameStateTest` covers the
clock tick and its 32-bit wrap, the restore from a save and the player, level and queue slots. Birth and load can now be
ported against a tested clock, though `seedRandart` still has no accessor and `targetOkay` stays a stub until targeting
arrives.

### `UIEntryValueRegistry` checked against `compute_ui_entry_values_for_object()`,
`compute_ui_entry_values_for_player()` and `is_ui_entry_for_known_rune()` in `ui-entry.c`

`UIEntryValueRegistry` is the Java home of the bind functions, the two value computations, the known-rune test and the
three helpers under them, `modifier_to_skill()`, `get_timed_modifier_effect()` and `get_timed_element_effect()`. Every
one matched C on the branches and boundaries I walked through, so no code changed, but the Javadoc cited C line numbers
throughout, described the fixed-value override as covering only modifiers and flags, and promised a fatal error for a
missing combiner that only fires for a `null` one. The class, both fields, every method and both records now say what
the port does and where it departs from C (the caller-supplied cache, the unchecked `null` registry, the `NONE`
combiner), and the new `UIEntryValueRegistryBoundariesTest` pins every property family, the auxiliary and timed-aux
bookkeeping, curse order, the timed speed table and the racial skill division against figures derived from C. The UI
status and character-sheet work can lean on both computations knowing their edge cases are tested.

## Things not to drop

- `GameWorld.processWorld` reads `Food.PY_FOOD_STARVING` and `Food.PY_FOOD_HUNGRY`, which are hardcoded to 100 and 1500,
  where C reads the thresholds loaded from `player_timed.txt` and held in `PlayerRegistry`; the two agree for the
  shipped data but would drift if `player_timed.txt` or `player:food-value` changed.
