# Precis — 2026-08-19

## Key points from the day

### The curse map's ordering is load-bearing now, and the signature does not say so

`weightOne` folds an object's weight through each of its curses in turn, and the fold is not commutative — an additive
curse and a multiplicative one give different answers depending on which runs first. Retyping the backing map to a
`LinkedHashMap` fixed that, but `getCurses` still returns a plain `Map`, so the guarantee the fold depends on is
invisible to anyone reading the declaration, and a later swap back to `HashMap` would break it silently with nothing to
fail. The choice is between saying so in the Javadoc and putting it in the type as a `SequencedMap`, which the project's
Java level supports. Whichever way it goes, this is the shape to watch for elsewhere: a correctness fix made in a
field's type, where the accessor's type still promises less.

### `adjustSkillScale` was two faults sharing four lines

C adjusts a skill by a fraction of its own magnitude, rounding the penalty up so that a decrease mirrors what the
equivalent multiplication would give. The port dropped the absolute value, so a negative skill scaled by nothing at all,
and its parentheses folded the round-up term into the multiplier instead of adding it after — a request to shave a tenth
off a device skill of 30 took the whole 30 instead of 3. Both are corrected and the method now matches value for value
across the positive, negative and zero cases. The transcription lesson is the parentheses one: the expression read
plausibly and compiled, and only running numbers through both versions showed it.

### The curse weight multiplier tests the multiplier, not its sign

A curse can scale an object's weight rather than add to it, and C floors the incoming weight at one first — but only
when the multiplier is greater than one, so that a multiplier can do something useful to an otherwise weightless item
without a halving inventing weight out of nothing. The port tested the curse's weight for being non-negative instead,
which the assertion just above had already guaranteed, leaving the other branch dead and a weightless item coming out at
one tenth of a pound. The threshold is now the multiplier itself. Worth carrying forward that a condition made
unreachable by a guard above it is a smell in its own right, whatever the branch would have done.

### `weightOne` had three faults and none of them were the arithmetic

The fold itself was right; what surrounded it was not. The curse map is created on demand, so the loop would have thrown
on the great majority of objects, which carry no curses at all; curses with zero power were folded in where C treats a
zero-power slot as an absent curse; and the iteration order was a `HashMap`'s. Routing the loop through the existing
accessor fixed the first, a power test the second, and the retype the third. The pattern across all three is that the
port of an array-plus- sentinel structure into a map moves the questions from "what is in the slot" to "is the slot
there at all", and each of C's guards has to be re-asked in those terms rather than dropped.

### `weightLimit` needed nothing

The strength-to-carrying-capacity lookup and its hundredfold scale match C exactly, and the thirty-eight entry table
behind it is element-for-element identical to the original. The only thing worth a second look is the fallback value on
the stat-index lookup, which reads like the stat value 3 where the index for that stat is 0 — reachable only if the
index map can be missing a strength entry, which it should not be. Nothing to change unless that turns out to be
possible.

### `magicRealm` moved its dedup from identity to name, which is where C has it

The method collects the distinct realms a class has spellbooks from, and C compares realm names with
`streq` because its list holds copies. The first port used a `HashSet` of realm objects, which worked only because every
book resolves its realm through the registry and so shares one instance — a correctness argument that lived in another
package entirely. Keying a map on the realm name makes the test the same one C makes and removes that dependency. The
empty case also changed on purpose: C returns `NULL` where the port returns an empty set, which is the better Java and
costs the callers a null check they no longer need.

### `averageSpellStat` and `calcBlows` were both right first time

The spell-stat average is a sum of stat indexes over the class's realms with a round-up divide, and the blows
calculation is a strength-versus-weight index into the blows table, capped, crossed with a dexterity index. Both matched
C statement for statement, including the round-up parentheses that the skill-scale port had got wrong earlier in the
day. The only thing either needs is a note that
`averageSpellStat` divides by the realm count and so has a precondition its two callers already enforce. The C function
also frees the realm list as it walks it, a hazard that simply does not exist in the port.

### `calcMana` had the encumbrance loop inverted and wrote its answer too early

C weighs the armour by skipping the slots that are not armour — weapon, bow, ring, amulet, light — and the port had all
five tests negated, so every slot was skipped and no caster was ever encumbered. Underneath that were two structural
faults: the running total was written straight into the player's maximum mana rather than into a local, so a
hypothetical-state call clobbered the real character before it reached its early return, and the whole save-clamp-redraw
tail ran unconditionally instead of only when the maximum had actually changed. All three are fixed. The pattern to
carry forward is that C's habit of computing into a local and committing at the end is usually load-bearing, not style.

### `calcBonuses` took two passes and is down to a handful of open faults

The first read of the ported half turned up sixteen findings, most of them transcription rather than misunderstanding:
modifiers written into the wrong state field, guards that had drifted outside the block they belonged to, a
vulnerability map that was never seeded and so threw on its first read, a sign flip on holy-orb resistance for evil
characters, and the class skill multiplier dropped from the per-level bonus. Eleven were fixed the same evening and
re-verified. What remains is the item speed modifier still landing in infravision, the two armour lines having traded
places, the missing berserk-strength block, and the curse walk — which is not a fault but the largest unwritten piece,
since C re-runs its whole equipment body once per curse and treats each curse as an invisible second item in the slot.

## Things not to drop

- `PlayerState` has an `ac` field but no accessor to accumulate into it, so an item's base armour has nowhere to go once
  the two armour lines in `calcBonuses` are put back the right way round.
- The item speed modifier in `calcBonuses` is written into see_infra, and the two armour lines apply the enchantment
  where the base value belongs and vice versa.
- The `TMD_SHERO` block is missing from `calcBonuses` — melee to-hit, an armour penalty and a device scale — though both
  the effect and the skill exist.
- The curse walk in the equipment loop is still a TODO, and with it every curse's flags, modifiers, resistances and
  combat bonuses.
- `calcBonuses` excludes two slot types from the to-hit and to-damage bonuses that C does not; worth a comment if it is
  deliberate.
- `getCurses` returns `Map` while the field is a `LinkedHashMap`; the ordering `weightOne` relies on needs to be stated
  in the Javadoc or in the type before something quietly undoes it.
- The stat-index fallback in `PlayerState.weightLimit` answers 3 where an index of 0 is the value matching a strength of
  3.
- `averageSpellStat` throws on a class with no realms; both call sites guard it, so the precondition wants a Javadoc
  line rather than a check.
