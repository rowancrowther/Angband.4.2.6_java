# PlayerStatusView — the write side

`channel.messages.data.PlayerStatusView` (`player_status_view_setters.md`'s subject) is the read-side snapshot
`player_view_cache_proposal.md` designed and `frontend_core_data_crossings.md`
justified: one immutable record, pushed by the core on state change, read locally by the front end. This document is
that design's write-side counterpart — for each of the record's 33 fields, where the underlying value actually lives in
the port today, whether a setter already exists to hook a view-refresh into, and where one still needs writing.

Rowan's working rule under discussion: a setter that changes a value should also be the thing that rebuilds and
republishes the `PlayerStatusView` snapshot. That only works where a real setter chokepoint exists. Where a field is
currently mutated by direct/internal field access instead, or has no port equivalent yet at all, the setter has to be
written (or the subsystem finished) before that rule can apply.

**Source note:** every row below is sourced from a file read this pass — `Player.java`,
`PlayerState.java`, `PlayerRace.java`, `PlayerClass.java`, `PlayerBody.java`, `PlayerUpkeep.java`,
`PlayerTimed.java`, `TimedEffect.java`, `Monster.java`, `MonTimed.java`, `MonsterFlag.java`,
`Chunk.java`, `GridLightLevel.java`, `Flag.java`. Where nothing turned up in a repo-wide grep, the row says so rather
than guessing a location.

## Setters to write

- **`Monster`**: `getHp`/`setHp`, `getMaxHp`/`setMaxHp` (currently constructor-only)
- **`Monster`**: a `monsterFlagOn(MonsterFlag)` counterpart to the existing `monsterFlagOff`
- **`Player`**: no new setter needed after all — `playerExpGain`/`playerExpLose` are already the external chokepoint for
  `exp`/`maxExp` (see the audit below); hook the view-refresh there, not into a new `setExp`
- **`PlayerUpkeep`**: `setRestingCounter` (getter exists, no setter); the "repeating" half of
  `restingRepeatingState` still needs its source traced
- **Title**: a level→title lookup function (C's `player_title()` equivalent) needs writing before a setter question even
  applies — there is no source data at all yet
- **Study/detection status**: no port equivalent exists for either `studyStatus`/`studyConditions`
  or `detectionStatus` — bigger gaps than a missing setter
- **Level feeling**: `Chunk.feeling` needs a getter/setter, but the string itself is blocked on the still-stubbed
  `displayFeeling`/level-feeling subsystem

## Direct/bypassed access audit

All fields on `Player`, `Monster`, `PlayerState`, `PlayerUpkeep`, `Chunk` and `Pile` that back a
`PlayerStatusView` value are `private` (confirmed by grep across each class), so true external direct-field-access is a
compile error and cannot happen from outside the declaring class. The two remaining ways a value could bypass its
setter: (A) mutated only by scattered internal methods with no external chokepoint at all, or (B) a getter hands back a
live mutable object that a caller mutates directly instead of going through a class-level setter. Every row below is
sourced from a grep/read done this pass across the whole `src/main` tree (`src/test` noted separately where it differs).

| Getter/Object                                     | Returns live mutable ref or copy?                                                                             | Bypassing callers found (file:line)                                                                                                                                                                                                                                                                                 | Verdict                                                                                                                                                                                                                                  |
|---------------------------------------------------|---------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Player.exp`/`maxExp`                             | n/a — no getter for `maxExp` at all                                                                           | None from outside `Player.java`. Both fields are written only by `Player.adjustLevel` (`Player.java:1143-1152`), and `adjustLevel` itself is only called from `Player.playerExpGain(long)` and `Player.playerExpLose(long, boolean)` — both **public** methods.                                                     | Safe, but not a gap the way the prior section framed it — `playerExpGain`/`playerExpLose` already *are* the external chokepoint, just not named `setExp`. Hooking a view-refresh into `adjustLevel` covers both.                         |

**No genuine encapsulation bypasses were found in `src/main`.** Every value either has a real external chokepoint (even
if not literally named `setX`), or is safe because the mutable internals are never exposed, or is a confirmed gap
already listed above rather than a bypass. The one correction to the prior section: `Player.exp`/`maxExp` do have an
external write path —
`playerExpGain`/`playerExpLose` — it just isn't shaped like a conventional setter.
