# Precis — 2026-10-28

## Key points from the day

### ObjectBaseAssembler.assemble

`ObjectBaseAssembler.assemble` turns each parsed `object_base.txt` record into an `ObjectBase`, standing in for the `parse_object_base_*` handlers in `obj-init.c` and the zeroed `kb_info` slot that `finish_parse_object_base` leaves for tval 0. The last assembler in the object-base chain still carried the soft-error contract in its Javadoc and in 13 tests, although the code had already moved to C's behaviour: a bad tval, flag or number ends the load, an unknown colour is white, `IGNORE_` sets the ignore bit, an absent number is 0 and the sentinel has no name. A clause-by-clause check found no mismatch, so the port is unchanged. The class, logger and `assemble` Javadoc now record the fatal paths, the prefix rule of `grab_element_flag`, the `NONE` and `MAX` flags, the sentinel and the clamped-number deviation, and a new `ObjectBaseAssemblerTest` of 109 cases pins each branch while 13 reader and domain tests that pinned the old behaviour were rewritten. Anything that reads a base's name must now expect `null` for a record with no plural part, as C's `NULL` name does.

### ObjectPropertyAssembler.assemble

`ObjectPropertyAssembler.assemble` turns each parsed `object_property.txt` record into an `ObjectProperty`, standing in for the `parse_object_property_*` handlers in `obj-init.c`. Like the object-base assembler it still described soft errors in its Javadoc and in 16 tests, although the code already stops the load on a bad type, subtype, id-type, code, tval or number, and the old tests wrongly said C has no flag `MAX`. The check found one real difference: the grammar's `type-mult:` map was unordered, so two spellings of one tval could resolve in any order. The grammar now keeps the lines in file order, which leaves a single narrow case (a repeated spelling after an alias) recorded in `docs/Accepted_Deviations.md` and pinned by a test. The class, logger and `assemble` Javadoc now record the fatal paths, the table each code reads, the valid flag `NONE` and `MAX`, the absent-code defaults and the two deviations, and a new `ObjectPropertyAssemblerTest` of 109 cases replaces the stale `ObjectPropertyAssemblerTypeTest` while 10 reader tests were rewritten.

### PainAssembler.assemble

`PainAssembler.assemble` turns each parsed `pain.txt` record into a `MonsterPain`, standing in for `parse_pain_type` and `parse_pain_message` in `mon-init.c`. Its Javadoc and five reader tests still described soft errors and a skipped record, although the code had already moved to C's behaviour: a serial starting with `-` or an eighth message ends the load, and fewer than seven messages are padded with `null` as C leaves the slots `NULL`. A clause-by-clause check found no mismatch, but the committed `PainGrammar.java` was stale (`message+` against the grammar's `message*`) and was regenerated. The class, logger and `assemble` Javadoc now record the fatal paths, the base-0 serial reading (`010` is 8, `08` is 0) and the clamped-number deviation, and a new `PainAssemblerTest` of 22 cases pins each branch while the reader, loader and `MonsterPainTest` tests that pinned the old behaviour were rewritten. Decided 261028 (option A): a short `type:` block loads as in C, so the first code to read a message, the port of `get_message_text`, must expect `null` for an unfilled slot.

### MonsterPain

`MonsterPain` is the Java copy of `struct monster_pain` in `monster.h`: a serial number and seven pain messages that `get_message_text` in `mon-msg.c` will read by health band. The class had already moved to C's behaviour, accepting a `type:` block with fewer than seven messages and padding the missing slots with `null`, but its class, field, constructor and `getMessage` Javadoc still said short lists and `null` were refused and that the list was unmodifiable, and one test still expected an `IndexOutOfBoundsException` for an unpadded short list. A clause-by-clause check found no mismatch, so the port is unchanged. The Javadoc now records the padding, the one fatal case (more than seven), the `null` slots and the private `ArrayList` copy, and `MonsterPainTest` pins an unpadded short list, an empty list, exactly seven and `toString` with unfilled slots. The port of `get_message_text` can rely on `getMessage` giving `null` for an unfilled slot whether or not the caller padded the list.

### PitAssembler.assemble

A clause-by-clause check found no mismatch, so the port is unchanged. ### ParseUtils (whitespace skipping, trimmers, strtol check)

`ParseUtils` turns the integer text the grammars hand over into an `int` as `strtol` does in `parser.c` and `datafile.c`, and holds the whitespace tests and trimmers that sit beside it. Your edits make the base 0 and fixed base 10 readings skip leading C whitespace and refuse text of nothing but whitespace, and add `onlyCSpace` and the `cTrim` family. A run of 122 inputs through a compiled C `strtol` in base 0 and base 10 differed only on a lone `-` or `+`, which C refuses and this read as 0, apart from the clamp past 32 bits that `Accepted_Deviations.md` already records. Your edit makes all three forms of `parseIntString` refuse a lone sign, so the class Javadoc no longer lists it as a difference, and the accepted-deviation heading and the trimmer notes are corrected. The new `ParseUtilsStrtolTest` pins all 122 C results in four groups (agree, clamped, refused, lone sign), so any later change to the digit reader is checked against C and not against the port.

### ClassEquipAssembler.assemble

`ClassEquipAssembler.assemble` turns each parsed `equip:` line of `class.txt` into a `StartItem`, standing in for `parse_class_equip` in `init.c` and the subtype reading of `lookup_sval` in `obj-util.c`. Its Javadoc still described soft errors and dropped entries, although the code already ends the load on a bad tval, subtype, quantity or exclusion option and returns the items in reverse file order as C's chain does. A clause-by-clause check found two differences in the numeric subtype, a number of `INT_MAX` or more that C refuses and `-0` that C reads as 0, and both were accepted as deviations on 261028. The class, logger, `assemble` and `parseEopts` Javadoc now record the fatal paths, the subtype forms, the `strtok` tokenising and the two deviations, and 24 new cases in `ClassEquipAssemblerTest` pin each branch, with the two deviations marked so a change to them fails loudly. Code that reads `StartItem.getsValue()` must expect either a name or a bare number that need not match any kind, as C's `lookup_sval` allows.

### ClassMagicAssembler.assemble

`ClassMagicAssembler.assemble` turns a class's parsed `magic:` record into a `ClassMagic`, standing in for `parse_class_magic` in `init.c` and for the `class_max_books` limit that `parse_class_book` applies to each `book:` line. Its Javadoc still said a malformed scalar reports a soft error and skips the record, although the code already ends the load on a leading `-` or a missing number in any of the three `uint` fields, in the order C reads them, and on more books than the line declares. A clause-by-clause check found no mismatch, so the port is unchanged, and two reader tests that pinned the old "contained an error" report were rewritten to expect the stop. The class, logger and `assemble` Javadoc now record the fatal paths, the base-0 reading, the count rule (fewer books accepted, a declared 0 refuses every book, a skipped book still counts) and the clamped-number deviation, and a new `ClassMagicAssemblerTest` of 38 cases pins each branch. The port of `parse_class_book` can rely on this class owning the surplus-book check, so `ClassSpellBookAssembler` need not repeat it.

### ClassSpellAssembler.assemble

`ClassSpellAssembler.assemble` turns each parsed `spell:` block of `class.txt` into a `MagicSpell`, standing in for `parse_class_spell` and `parse_class_desc` in `init.c`, with the spell's effects handed on to `EffectAssembler`. Its Javadoc still said a malformed integer is reported and skipped, although the code already ends the load, and `MagicSpellTest` pinned a dropped spell. A clause-by-clause check found two differences, a negative or `-0` level, mana, fail or exp that the code refuses and C's `int` fields store, and the figures being checked level, fail, mana, exp where C reads level, mana, fail, exp; both were accepted as deviations on 261028. The class, logger and `assemble` Javadoc now record the fatal paths, the base-0 reading, the absent upper bound, the empty description and the two deviations, and a new `ClassSpellAssemblerTest` of 47 cases pins each branch with the deviations marked, while the stale `MagicSpellTest` case now expects the stop. Code that reads a spell's description must expect an empty string, not `null`, for a spell with no `desc:` line.

### ClassSpellBookAssembler.assemble

`ClassSpellBookAssembler.assemble` turns each parsed `book:` block of `class.txt` into a `MagicBook` and registers the object kind that backs it, standing in for `parse_class_book`, `parse_class_book_graphics`, `parse_class_book_properties` and `write_book_kind` in `init.c`. The code had already moved to C's behaviour, stopping the load on a bad tval, realm, glyph, number or base and capping the spells at the declared count, but its Javadoc still described soft errors and skipped books. A clause-by-clause check found two differences, a book with no `book-graphics:` line getting glyph code point 0 where `write_book_kind` leaves `*`, and the kind's level being the smaller depth where C takes the first number of the range as written, and your edits fixed both. The class, logger and `assemble` Javadoc now record the order of the fatal checks, the declared-count cap, the defaults and the remaining differences, and a new `ClassSpellBookAssemblerTest` of 57 cases pins each branch with two documented differences marked, while 13 tests in `PlayerClassReaderTest` and `ClassMagicAssemblerTest` that expected a skipped book were rewritten to expect the stop. A class can no longer load with fewer books than its file gives it, and any test that needs a good book must seed the realm, object-base and object-kind registries, which the new `BookRegistryFixture` does.
