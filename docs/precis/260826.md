# Precis — 2026-08-26

## Key points from the day

### The inventory rebuild was reviewed end to end, and cannot run yet

`calcInventory` and everything below it was compared against the original, function by function, covering the pack and
quiver fill, the split and copy path, the ordering comparator and the two pricing functions it reaches. Three of the
fourteen findings are hard stops rather than wrong answers: the pack list is never sized so the first write throws, two
gear walks index past the end of a list where the original walked a null-terminated chain, and the comparator's null
test means no candidate is ever selected. All three are corrections to code that already exists rather than missing
work, and the findings and their reasoning are written up in `docs/calcInventory_review.md`. Once they are cleared the
function should be exercisable for the first time, which is what the rest of the list needs before it can be judged.

### The power and pricing subtree was reviewed and has three arithmetic slips that change every number

The whole of `objectPower` and its twenty-odd helpers was reviewed on the same basis, after the question about
`bowMulitplier` showed the earlier review had stopped one call short of it. The three that matter are a divide where the
original subtracts in the slay term, the wrong one of two adjacent constants in the weight term, and a loop nested one
level too deep in the element term — each of which changes the answer for a large class of objects rather than an edge
case. Nothing was changed today beyond the guard fix below; the findings are recorded in `docs/objectPower_review.md`.
Because every price in the game runs through this code, it is worth clearing before any of the pricing or listing
behaviour is tested against the original.

### The ordering comparator is written to two argument conventions at once

`earlierObject` is the port of the function that decides which of two objects comes first in a listing, and most of its
body reads as though the receiver is the incumbent and the parameter is the challenger, while its type comparison and
both of its call sites read the other way round. That matters more than a single wrong test, because it means each block
has to be judged separately rather than the whole method being flipped. The fix is to settle which object the receiver
is meant to be and make the body and the call sites agree. It is the one finding in either review that is a design
question rather than a correction, and it should be answered before the individual blocks are touched.

### The saturating-add helper was the day's fix

Both methods in `Guards` were clamping with the same value for the lower and upper bound, so every call returned the
maximum integer regardless of its arguments. That reached the curse power, the weight adjustment and the curse attribute
merge, which meant any cursed object priced at the integer maximum before any of the other findings got a chance to
matter. Both methods now clamp between the minimum and the maximum, which is what the original does. It is the only
change made to the source today, and it unblocks judging the remaining curse findings by their actual numbers.

### Curse pricing is the first real structural divergence in this subsystem

The original prices a curse by running the ordinary power calculation over the curse's own object, because in C a curse
*is* an object. The port's `Curse` is a flattened record, so the same work is done by a second overload of nearly every
power function, twenty-one of them. Most of those overloads are correct precisely because of what a curse object is — no
base armour, not jewellery, no brands or slays in the data — and checking that took as long as the rest of the review.
Going forward this is the shape to keep in mind whenever the two power paths drift: there is no single function to fix,
and a change to one side needs the same change considered on the other.

## Things not to drop

- The two review documents are the detail for everything below; the precis deliberately does not repeat their line
  references.
- Three findings block `calcInventory` from running at all — the unsized pack list, the two gear walks that run past the
  end of the list, and the comparator returning the wrong answer for a null argument.
- The pack loop runs one iteration short of the original, which is where the deliberate "overfull by one" slot comes
  from, and the pack re-arrange message is missing a negation.
- `ItemObject.copy` has three separate problems: it dereferences four nullable fields, it deep-copies the kind and ego
  and artifact templates the original shares, and it drops the origin depth.
- Both pricing functions have their own faults — a saturation constant with the wrong sign, and a clamp that lifts
  negative values where the original lifts only zero.
- The three arithmetic slips in the power subtree are the slay term's divide, the weight term's constant, and the
  element term's nested loop.
- A further group of power findings are null and unboxing hazards rather than wrong arithmetic — the modifier map, the
  curse element map, the activation list, and the curse and brand and slay collections the original guards and the port
  does not.
- The curse attribute merge counts a curse's to-armour twice and silently drops any resistance for an element the base
  object says nothing about.
- `Player.slotByType` never reaches its fallback, which is reachable from anything that asks an object which slot it is
  worn in, not just from the power code.
- `flagsPower` looks its flags up in the modifier table rather than the flag table, and should fail loudly rather than
  quietly.
- `bowMulitplier` is spelled with the letters transposed, which is why it stayed invisible to the first review's
  searches.
- The `objectPower` subtree review did not audit the loaded registry tables themselves, only the code that reads them;
  they are the next place to look if the numbers still disagree afterwards.
