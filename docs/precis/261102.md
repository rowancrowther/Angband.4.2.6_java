# Precis — 2026-11-02

## Key points from the day

### UIEntryAssembler.assemble

`UIEntryAssembler.assemble` and `parseEachEntry` turn each parsed `ui_entry.txt` record into `UIEntry` objects, standing in for the `parse_entry_*` callbacks and `hatch_embryo` in `ui-entry.c`, and were checked again against C after the fifteen-item list in `docs/Changes_To_UIEntryAssembler.md`. That check found a `priority:` followed by text, such as `5x` or `0x10`, loading as a number where C refuses it, labels left uncut where C keeps 80, 5 and 2 characters, and a new `registerLabel` that overwrote an explicit `label5` or `label2` and threw on a label shorter than its `label5`. You fixed them by requiring a sign and digits only, cutting each label once per path, and having `registerLabel` keep the explicit shortened labels and take the shorter slots from them. The label range (`label1` to `label10`), a priority at or below the `int` minimum, and the directive order are now accepted deviations in `docs/Accepted_Deviations.md`, and moving `ParseUtils` and `DataFileParseException` into `channel` and giving the stat names to `HelperFunctions` closed every frontend boundary crossing, so the frontend test no longer needs a baseline entry. Thirteen new assembler tests pin the priority text and the labels, six `UIEntryReaderTest` cases now expect the fatal exception, and `UIEntryBaseAssemblerTest` reads category names through the getter because `UIEntryCategory` has no `toString`.

### UIEntryAssembler.assemble priority text

`UIEntryAssembler.assemble` reads the `priority:` number the way `parse_entry_priority` in `ui-entry.c` does with `strtol`, and was checked once more against C. The check found a space or tab before the number, such as `priority: 5`, refused where C loads it, and a first fix then accepted trailing whitespace that C refuses. The assembler now removes only the leading whitespace with `ParseUtils.cTrimFront`, so the number is read from the first non-space character and anything after the digits stays fatal. Three new `UIEntryAssemblerTest` cases pin leading, trailing and scheme-name whitespace, the suite is green at 13601 tests with no failures and 20 skipped, and two Javadoc blocks were corrected, the `priority:` note on `assemble` and the description of the duplicate-parameter throw in `parseEachEntry`. Going forward a `priority:` line follows C for every whitespace case, and the throw in `parseEachEntry` is documented as the Java form of `ui_entry_insert`'s duplicate-name `quit()`.

### ActivationAssembler.assemble

`ActivationAssembler.assemble` reads the `aim:`, `level:` and `power:` text of each `activation.txt` record as `parse_act_aim`, `parse_act_level` and `parse_act_power` in `obj-init.c` do, and numbers the list as `finish_parse_act` does, and was checked again against C and `parser.c`. The check found the behaviour matching, but its Javadoc still said `EffectAssembler` returns `null` for a bad effect, which it no longer does since it throws itself, and the `effects == null` branch is now dead. The class block, the `assemble` block and the inline comment now say that the effect throws, and the class block carries an Outstanding note for the dead branch and for white space before a `-` on `power:`. Four new assembler tests pin a leading `+`, white space before a `-`, and white space alone, and the suite stays green at 13542 tests with no failures.

### UIRegistry

`UIRegistry` holds the loaded UI renderers and the single shared entry list, and its name lookups were checked against `ui_entry_search`, `ui_entry_lookup` and `ui_entry_renderer_lookup` in `ui-entry.c` and `ui-entry-renderers.c`. The check found `getUIEntryBase` searching a separate list of bases that C does not have, so a `template:` naming a `ui_entry.txt` record would have missed where C finds it. The separate list, its setter and `getUIEntryBase` are gone, and `getUIEntry` is the one lookup for templates, overrides and bindings. `UIRegistryTest` was rewritten for the single list, with shipped-data cases, and eight other test files stopped setting the removed field; the suite is green at 13549 tests with no failures and 20 skipped.

### ObjectPropertyAssembler.assemble

`ObjectPropertyAssembler.assemble` resolves each parsed `object_property.txt` record into an `ObjectProperty`, standing in for the `parse_object_property_*` handlers and `finish_parse_object_property` in `obj-init.c`, and was checked again against C. The check found the type, subtype, id-type, code, number, type-mult and bindui handling matching, with the code tables, flag list and element list agreeing name for name with `datafile.c`, `list-object-flags.h` and `list-elements.h`. The class block now records the guard for an empty `type:` and the extra spellings `TValue.fromName` accepts, and its date is refreshed. Three new parameterized tests walk every name in the modifier, flag and element tables, which takes the assembler suite to 188 tests, and the full suite is green.

### UIDataLoader.finalPass

`UIDataLoader.finalPass` and `fillOutShortened` are the Java form of `finish_parse_ui_entry` and `fill_out_shortened` in `ui-entry.c`, and were checked against C. The check found the shortened-label cascade and the priority backfill matching, but a name used as a label was not cut to `MAX_ENTRY_LABEL` (80) characters, as C's `text_mbstowcs` cuts it, so a 100-character name gave a 100-character label. The name is now cut to `UIEntryAssembler.MAX_ENTRY_LABEL`, which was made `public static` for the purpose. All seven Javadoc blocks in the file were rewritten, including the stale base-list wording, and `UIDataLoaderTest` gains four boundary tests (79, 80, 81 and 100 characters); the suite is green at 13561 tests with no failures and 20 skipped. Going forward the one place a label can exceed 80 characters is gone, so the label and every shortened label derived from it follow C.

### UIEntry

`UIEntry` is the Java form of `struct ui_entry` in `ui-entry.c`, with `uiEntryHasCategory`, `setParamIndex` and `copy` as its behaviour, and it was checked against C. The check found the category search, the shortened-label slots, the stat and element split of `param_index` and the flag handling matching, but the class block still described the dropped `UIEntryBase` template and several field and `copy` blocks were wrong or carried C line numbers. All of the class, field and method blocks that were wrong, thin or carried line numbers were rewritten, recording what `struct ui_entry` fields are not held here, the `ELEM_NONE` offset in `setParamIndex`, and that the constructor stores the category list and flag set by reference. `UIEntryTest` grows from 10 to 34 tests, covering strcmp-exact category matching, the label slots, every `setParamIndex` kind, flag copying and `copy` independence, and the suite is green at 13585 tests with no failures and 20 skipped. Going forward the entry's behaviour is pinned to C's element order and label slots, so the later render and registry ports can lean on it.

### HelperFunctions

`HelperFunctions` holds the nine small lookup functions behind C's `name_parameters[]` and `priority_schemes[]` tables in `ui-entry.c`, the dummy, element and stat name schemes and the three priority schemes. The element lookup had been moved to a plain 0-based index, so the class and `getElementName` Javadoc and the whole test class still described and expected the old one-place shift. The Javadoc now says index 0 is `ACID` as in C, notes that C's asserts become exceptions, and documents the `stats` field, while `HelperFunctionsTest` is rewritten against the names in `list-elements.h` and `list-stats.h`, with 19 tests. Anything later that expands an element or stat parameter can pass C's own indices straight through.

### UIEntryCategory

`UIEntryCategory` is the resolved (name, priority, priority set) triple behind C's `struct category_reference` in `ui-entry.c`, the form `UIEntry` keeps after parsing. Its three fields and the constructor already matched C, but the Javadoc cited C line numbers and named two C functions that do not exist, and the three setters and `copy()` had no Javadoc at all. Every block was rewritten to name `parameterize_category_list`, `finish_parse_ui_entry` and `cmp_desc_prio`, which read or fill the fields, and thirteen unit tests now cover the constructor, each setter writing one field only, the unset-to-default fill, and `copy()` giving an independent object. Anything that gives an unset category a priority must call both `setPriority` and `setPrioritySet`, because neither setter touches the other field.

## Things not to drop

- `UIEntryBaseAssembler` adds categories to the entries it builds without sorting them by name, so `UIEntry.uiEntryHasCategory` can return an index that differs from C's sorted one for a template entry; presence is unaffected.
- `UIEntryAssembler` calls `registerLabel` with the raw `label` in the element branch but with `newLabel` in the stat branch, so an element record with no `label:` may get empty shortened labels where C derives them from the element name.

- `HelperFunctions.stats` is a public, mutable array, and `UIEntryAssembler` reads it directly instead of through the package-private `getStatName` and `getStatCount`.
- `UIEntryNameParameter` and `UIEntryPriorityScheme` have no callers in `main` outside their own files, because `UIEntryAssembler` expands stat and element parameters and priorities inline, so the `HelperFunctions` element lookups are exercised only by tests.
- `UIEntryCategory` has no `toString()`, so `UIEntryBase.toString()` prints the categories as object addresses.
- `ActivationsGrammar.g4` keeps only the last `aim:` or `power:` line of a record, so a negative first line overwritten by a later valid one loads where C quits; not yet in `docs/Accepted_Deviations.md`.
- `UIRegistry.getUIEntries` and `getUIEntryRenderers` throw a `NullPointerException` before load, where `getUIEntry` throws `IllegalStateException` and C's unloaded arrays are simply empty.
- `UIRegistry` still imports `UIEntryBase`, which is now unused.
- `ObjectPropertyAssembler` has its `UIRegistry.getUIEntry` bind lookup commented out, so C's `bind_object_property_to_ui_entry_by_name` is not yet ported.
- `TValue.fromName` falls back to the Java constant name, so `drag armor` or `soft_armor` resolves where C's `tval_find_idx` returns -1; `ObjectPropertyAssembler` inherits it on `type-mult:`.
- `UIEntryBaseAssembler` still builds a `UIEntryBase` per record and returns them, which `loadUIEntryBases` ignores, though `UIEntryBase` was dropped in the 260919 decision.
- `UIEntryRendererReader` cannot carry the `combine`, `units` and `combined-renderer` directives that C's `ui_entry_renderer.txt` parser accepts.
- `UIEntryGrammar.g4` says in its header that `priority` appears at most once, but the record rule reads `(priority {...})*`, so a second `priority:` line is accepted and only the last survives in `UIEntryParseRecord`.
