# Parked items

*Created 2026-11-11.* This file lists the work that has been deliberately set aside, one line each: what it is, what it waits on, the date it was decided to park it, and where the detail lives. It links to the existing entries and does not copy them, so a change of mind is made in the place the detail lives and then reflected here. It is not a checklist (`ROADMAP.md` is) and it is not a list of accepted deviations (`Accepted_Deviations.md` is). Parked means "not now, and not forgotten"; accepted means "decided, and Java differs from C on purpose".

Dates are the day the item was decided to be parked. Where a source gives only a file date or a "still open at" date, the line says so, and that date is the best record there is.

## Parsers and data

- **Monster lore parsing (`LoreReader`, `LoreGrammar.g4`, `LoreLexer.g4`).** Parked 2026-08-13. Waits on real game-generated lore data to test against; it is the last item on the roadmap. The `LoreReaderTest` skips are this park, not neglect. Detail: `Issue_Approach_Order.md` Stage 10, `grammar_issues.md` (the lore entry), `ReaderPort.md`.
- **Loading `lore.txt` at start-up.** Parked 2026-08-13 ("Defer to chapter 8"). The load call in `GameConstants` stays commented out; the file lives in the user directory and C tolerates its absence. Waits on save/load in Chapter 8. Detail: `ROADMAP.md`.
- **Load-time checks on `dice:` and `expr:` text.** Decided 2026-10-25, entered in Stage 10 on 2026-11-11. A bad dice string, a bad operations string and an `expr:` letter that no `$` binds are refused by C at load and are not checked in Java. Waits on the roll engine, which `EffectAssembler` will call at load, as it calls `Random.parseStr` today. Detail: `Issue_Approach_Order.md` Stage 10, memory `effect-dice-validation-deferred-to-roll-engine`.
- **A `default:` line after the first `name:` in `object_base.txt`.** Parked 2026-11-13, accepted as a deviation to be worked on in a later version. C applies it to the records that follow, in either of two shapes (between records, or inside one); Java stops the load. The between-records shape is a loop-shape change in the `file` rule of `ObjectBaseGrammar.g4`, and the inside shape also needs the fold to read the defaults as they stood at the `name:`. Detail: `Accepted_Deviations.md` under "Object base", `grammar_issues.md` (the `ObjectBaseGrammar.g4` entry).
- **A vault with no `D:` lines has a `null` flat layout (`Vault.getMapLines()`).** Parked 2026-11-18. C's `v->text` is also NULL until the first `D:` line, so `VaultAssembler.parseMap` matches C and the record loads; the per-row `getMap()` is an empty list. Nothing in `src/main` reads either getter yet (only `parseMap` itself), so nothing can fail today, and the shipped `vault.txt` gives every vault `D:` lines. Waits on the port of the vault room builders (for example `build_vault`), which index `text[y * wid + x]`: decide there whether the reader guards against a null layout or the assembler refuses a vault with no `D:` lines. Pinned by `VaultAssemblerTest.aRecordWithNoMapLinesHasNoFlatLayout`.
- **One `Directive` per line in `RoomProfileGrammar.g4`.** Parked 2026-11-19. C checks `type:`, `rating:`, `rows:`, `columns:`, `doors:` and `tval:` as each line is read, so `rows:99` followed by `rows:5` stops the load; `RoomProfileGrammar.g4` overwrites a text field per line, so the assembler only ever sees the last value and loads it with rows 5. The same goes for `type:-1` then `type:1` and `tval:bogus` then `tval:rod`. The fix is the `VaultGrammar.g4` shape: the record keeps every directive as a `Directive` in file order and `RoomProfileAssembler` walks them, checking each as C does. Until then the unordered, optional directives of Stage 7a are in place and only the repeated-bad-first-value case differs. Detail: `Issue_Approach_Order.md` Stage 7a, `grammar_issues.md` (the `RoomProfileGrammar.g4` entry). Pinned by `RoomProfileReaderTest.aBadFirstValueOfARepeatedDirectiveIsLostHereWhereCRefusesIt`.
- **Three lexer differences in `RoomProfileLexer.g4`: a space-only `flags:` separator, a hexadecimal number, and a field after a value.** Parked 2026-11-19. C splits `flags:` with `strtok(s, " |")`, so `flags:FEW_ENTRANCES MAX` is two flags; `FLAG_OR` needs the `|`, so Java refuses the file. C reads `rows:0x3` as 3 (`strtoul`, base zero); `INTEGER` is `'-'? ('0'..'9')+`, so Java refuses it. C tokenizes a number on `:` and ignores the rest, so `type:1:7` reads 1; Java gives a syntax error. The first is the shared flag-separator shape (16 lexers, `Issue_Approach_Order.md` "What the lexers require now"). The other two are the wide `INTEGER` token that the Stage 4 grammars already have, with the base zero reading in the assembler through `ParseUtils`. Detail: `grammar_issues.md` (the `RoomProfileGrammar.g4` and `RoomProfileLexer.g4` entry). Pinned by `RoomProfileReaderTest.flagsSeparatedByASpaceAloneAreRefusedHereWhereCSplitsOnIt`, `aHexadecimalRowCountIsRefusedHereWhereCReadsBaseZero` and `aFieldAfterTheValueIsRefusedHereWhereCIgnoresIt`.
- **A leading `effect-dice:` in `PlayerTimedGrammar.g4` does not stop the load.** Parked 2026-11-19. C's `parse_player_timed_effect_dice` (`player-timed.c`) returns `PARSE_ERROR_MISSING_RECORD_HEADER` when no `on-begin-effect:` or `on-end-effect:` line has opened an effect in the record, so `effect-dice:5` straight after `name:`, or before its effect line, stops the load. The grammar keeps each effect as an `EffectParseRecordType` in a list and attaches `effect-dice:` to the last one opened; with the list empty it does nothing, so the dice are dropped and the record loads, as `ChestTrapGrammar.g4` does. The fix is for the grammar to throw from that guard, or to hand the unattached dice to `PlayerTimedAssembler` to refuse with the record's line and file. Detail: `Issue_Approach_Order.md` Stage 7a. Pinned by `PlayerTimedReaderTest.anEffectDiceWithNoEffectOpenIsDroppedHereWhereCRefusesIt` and `PlayerTimedReaderTest.anEffectDiceBeforeItsEffectLineIsDroppedHereWhereCRefusesIt`.
