# Precis — 2026-09-01

## Key points from the day

### `Player.java` was split along C's file boundaries

`Player` had absorbed six C translation units and stood at 6241 lines, with four more C files destined for it if nothing
changed. The plan written this morning, `docs/Player_split_plan.md`, decided a method's home by which C file defines it
rather than by what the Java signature touches, and every row of it is now done. `Player.java` is 1686 lines and holds
`struct player` plus
`player.c`. Going forward the rule is mechanical: a newly ported function goes to the class named after its C file, and
a new C file means a new Java class rather than another tenant on `Player`.

### The new classes are static, taking the player as the first argument

Moving instance methods off `Player` meant choosing a form for them. Everything that moved became a static method whose
first parameter is the player, which keeps each Java argument list identical to its C original so the two can still be
read side by side. The cost is at the call sites, which now name the class they are calling — and that is the point,
because the class name says which C file the behaviour comes from.

### The fields were widened rather than wrapped

The split needed same-package access to 63 private fields, and the plan offered accessors or wider fields. The fields
were widened to package-private, so the `middle.player` package boundary is now what does the job C's `static` does, and
nothing outside the package gained any new reach. Worth holding on to: that protection is the package, not the
compiler's `private`, so a class added to this package sees everything.

### Three clusters left the player package entirely

`obj-gear.c` and `obj-ignore.c` code had been living on `Player` and is not player code at all. Ten methods went to
`ObjectUtils`, four to a new `ObjectIgnore`, and the monster refresh went to
`MonsterUtils`. A duplicate stub of `equipLearnFlag` that had been sitting in `ObjectUtils` was deleted rather than left
as a third copy, which was the risk the plan called out.

### Test doubles that subclass the player stopped working

The knowledge-walk test recorded what it saw by overriding a method on a `Player` subclass, and a static method cannot
be overridden. It was reworked to observe the collection the walk iterates instead, pushed into both the level's objects
and the player's gear. That boundary is the more durable of the two anyway, because it watches the loop rather than what
the loop calls — the shape to reach for whenever a moved method leaves a test double with nothing to hook.

### The port's two records of itself were brought back into line

`docs/ported_functions.md` had been accurate at 260830 and was left behind by both the split and the week's porting, and
the reference C source was missing its stamps for a whole file. The document is regenerated at 295 C functions across 43
files, with 59 rows repointed at their new classes and two new sections for `player-history.c` and `randname.c`; 25
stamps were added to the C source, and every listed function now carries one. These two and `docs/ROADMAP.md` are the
only places the port records what it has done, and all three drift the moment a class moves.

### A Javadoc pass over what was left behind

The accessors that stayed on `Player` were commented in full, as were the four new classes, and
`StringUtils` gained the four character helpers the safe-name port needed. One contradiction was settled:
`PlayerHistory` claimed in one block that its constructor is the port of C's list initialiser and in another that the
same function has no counterpart, and the second claim was dropped.

## Things not to drop

- `learnRune` is public. The split plan wanted it package-private, because C keeps it static and it is the single
  guarded entry that fires the second update and the group fan-out.
- The 63 fields are package-private, so anything added to `middle.player` sees all of them; the package boundary is the
  whole of the protection now.
- `PlayerTimed.clearTimed` and `PlayerTimed.incTimed` are superseded stubs that take no player and can never work; one
  caller in `GameWorld`, paralysing the player, is all that keeps them alive.
- A test double that subclasses `Player` can no longer observe anything that moved, because the moved methods are
  static; the collection a walk iterates is the boundary to record on instead.
- `updateMaxLevel` and `updateDungeonDepth` have no C original found and stay on `Player` until their provenance is
  established.
- `ported_functions.md` lists only full ports, so the stubs left in `ObjectUtils` and `ObjectIgnore`, and the partially
  implemented knowledge refresh, are deliberately absent from it.
- `find_roman_suffix_start` is ported, listed and stamped, but its roadmap box under stage H is unticked.
- Chapter 3 stages A to F are complete; stage G, `player_generate` and its helpers, is next.
- Dropping the allocation note from `PlayerHistory` leaves the reason C's list-grow function has no counterpart recorded
  nowhere.
