# Precis — 2026-09-24

## Key points from the day

### Batch /port verify over 18 ui_entry files stopped at stage 1

A `/port` verify pass was run across the whole ui_entry group in one batch — `UIEntry`, `UIEntryAssembler`,
`UIEntryBase`, `UIEntryBaseAssembler`, `UIEntryBaseParseRecord`, `UIEntryCategory`, `UIEntryCode`, `UIEntryEmbryo`,
`UIEntryNameParameter`, `UIEntryPriorityScheme`, `UIEntryRendererEnum`, `UIEntrySpec`, `UIEntryValue`,
`UIEntryValueRegistry`, `UIEntryValueSnapshot`, `UILoop`, `UIMessage` and `UIRegistry`.

Most of the group checked out clean against `ui-entry.c`, but eight real discrepancies turned up, the most structural
being that the 260919 decision to drop `UIEntryBase` and share one registry is only half-implemented.

No fix was written for any of them — stage 1 found mismatches, so the pass stopped there per the port rules, with
nothing touching `src/main`.

The numbered list below is what's open going into the next session; none of it is fixed yet.

### objectFlagIsKnown ported

`ObjectUtils.objectFlagIsKnown` was checked against C's `object_flag_is_known` (`obj-knowledge.c`) and verified clean at
stage 1: the same three OR'd checks, in the same order, with the same fall-through to false.

The method carried no Javadoc at all, so a caller reading `ObjectUtils` had to open the C source to learn why the three
checks exist or which struct each one is standing in for.

A method-level block was added naming the C cross-reference and tying each of the three branches to the exact C
expression it mirrors, and six unit tests were written from the C original's branches (fully known, player-known flag,
shadow-known flag, and the false fall-through) in a new `ObjectUtilsObjectFlagIsKnownTest`.

Object-flag lookups elsewhere in the port — stores, the ui-entry value registry — can now cite this method's Javadoc
instead of re-deriving the three-check rule from the C source each time.

### curseObjectFlagIsKnown and objectElementIsKnown ported

`ObjectUtils.curseObjectFlagIsKnown` and `objectElementIsKnown` were checked at stage 1 as the curse-shaped counterparts
to `objectFlagIsKnown`'s and C's `object_element_is_known`, both of which C never calls with a curse.

`curseObjectFlagIsKnown` matched cleanly, but `objectElementIsKnown` did not: it took no `Player` and so had no way to
check the player's own element-rune knowledge, and its known-shadow check had a dead branch that read a curse with a
recorded-but-zero resistance level as known, a false positive C's original never produces. Rowan fixed both before this
pass reached Javadoc.

The corrected method now takes the `Player` and reads the player's rune knowledge before falling back to the curse's own
known-shadow, matching C's three-check order exactly. Javadoc was added to both methods and six new unit tests written
across two files, including one pinned directly to the fixed bug (a known-but-zero shadow entry now reports unknown
rather than known).

Curse-side element and flag knowledge queries elsewhere in the port can now rely on `objectElementIsKnown` agreeing with
the player's rune state instead of only ever reading the curse's own shadow.

### UIEntryValueRegistry's compute/known-rune methods verified

`UIEntryValueRegistry`'s core methods — `computeForObject`, `computeForPlayer`, `isKnownRune`,
`modifierToSkill`, `getTimedModifierEffect` and `getTimedElementEffect` — were checked clause by clause against
`ui-entry.c` and found to match: curse-power gating, the auxiliary/timed-as-aux swap, the racial skill and infravision
contributions, and the unknown-value sentinel all line up.

This was the file the previous precis flagged as wanting its own dedicated pass; that note is now out of date on both
counts it raised — the class, its fields and every method already carry full Javadoc, and the curse-walk ordering it
flagged as an unconfirmed risk turns out not to be reachable yet, since nothing in the port can currently put more than
one curse on an item.

A full `UIEntryValueRegistryTest` suite was written straight from the C originals' branches rather than mirrored off the
port, covering registration upsert semantics, curse power gating, the unknown sentinel, both special-cased player
abilities, and the racial-skill/infravision contributions; the suite is green.

Second-character-screen values for objects and players can now be trusted to agree with C, and any future change to the
combiner or curse-walk logic has a regression suite ready to catch a divergence.

### Second /port pass over the same 18-file batch: re-verified against the fixes, six files Javadoc'd and tested

A second `/port` run was invoked over the same 18-file `ui_entry` batch this precis already tracks. Rather than
re-litigating everything from scratch, each file was re-read this turn and checked against the "Things not to drop"
list below and the C original, since a finding from earlier today is stale the moment the underlying file changes.

Two of the eight tracked items turned out to already be fixed since they were written — `UIEntryCode.sortFunction`
now reads a matching category's priority unconditionally (no `isPrioritySet()` gate), and `UIEntryAssembler`'s create
path now drops a record with no combiner instead of inserting it regardless, both now matching C. The other six items
(`UIEntryBase` not yet folded into one registry, the two template-category-priority spots that follow from that, the
unused `UIEntryBaseAssembler` return list, and `buildCategories`' after-priority inheritance) are unchanged and still
open — see the updated list below.

Six files in the batch carried no Javadoc at all — `UIEntryCode`, `UIEntryNameParameter`, `UIEntryPriorityScheme`,
`UIEntrySpec`, `UIEntryValue` and `UIEntryValueSnapshot` — plus `UIRegistry`, whose three lookup methods were one-liners
with no C cross-reference or provenance stamp. All seven were verified clause-by-clause against
`ui-entry.c` first; `UIEntryCode`'s sort and iterator-building logic and `UIRegistry`'s three lookups matched exactly,
and `UIEntryNameParameter`/`UIEntryPriorityScheme` matched their C tables field-for-field.

Full Javadoc was written for all seven (class, fields, methods, provenance stamps), and new unit tests were added for
the three with real logic — `UIEntryCodeTest` (iterator filtering and every sort-ordering branch),
`UIEntryPrioritySchemeTest` and `UIEntryNameParameterTest` (both derived from the C table functions directly). The full
suite (5377 tests) is green.

While writing `UIEntryNameParameterTest`, one new discrepancy turned up: `HelperFunctions.getElementName` returns
`ElementEnum`'s own constant name (e.g. `"ELEM_ACID"`), not the bare token C's `get_element_name` returns (e.g.
`"ACID"`). It's inert today — nothing in the live assembly pipeline calls `UIEntryNameParameter`'s `getParamName`
for the element scheme, since both assemblers expand `parameter:element` with their own hand-rolled loop over
`ElementEnum.values()` that strips the prefix itself — so the test asserts the count but leaves the element name
unasserted rather than pinning it to the wrong value. See the new item 9 below.

This batch's remaining open items (1, 4, 5, 6) are all traceable to the same root cause — the 260919 "one registry"
decision not yet being implemented — so fixing `UIEntryBase`'s fold-in first would likely resolve several of them
together rather than needing four separate patches.

### HelperFunctions.getElementCount's doc/test mismatch fixed

A full-suite run at the end of the `ChannelEntryFlag`/`GameConstants`/`KnownObject`/`ObjectProperty` pass above turned
up two failing tests, `HelperFunctionsTest` and `UIEntryNameParameterTest`, both asserting that
`HelperFunctions.getElementCount()` returns 26.

The method's own Javadoc claimed the return value was "one more than" `ElementEnum`'s real element count, but the code
(`values().length - 2`) actually returns the count unshifted, matching C's `get_element_count()` exactly —
`ElementEnum` carries two Java-only placeholders, `ELEM_NONE` and `ELEM_MAX`, both of which need subtracting off, not
one. The doc was wrong, not the code, which Rowan confirmed.

Both tests were corrected to expect 25 and renamed to describe the real behaviour, and the misleading Javadoc line was
fixed to match.

The full suite is green again, and the method's doc no longer contradicts its own code.

## Things not to drop

1. `UIEntryBase` is still a separate live type, not folded away as the 260919 "one list" decision called for:
   `UIRegistry.java:57` keeps a second `uiEntryBases` list alongside `uiEntries`; `UIEntry.java:62` still has a
   `private UIEntryBase template` field; `UIEntryAssembler.java:295` resolves `template:` against the separate
   `UIRegistry.getUIEntryBase(name)` list rather than the shared registry; and `UIEntryBase.java:104`'s `categories`
   is still `List<String>` with no priority field to copy onto a child entry.
2. `UIEntryPriorityScheme.java:25` — `PRIORITY_SCHEME_NEGATIVE_INDEX`'s stored name is `"negative index"` (space); C's
   is `"negative_index"` (underscore, `ui-entry.c:160`). Inert today since callers match the raw parsed string directly
   rather than calling `getName()`. ***DONE***
3. `UIEntryCode.java:52-99` (`sortFunction`) — when a category matches but `isPrioritySet()` is false, it uses `0`
   instead of `category.getPriority()`. C's `cmp_desc_prio` (`ui-entry.c:391-440`) reads `.priority` unconditionally,
   with no `priority_set` check. Inert since `UIDataLoader.java:181-183` always sets `prioritySet=true` before an entry
   reaches the registry. ***DONE*** — re-read 260924: `sortFunction` now reads `category.getPriority()` unconditionally
   once a matching category is found, no `isPrioritySet()` gate present. Matches C.
4. `UIEntryAssembler.java:434-441` and `:539-549` — template categories are built with the new entry's own priority and
   `prioritySet=false`, instead of copying the template's own stored category priority and `priority_set` the way C's
   `parse_entry_template` does (`ui-entry.c:1983-1988`). Latent: no shipped `ui_entry_base.txt` record combines
   `category:` with `priority:`, and issue 1 means `UIEntryBase` can't hold a per-category priority yet anyway.
5. `UIEntryBaseAssembler.java:137` — `assemble()` still builds and returns an unused `List<UIEntryBase>` per record,
   separate from the plain `UIEntry` it actually feeds to `UIRegistry.setUIEntries()` at line 148. Looks like leftover
   from before the 260919 rework rather than a live behaviour.
6. `UIEntryAssembler.java:113-123` (`buildCategories`) — an after-priority category inherits the before category's
   priority instead of 0, when both are present on the same record. Latent: no shipped record has a `category:` line
   before a `priority:` line.
7. `UIEntryAssembler.java`'s create path has no equivalent of `hatch_embryo`'s `combiner_index == 0` guard
   (`ui-entry.c:1773-1779`), which drops the whole record rather than inserting it. Latent: no shipped `ui_entry.txt`
   record lacks both `combine:` and `template:`. ***DONE*** — re-read 260924: `parseEachEntry`'s create path now returns
   `false` (dropping the record, `assemble`
   reports it as an error) when `embryo.getUiEntry().getCombineType()` is `null` or `CombinerName.NONE`. Matches C.
8. `UIEntryValueRegistry.java` — 650 lines, no class or method Javadoc, not clause-verified this pass; wants its own
   dedicated `/port` run. One risk flagged in passing: `computeForObject`'s curse loop
   (`UIEntryValueRegistry.java:102-259`) iterates `item.getCurses().keySet()`, which has no guaranteed order the way C's
   fixed `curse_ind` walk does (`ui-entry.c:702-824`) — a real risk if that map is a `HashMap` and an order-sensitive
   combiner like `LOGICAL_OR_WITH_CANCEL` is in play, not a confirmed bug. ***DONE*** — resolved in the dedicated
   `UIEntryValueRegistry` pass earlier today: `ItemObject.curses` is a
   `LinkedHashMap`, so iteration order is insertion order, not arbitrary.
9. `HelperFunctions.getElementName` (`UIEntryNameParameter.ENTRY_NAME_PARAMETER_ELEMENT`'s `ith_name_func`) returns
   `ElementEnum.values()[index].name()` (e.g. `"ELEM_ACID"`) rather than C's bare `get_element_name` token (e.g.
   `"ACID"`, `ui-entry.c:1606-1610`). Found 260924 while writing `UIEntryNameParameterTest`. Inert: nothing calls
   `UIEntryNameParameter.getParamName` for the element scheme today, since `UIEntryAssembler`/`UIEntryBaseAssembler`
   expand `parameter:element` with their own loop over `ElementEnum.values()` that strips the `ELEM_` prefix itself.
