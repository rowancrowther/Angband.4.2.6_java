# Precis — 2026-11-25

## Key points from the day

### Activation

`Activation` is the Java form of C's `struct activation`, the record `activation.txt` fills through the `parse_act_*` handlers in `obj-init.c`. Its field and method blocks were one-line stubs, so nothing said which C member each field stood for, that `aim` is parsed but never read by C, or that `copy()` throws on a null effect list. The class, all seven fields, the constructor and the accessors now carry full Javadoc naming the C member, its parse handler and its readers, and `ActivationCopyTest` now pins effect order, the null message and description, the caller's list being kept, and the null-list throw. Later code that reads an activation's level, message or description has the C readers to port against, and a null effect list is documented as unsupported rather than found out at runtime.

### AllocEntry

`AllocEntry` is the Java form of C's `struct alloc_entry` in `alloc.h`, the row type of the monster race table in `mon-make.c` and the ego-item table in `obj-make.c`. It already matched the C struct field for field, but its Javadoc described the table as an object table and said nothing about what `index`, `level` and the three probabilities mean in each of the two tables that use it. The class and its five fields now record that `prob1` is the base weight, `prob2` is `prob1` or 0 after the restriction pass, `prob3` is `prob2` or 0 after the level pass, and that an ego entry's `level` is unused, and `AllocEntryTest` gained cases for how each table loads an entry and for the restriction reset. Whoever ports the race and ego tables later can set the fields from those documented rules and test against the pinned scenarios.
