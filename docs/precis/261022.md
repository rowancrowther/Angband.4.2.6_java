# Precis — 2026-10-22

## Key points from the day

### ActivationAssembler.assemble

`ActivationAssembler` turned a bad `aim:`, `level:`, `power:` or effect into a soft error and dropped the record. It also read the three numbers by plain text comparison, so `aim:2` was false and `level:010` was 10. A load could succeed with activations missing, and the numbers could differ from C's. `assemble` now stops the load with `DataFileParseException` naming the file and the line the record starts on, and reads the three fields as C's `strtol` and `strtoul` with base 0 do, clamping a number too big for an int. Activation values now match C except for the clamp, the line per record and the order faults are reported in, which `Accepted_Deviations.md` records, and the Javadoc and the three activation test classes are rewritten to match.

### HelperFunctions.parseIntString

`HelperFunctions` was written on 2026-10-22 to read the activation numbers as C's `strtol` with base 0 does. Its octal and decimal reading shared one digit-limit test with a wrong sign in the arithmetic, so the limit never applied and `08`, `09` and `019` stopped the load where C reads 0, 0 and 1. The limit is now built as the base's last digit plus `'0'`, so reading stops at the first character that is not a digit of the base. Activation numbers now read as C reads them, the class and every function carry Javadoc, and `HelperFunctionsTest` covers decimal, octal, the digit limit, the clamp and the no-digits stop.

### ArtifactAssembler brand and slay order

`ArtifactAssembler` held an artifact's brands and slays in `HashSet`s, so their order was arbitrary, where C walks them by registry index and that index runs in reverse file order. Nothing reads the order yet, but the multiplier loops that will need it match C only if the sets arrive sorted. `assemble` now fills `LinkedHashSet`s by looping the registry lists, and `Artifact.copy` keeps them as `LinkedHashSet`s, so the order survives a copy. `ArtifactBrandSlayOrderTest` pins it for all 138 artifacts, 4 of which list their brands and 35 their slays in a different order from C's, and the ego and object assemblers will follow when they are ported.

### ArtifactReaderTest brought up to the hard stops

Once `ArtifactAssembler` threw `DataFileParseException` instead of dropping a record, 13 tests in `ArtifactReaderTest` failed, because they expected skipped records, `null` times and the old deviations from C. They now assert the throws through one `assertStops` helper, expect a zero `Random` where an artifact has no `time:`, and expect `alloc:`, `graphics:`, `act:`, `IGNORE_`/`HATES_` and a second parse to behave as C does. Those five behaviours were open entries in `Assembler_Issues.md` and are now closed in the code, and the full suite is green.

### HelperFunctions fixed-base reading

`ArtifactAssembler` reads the two numbers of an `alloc:` range with a second `parseIntString` that fixes the base at 10, as C's `grab_int_range` does, so `010` is ten there and eight everywhere else. Both overloads gave the same answer as `strtol` on 29 inputs, including the octal digit limit and the clamp, and a lone `-` is the one case that differs, which the lexer never produces. The class block now names both callers and the second reading, the overload and every `type` parameter are documented, and `HelperFunctionsTest` covers the fixed-base rows worked out from `strtol` in C. A third caller will need nothing more than the right `type` string.

## Things not to drop

- `ActivationAssembler.java` `power < 0` check after the `-` test can never fire, because the `-` test already rejects every negative `power`.

- `EffectAssembler.java` still appends to `errors` and returns `null` for a bad effect; `ActivationAssembler.java` throws on that `null`, but the 22 sites in `EffectAssembler.java` are not yet converted.
- `ErrorParsing.java` `reportAndCheck` passes a load that has errors as long as one item survived, so soft errors elsewhere still never stop a load.
- `ActivationReader.java` Javadoc (class block and `parse`) still says an assembler error skips only the offending record.
- `Artifact.java` `copy` carries the activation and activation message across where C's `copy_artifact` clears both to NULL, and the class block wrongly says C never copies an artifact.
- `ArtifactAssembler.java` has three small divergences from C: a `values:` figure of exactly `INT_MAX` or `INT_MIN` loads where C refuses it, a special light's kind has its weight, cost and time overwritten when the record has no such line and keeps its activation when `act:` is unknown, and an absent `msg:` gives `""` where C holds NULL and `cmd-obj.c` tests for it.
- `ArtifactAssembler.java` assemble Javadoc still says a bad record goes into `errors` and is skipped.
- `docs/Assembler_Issues.md` still lists the `IGNORE_`/`HATES_`, `alloc:`, unknown `act:`, `graphics:` and second-parse artifact entries as not fixed, though all five are now fixed in `ArtifactAssembler.java`.
