# Precis — 2026-11-04

## Key points from the day

### UIEntryRendererAssembler.assemble

`UIEntryRendererAssembler.assemble` turns each parsed `ui_entry_renderer.txt` record into a `UIEntryRenderer`, standing in for the `parse_renderer_*` callbacks and `finish_parse_ui_entry_renderer` in `ui-entry-renderers.c`, and `padString` is the Java form of `augment_colors` and `augment_symbols`. The check against C found four problems: a new name was inserted at index `size() - 1`, which crashed the first record and put each later one in front of the last; `sign:SIGN_DEFAULT` was accepted; an unset sign came out `null` instead of the backend default; and a sign was lost when a later block with the same name left it out. You fixed them by appending new names at the end, refusing the `SIGN_DEFAULT` sentinel, storing the raw sign, and resolving an unset sign from the code in effect through `UIEntryRendererEnum.getEntry`, the same shape as the `ndigit` default. Fourteen new assembler tests pin list order, same-name merging, re-padding when a later block changes the code, the 64-character cap and case-sensitive codes and signs, two tests now expect `UI_ENTRY_RENDERER_NONE` for a block with no code, and the suite is green at 13617 tests with no failures and 20 skipped.

### UIEntryRenderer

`UIEntryRenderer` is the Java form of C's `struct renderer_info`, and it now holds each colour table, symbol table, digit count and sign twice: raw, as the data file left it, and resolved against the backend's defaults. C needs only one copy because it reopens a repeated record and pads once at finish, whereas the assembler resolves record by record. The class was checked against the struct and the parser's initial and finished states, then fully Javadoc'd and given ten tests. The raw half is `null` until the assembler sets it, and combiner, units and combined-renderer stay uncarried until those directives are parsed.

### UIEntryRendererEnum

`UIEntryRendererEnum` is the Java form of the `backends[]` table in `ui-entry-renderers.c`, built from `list-ui-entry-renderers.h`, and holds the defaults each data-file renderer falls back on. The check against C found all six rows match in combiner, colours, label colours, symbols, digit count and sign, in C row order after the `UI_ENTRY_RENDERER_NONE` sentinel, so no existing code had to change. You folded the short-lived `getDefaultSign` back into `getEntry`, which the assembler now calls for the sign default, and the Javadoc records what the enum leaves out: the draw and width functions, and a getter for the combiner. Three new tests pin the row order, the `NO_SIGN` default on every constant, and non-empty tables on every C row, and the suite is green at 13627 tests with no failures and 20 skipped.

## Things not to drop

- `UIEntryRendererParseRecord` has no fields for C's `combine:`, `units:` and `combined-renderer:` directives, so a renderer file using them cannot be represented; the shipped `ui_entry_renderer.txt` uses none of them.
