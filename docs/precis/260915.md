# Precis — 2026-09-15

## Key points from the day

### `SavefileGetterImpl.gotSavefile` verified, fixed, and covered

`SavefileGetterImpl` - the Java port of C's `struct savefile_getter_impl` and `got_savefile()` (`src/ui-game.c`) - was
checked against the original this session. Two real discrepancies turned up in the existing port: the directory-open
success flag was set unconditionally instead of reflecting whether the save directory actually opened, and the
null-directory guard was conflating "never opened" with "enumeration already finished", logging an error on what is an
entirely ordinary case for a caller. You fixed both, adding a flag that tells the two null-directory causes apart the
same way the C original's two separate call branches do. The class and its methods now carry full Javadoc with the C
cross-reference, and a new test class covers a directory that fails to open, an empty directory, several entries
enumerated one at a time, and sub-directories being skipped; the full project suite is green.

### `SavefileDetails` verified and covered

`SavefileDetails` - the Java port of C's `struct savefile_details` (`src/ui-game.h`) - was checked against the original
this session. The C struct is a plain data holder with no behaviour of its own, populated field-by-field by
`got_savefile()` in `src/ui-game.c`, and the Java class already mirrored that shape exactly: `fileName`/`description`/
`offset` line up one-to-one with `fnam`/
`desc`/`foff`, with empty strings standing in for the C struct's zero-allocated `NULL`s. No divergence was found, so the
pass moved straight to documentation and tests. The class and all six members now carry full Javadoc with the C
cross-reference, and `SavefileDetailsTest` covers the default zero-allocated state plus a round trip through every
setter/getter pair, including the
`foff`-as-prefix-length case the C comment calls out; the full project suite is green. The reference C source's stamping
step was blocked by a permission denial again this session, the same snag as 260914's `AngFile` pass, and still needs
doing by hand or with permissions adjusted.

### `GameConstantsParseResult` verified and documented

`GameConstantsParseResult` - the holder `GameConstantsReader.parseWithResults` returns, pairing the assembled game
constants with any parse errors - was checked this session. It has no single C counterpart to diverge from, so the pass
confirmed it faithfully carries the two outcomes the reader already produces: a populated result, or a null-data result
with the errors collected during assembly; no discrepancy turned up. Its Javadoc now carries the same dated provenance
stamps as the rest of today's Reader sweep, and a small dedicated test class pins its two-state contract independently
of the ANTLR reader pipeline. This closes out the one file the Reader Javadoc sweep had missed, leaving the package
internally consistent.

## Things not to drop

- `SavefileGetterImpl.gotSavefile` has no equivalent of C's SETGID-prefix filtering (`ui-game.c:1204-1209` sets up
  `uid_c`, `ui-game.c:1231-1234` skips any `fname` that doesn't start with it) - not a bug, since SETGID doesn't apply
  to this port, but the "only show this player's own savefiles" behaviour it provided has no Java replacement yet if a
  shared/multi-user save directory is still wanted.
