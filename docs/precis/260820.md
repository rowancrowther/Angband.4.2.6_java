# Precis — 2026-08-20

## Key points from the day

### The equipment walk needed a shape C gets for free

C's equipment loop rebinds one pointer — first to the slot's item, then to each curse's template object — so one loop
body serves both and a cursed item is simply examined more times. The port could not follow that, because a curse here
has no object of its own: the parser flattens it into named fields, and the first attempt iterated the curses only,
which meant an uncursed item contributed nothing at all and a cursed one had its own values applied once per curse. A
`BonusSource` interface restored the single variable, with an item implementation and a curse implementation the body
reads without knowing which it has. The abstraction is port-only and worth remembering as such — the curse side answers
several questions with flat constants, and every one of those constants is C's behaviour rather than a shortcut.

### The combat bonuses were three separate faults wearing one coat

Base armour and the armour enchantment are different quantities in C, added under different conditions, and the port had
merged them into one line that counted the enchantment twice and left the armour at zero. Speed had landed in
infravision, and the berserk-strength block was missing entirely. All three are now line-for-line against the original,
and the base armour has somewhere to live on both the item and the state. The lesson is the merge itself: two adjacent
lines that look like a duplicate are worth reading twice before one is deleted.

### The food constants and the food grades were on two different scales

The nourishment thresholds are not constants in C at all — they are filled in at parse time from the data file's grades,
each multiplied by a scale the constants file sets — and the port had a stub enum of invented numbers on one side and
unscaled grades on the other. Every food calculation in `calcBonuses` divides by one of those ranges, so the arithmetic
was wrong by two orders of magnitude in both directions. The enum now holds the real products and the assembler applies
the scale, gated on the food effect so the stun bands are not inflated with it. That gate matters more than it looks:
scaling everything would have stopped the stun penalties applying at all, silently.

### The grade parser gained the validation C has and the port had dropped

C checks every grade line twice over — the maximum must be positive, must still fit the counter's type after scaling,
and must sit strictly above the grade before it — and rejects the whole record when any of that fails. The port had none
of it, then briefly had a ceiling pointing the wrong way, which would have admitted values a hundred times larger than
the original allows. Both checks now run for every effect with the scale folded in, and a bad grade drops its record
rather than leaving a hole in the band ladder. Worth carrying forward that the ceiling exists because the counter is
sixteen bits in C, not because anyone chose the number.

### A verification pass that actually compiled found what reading had not

The chain was walked twice by eye and reported clean both times; running the build found the equipment loop referring to
a local that no longer existed, and a later pass found the carrying limit had lost its table lookup and would divide by
zero for a weak character. Neither was visible in a careful read of the diff, and the second had been introduced by a
tidy-up that looked like an improvement. Compiling and running is now part of what "verified" means for this chain. The
habit to keep is the cheap one: build before reporting, every time.

### Twenty-four files got their Javadoc, and three of them were wrong rather than missing

A hundred and sixty-three members across the calculation chain had no documentation, including the three new
bonus-source types which had none at all. Three existing comments described the opposite of what the code did — a
class's armour allowance called a spellbook weight, an equipment slot's acid column read as protection when it means
vulnerability, and a stub banner left behind on an enum that had since been fixed. All are corrected, and the new blocks
carry the reasons rather than the restatements, so the port-only decisions can be read from the code. The blocks that
explain why a curse answers with constants are the ones most likely to save someone from "fixing" them.

### The test suite was order-dependent and quietly so

Constructing a player reads the registries for a body and a race, so eight test classes passed as part of the whole
run — some reader had loaded the real data first — and failed when run alone. That is a false green: the result depended
on execution order, and anyone running one class from the IDE saw a failure that had nothing to do with their change. A
shared extension now supplies the four pieces of registry state a player needs, seeding only what is absent and clearing
only what it seeded. All eight now stand alone, and the extension defers to real data when the full suite runs.

### A hundred and one new tests, and a fixture for the hardest function to test

Twelve new classes cover the bonus sources, the player state, the grade scaling and validation, the skill-scaling
rounding rule, the curse weight arithmetic, the flattened spell index and four enums whose order is behaviour rather
than presentation. The thirteenth is the interesting one: `calcBonuses` derives everything at once from six sources, so
a test asking what a ring gives had to supply all six and have five contribute nothing. The fixture builds exactly
that — an empty race, an empty class, neutral stats — and its tests assert differences rather than totals, which keeps
them from breaking every time an unrelated source is touched. It is the piece that makes the rest of the chain testable
at all.

### The hit point calculation came down to one comparison

`calcHitpoints` is a short function and read as correct on the first pass, with the maximum built from the fixed hit
dice and a constitution bonus in hundredths of a point per level. The one divergence from the original was the clamp on
the current total, which compared with `>` where C compares with `>=` — so a character landing exactly on a reduced
maximum kept its sub-hitpoint regeneration credit instead of losing it. That is now `>=`, and the method is documented
with the two guards spelled out: the outer one on the maximum having actually moved, the inner one on why equality still
clears the fraction. Both are the kind of thing a later tidy-up would collapse, so the reasons are in the code rather
than in a review comment.

### The new tests are aimed at the edges rather than the happy path

Nine tests now cover the function directly, in three groups: the maximum itself, the clamp on the current total, and the
guard on the maximum having changed. The bonus scaling is asserted at two different levels so a division in the wrong
place cannot pass, the negative case pins truncation toward zero rather than flooring, and the equality case is a test
of its own because it is invisible in play. The character is assembled by reflection, as the fixture already does, since
levelling and character creation do not exist to build one properly. The class passes on its own and stands as the
record of what the two guards are for.

### The state comparison needed a copy C gets from its language

`updateBonuses` recalculates the character and then sets the result beside the old one to see what moved, and C takes
that "before" picture by assigning one struct to another — a copy of every byte. The port had transcribed the line
directly, which in Java binds a second name to the same object, so the recalculation wrote through into the field being
compared against and every comparison tested an object against itself. A `copy` method on `PlayerState` now makes the
assignment mean what it means in C, and the whole notice-changes half works for the first time. The lesson generalises
past this method: a C line that copies by value is never a plain assignment here, and the failure is silent rather than
loud.

### Six transcription slips sat behind the one structural fault

Once the copy was real, the comparisons underneath it could be read properly, and six of them were wrong: a missing
negation on the partial-update guard, a heavy-weapon branch testing the bow, and two comparisons reading the wrong pair
of states. None would have shown up while the aliasing kept the whole block dormant. All six are now line-for-line
against the original, including the two deliberate asymmetries — armour compares what the character believes, light
compares what is true. Worth carrying forward that one structural fault can hide a crowd of small ones, and fixing it
makes the rest visible rather than finishing the job.

### A zeroed state had to be genuinely zeroed

The player's two state fields start as null and its maps start empty, where C's are struct members that exist and read
as zero from the moment the character does. The first call therefore had two ways to fail — a null on the copy, and an
unboxing failure on the first stat read behind it — neither reachable until the comparison block started working. The
fields are now filled on first use and the reset refills every stat map, matching what C's `memset` leaves behind. The
port's maps will keep needing this wherever C subscripts a fixed array, so it is the pattern rather than the instance.

### Thirteen tests aimed at a fault that raises no error

The failure an alias produces is silence: no flags raised, nothing thrown, and the first symptom a stale number on
screen somewhere else entirely. Ten tests now change exactly one thing between two calculations and assert the flag that
should follow, so each one fails under an alias and passes under a real copy, and three more cover the first call on a
character that has never been calculated. Copying and resetting are pinned separately, including independence in both
directions and the movement count staying distinct from the blow count. The suite cannot prove the alias case without
mutating production code, so the coupling is by argument rather than demonstration — worth knowing when reading them.

**Suite: 2367 tests, 0 failures. Build green.**

## Things not to drop

- `Food.java`'s comment block was replaced without being read first, so whatever was written there earlier in the day is
  gone; the code is untouched but the prose is worth checking before it is committed.
- `docs/Workpoints_CalcBonuses.md` still presents all nine work points as open when every one of them is closed.
- `PlayerState` has no getters for the three combat totals, so two tests reach the fields reflectively rather than have
  production accessors added for a test's benefit.
- `ItemObject` capitalises the armour-class family where `PlayerState` does not, so one line of the equipment loop
  carries three spellings of the same idea.
- The test support reaches private fields on the player, the equipment slot and both registries, because character
  creation and the wield command do not exist yet; a field rename will break tests rather than compilation.
- `calcMana`, `calcBlows`, `calcLight` and `calcShapechange` are exercised only through `calcBonuses`, never directly.
- The port's grade list still has no equivalent of C's implicit zero grade, so grade numbers run one lower throughout.
- `PlayerUtils.search` and the resting helpers remain declared stubs, as do the registry setters and most of the game
  world, none of which has tests.
- The only getter in `PlayerState` without a `get` prefix is the percentage damage reduction.
- `PlayerUpkeep.getRedrawFlags` returns a snapshot rather than the live set, so clearing has to go through
  `clearRedrawFlags`; wiping what the getter returns clears nothing and reads as a passing test.
- `PlayerUpkeep` exposes no reader for the update flags and no setter for partial mode, so the new tests reach both
  reflectively.
- The alias case is covered by argument rather than by a mutation run, since demonstrating it would mean breaking
  production code on purpose.
