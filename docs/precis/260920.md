## Create path — what `hatch_embryo` adds to Friday's pseudocode

Friday's precis (`docs/precis/260918.md:320-356`) gives the create path as a single loop over `i in 0..n-1`. That's the
right *shape*, but it's a synthesis — the actual C is split across two functions that fire at different times, and it
has three behaviours the pseudocode doesn't carry.

### 1. What decides create vs. override, and a case the pseudocode skips

The lookup-and-decide lives in `parse_entry_name` (`ui-entry.c:1882-1943`), which fires on every `name:` line — not once
per record. Before it builds the new/existing embryo, though:

```c
if (embryo) {
    if (streq(name, embryo->entry->name)) {
        /*
         * Strange case since the last record is the same as
         * this one.  Simply proceeed to modify the previous
         * record without a warning.
         */
        return PARSE_ERROR_NONE;
    }
    if (hatch_embryo(embryo)) { ... }
}
```

(`ui-entry.c:1888-1901`)

A `name:` line that repeats the *immediately preceding* name is neither create nor override in the Q2 sense — it's
silently folded into the embryo already open, no lookup, no hatch. Only when the name differs does the current embryo
get hatched (committed) and a fresh lookup happen. This case isn't in the results-list model in Friday's pseudocode
because that model assumes one grammar record per name; the shipped data may never trigger it (worth checking
`ui_entry.txt`/`ui_entry_base.txt` for back-to-back duplicate `name:` lines the way the override path was checked), but
the *rule* — same name as the open embryo skips the lookup entirely — is real and untested.

### 2. Hatching is deferred, and the fan-out has a reuse trick

`hatch_embryo` (`ui-entry.c:1756-1863`) is called when the *next* `name:` line arrives (or at EOF, via
`hatch_last_embryo`) — not inline as each field is parsed. Its fan-out loop:

```c
n = (*name_parameters[embryo->param_index].count_func)();
for (i = 0; i < n - 1; ++i) {
    struct ui_entry *entry = mem_alloc(sizeof(*entry));
    /* ... build entry for index i, ui_entry_insert(entry) ... */
}
/* index n-1 reuses embryo->entry itself, mutated in place, then inserted */
parameterize_category_list(embryo->categories, embryo->entry->n_category, n - 1, embryo->entry);
ui_entry_insert(embryo->entry);
```

(`ui-entry.c:1772-1859`)

only allocates `n-1` fresh `struct ui_entry`s; the last parameter index reuses the struct already sitting in the embryo
instead of allocating a new one. That's a C allocation-count optimisation with no Java equivalent worth porting —
`UIEntryEmbryo.java:29` already just holds a `UIEntry uiEntry`, and GC doesn't care how many objects get built. Flagging
it only so a side-by-side read of `hatch_embryo` doesn't look like it's doing something structurally different from the
`for i in 0..n-1` pseudocode — it produces the same `n` entries with the same field values, just via an asymmetric loop.

### 3. The category struct being fanned out

```c
struct embryonic_category_reference {
    const char *name;
    int psource_index;
    int priority;
    bool priority_set;
};
```

(`ui-entry.c:163-168`)

`parameterize_category_list` (`ui-entry.c:1657-1680`) is the per-entry resolution step inside the fan-out — for each
embryonic category, if `priority_set`, resolve `psource_index > 0 ? scheme(ind) : literal priority`; otherwise
`(0, false)`. This is exactly Q2's "test `prioritySet` first" rule from the precis (line 354), now traced to its source
function. Your `EmbryonicCategoryReferencies.java:23-51` already has all four fields (`category`, `pSourceIndex`,
`priority`, `prioritySet`) — checked just now, field-for-field match.

### One naming collision the precis flagged that's already resolved in Java

C reuses the name `param_index` for two different things: `embryo->param_index` (which parameterization table —
dummy/element/stat, set by `parse_entry_parameter`, `ui-entry.c:2005-2007`) and `entry->param_index` (which index
*within* that table this specific fanned-out entry is, set per loop iteration). Checked `UIEntry.java:417` and
`UIEntryEmbryo.java:31,36` just now — Java already spells these differently (`paramIndex` on `UIEntry` as `int`,
`parmIndex` on `UIEntryEmbryo` typed as the `UIEntryNameParameter` enum), so the ambiguity C has doesn't carry over.
Worth knowing it was a live trap in the original, not worth changing anything.

## Create path, full algorithm (deferred-hatch model)

Friday's pseudocode (`docs/precis/260918.md:320-356`) treats the create path as "one record → one fan-out, immediately."
The real control flow defers the fan-out to when the *next* `name:` line (or EOF) arrives, and that gap is where the
extra behaviour lives. This version replaces the flat loop with the actual two-phase shape: line handlers mutate an open
embryo, then `hatch()` commits it.

### State and triggers

```
embryo : EmbryonicUIEntry | null      # what "the currently open record" means
```

- `name:` line handler — `parse_entry_name`, `ui-entry.c:1882-1943`
- everything else (`template:`, `parameter:`, `category:`, `priority:`, `renderer:`, `combiner:`, `label*:`) — mutates
  the open `embryo` directly, one field-setter per line, same as Friday's write-up. Not re-derived here.
- hatch call sites — `parse_entry_name` when a *differing* name arrives (`ui-entry.c:1897`), and `hatch_last_embryo` at
  EOF (`ui-entry.c:1866-1879`).

### Algorithm

```
on "name:" line with value `name`:
    if embryo != null:
        if name == embryo.entry.name:                       # ui-entry.c:1889-1895, the "strange case"
            return                                           # NO lookup, NO hatch — keep editing the SAME open embryo
        hatch(embryo)                                        # commits whatever was open before starting the new one

    ind = lookup(name)                                       # ui-entry.c:1907 — search the COMMITTED entries[], never the open embryo
    if ind > 0:
        embryo = { entry: entries[ind-1], exists: true }      # ---- OVERRIDE ----  ui-entry.c:1908-1914
    else:
        embryo = { entry: blank UIEntry(name=name), exists: false }   # ---- CREATE ----  ui-entry.c:1915-1935

    embryo.categories = []                                    # fresh embryonic category list every record, regardless of exists
    embryo.paramTableIndex = DUMMY                             # ui-entry.c:1938 — which of {dummy, element, stat} count/name tables
    embryo.prioritySourceIndex = NONE                           # ui-entry.c:1939
    embryo.lastCategoryIndex = -1                                # ui-entry.c:1940

# ... template:/parameter:/category:/priority:/renderer:/combiner:/label*: lines run here, unchanged from Friday's account ...

hatch(embryo):                                                  # ui-entry.c:1756-1863
    if embryo.exists:
        return                                                  # OVERRIDE: fields already mutated in place on the committed entry, nothing to commit
    # ---- CREATE PATH proper — everything below only runs for a genuinely new name ----
    if embryo.entry.combinerIndex == 0:
        FATAL, abort load                                        # ui-entry.c:1763-1769 — checked HERE, at hatch time, against the fully-accumulated embryo
        return

    n = paramCount(embryo.paramTableIndex)                       # 1 / ELEM_MAX / STAT_MAX — ui-entry.c:1772
    for i in 0 .. n-2:                                            # every index EXCEPT the last; empty loop when n == 1
        paramName = paramName(embryo.paramTableIndex, i)
        entry = blank UIEntry
        entry.name           = embryo.entry.name + "<" + paramName + ">"
        entry.defaultPriority = (embryo.prioritySourceIndex != NONE)
                                   ? scheme[embryo.prioritySourceIndex](i)
                                   : embryo.entry.defaultPriority
        entry.categories      = parameterizeCategories(embryo.categories, i)
        entry.label           = nonEmpty(embryo.entry.label) ? embryo.entry.label : paramName
        entry.shortenedLabels = copyOf(embryo.entry.shortenedLabels)   # ui-entry.c:1812 — same 10 slots on every fanned-out entry, unresolved (no fill-forward yet)
        entry.renderer        = embryo.entry.renderer
        entry.combiner        = embryo.entry.combiner
        entry.paramIndex      = i
        entry.flags           = embryo.entry.flags
        insert(entry)                                             # sorted insert, duplicate name -> FATAL

    # last index (n-1): C reuses embryo.entry itself rather than allocating — a pure
    # memory-reuse detail (irrelevant under GC), but produces the SAME entry the loop
    # body above would have for i = n-1, with one extra rule:
    if n == 1:
        embryo.entry.paramIndex = -1                              # unparameterized: -1, never 0
    else:
        paramName = paramName(embryo.paramTableIndex, n-1)
        embryo.entry.name  = embryo.entry.name + "<" + paramName + ">"
        embryo.entry.label = nonEmpty(embryo.entry.label) ? embryo.entry.label : paramName
        embryo.entry.paramIndex = n-1
        if embryo.prioritySourceIndex != NONE:
            embryo.entry.defaultPriority = scheme[embryo.prioritySourceIndex](n-1)
    embryo.entry.categories = parameterizeCategories(embryo.categories, n-1)
    insert(embryo.entry)

parameterizeCategories(embryonicCategories, i):                    # ui-entry.c:1657-1680, pure function of (list, index)
    result = []
    for c in embryonicCategories:
        if c.prioritySet:                                          # TEST prioritySet BEFORE looking at psourceIndex
            priority = (c.psourceIndex > 0) ? scheme[c.psourceIndex](i) : c.priority
            result.add(Category(c.name, priority, prioritySet = true))
        else:
            result.add(Category(c.name, priority = 0, prioritySet = false))
    return result

# ---- FINISH PASS, after both files, unchanged from Friday's write-up ----
for each entry in results:
    if label empty -> label = name
    fillOutShortened(entry)
    for each category with !prioritySet -> priority = entry.defaultPriority, prioritySet = true
```

### Where this diverges from Friday's flat model

- **Hatch is deferred, not immediate.** The FATAL combiner check, the fan-out, and the insert all happen when the *next
  differing* `name:` arrives or at EOF — not the instant a record's fields finish parsing. For the port this mostly
  collapses back to "per record" if the assembler still processes one grammar record at a time, but it matters for the
  one case below.
- **Same-name-repeat short-circuits the whole record cycle.** `name: X` immediately followed by another `name: X` does
  no lookup and no hatch — it keeps editing the same open embryo as if the second `name:` line hadn't introduced a new
  record at all. This has no representation in the current `results`/lookup model at all; it would need checking whether
  the port's grammar can even produce two `name:` lines with no other line between them, or whether ANTLR's
  block-per-record structure makes this unreachable by construction (which would make it as dead as the override path,
  just for a structural reason rather than a data reason).
- **The n-1/reuse split is not two different behaviours** — every fanned-out entry, including the last, gets the
  identical treatment; C just avoids one allocation for the last one. Safe to port as a single uniform loop over
  `0..n-1`.
- **`parameterizeCategories` is a clean, separable pure function** —
  `(embryonic category list, index) -> resolved category list` — good candidate for its own method in the port rather
  than inlining the `prioritySet`-first test twice (once in the loop, once for the reused last entry, as C effectively
  does).

## Correction: the create path is not the common case

- Friday's precis claims the override path is dead on shipped data (`260918.md:370-372`), on the grounds that no `name:`
  value repeats in either file.

- That test was the wrong one. `lib/gamedata/ui_entry.txt:101-164` names thirteen entries —
  `resist_ui_compact_0<ACID>` through `<DISEN>` — that were created by the fan-out of `ui_entry.txt:85`, so
  `lookupByName` finds them and every one takes the override branch.

- Those thirteen records carry only `label:`/`label2:`/`label5:` and `category:` lines — no `combine:`. Routing them
  through the create path hits the `e.combine == NONE` FATAL at `ui-entry.c:1763` and aborts the load.

## Template application is positional, not a preamble

- Friday's pseudocode hoists `if r has a template:` above the field-setting block (`260918.md:323-329`), which reads as
  "templates apply first".

- C runs `parse_entry_template` in file order like any other handler, and it *replaces* renderer, combine,
  defaultPriority and flags — so a `renderer:` line before `template:` is silently discarded.

- Shipped data never exercises it: `template:` is the line immediately after `name:` in all 33 records that use one, and
  no record mixes `template:` with its own `renderer:`/`combine:`.

## lastCat must be a reference, not an index

- C stores `last_category_index`, a position in a list kept sorted by name (`ui-entry.c:2128`), and a later `category:`
  line can insert *before* it.

- The shipped data never catches this out — every record with a `priority:` places it before any `category:` — but the
  index is only safe because a `priority:` directive always immediately follows the `category:` it binds to.

- Holding the category object rather than its index removes the hazard for free, which is why the block above does.

## The psource captured at category-insert time is dead

- `parse_entry_category` passes the running `embryo->psource_index` into each new category (`ui-entry.c:2125`) with
  `priority_set = false`.

- `parameterize_category_list` only ever reads a category's psource inside the `priority_set` branch
  (`ui-entry.c:1669-1673`), and the only writer of `priority_set = true` (`ui-entry.c:2179-2181`) overwrites the psource
  on the same line.

- So that captured value can never be read; the field is only load-bearing when the `priority:` path sets it. It costs
  nothing to keep for shape-fidelity, but nothing depends on it.

## Two smaller things the flat loop hides

- `paramTable.name(i)` for DUMMY returns `""` (`ui-entry.c:1572-1576`), so the unparameterized case needs its name and
  label left alone rather than suffixed with `<>` — C gets this by branching on `param_index == 0` at
  `ui-entry.c:1827`.

- `get_element_count` is `N_ELEMENTS(element_names)`, a dense 0-based table indexed from 0 in the fan-out
  (`ui-entry.c:1588-1599,1775`).
