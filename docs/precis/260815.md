## 1. The double `updateObjectKnowledge()` — removed from `learnBrand`

**The question.** `Player.learnBrand` called `learnRune(rune, true)` and then
`updateObjectKnowledge()`, but `updateObjectKnowledge()` is already the last thing `learnRune`
does. Is the second call load-bearing?

**No — and it is dead in this wrapper specifically.** C's `player_learn_brand`
(`obj-knowledge.c:1407`) does have the second call, so the port was faithful, but it cannot fire usefully:

- the wrapper is guarded on `!knowsBrand(brand)`;
- knowledge of a brand and knowledge of its rune move together, because `KnownObject.learnBrand`
  marks every same-named brand at once (yesterday's fan-out fix);
- so on the one path that reaches `learnRune`, `learned` is necessarily true, `learnRune` gets past
  `if (!learned) return;`, and its own update runs.

`player_learn_slay` (`obj-knowledge.c:1384`) has exactly the same shape.

**Where the pattern comes from.** `player_learn_flag` (`obj-knowledge.c:1375`) has **no** guard:

```c
void player_learn_flag(struct player *p, int flag)
{
	player_learn_rune(p, rune_index(RUNE_VAR_FLAG, flag), true);
	update_player_object_knowledge(p);
}
```

If the flag was already known, `of_on` returns false, `player_learn_rune` bails early, and the trailing call is the only
one that runs. That is the one wrapper where it is reachable — and even there it achieves nothing, because
`player_know_object` recomputes identical values and the two
`event_signal`s just redraw. It is boilerplate that was defensible in one place and copy-pasted into the guarded ones.

**Why the deletion went in the wrapper, not in `learnRune`.** Counting C's call sites, most callers of
`player_learn_rune` have no update of their own and depend entirely on the one inside it:
`object_learn_unknown_rune`, `object_learn_on_wield`, `missile_learn_on_ranged_attack`, the three
`equip_learn_on_*` functions, the whole `object_curses_find_*` family, and `player_learn_all_runes`. Only four wrappers
plus `player_learn_innate` and `object_learn_on_use` add a second.

So the invariant that actually holds is **"`learnRune` leaves knowledge propagated"**, and the wrapper calls are the
redundant layer on top. Stripping it from `learnRune` would mean adding it to a dozen-plus sites not yet ported, and
every miss would be a silent bug — stale known-objects, no inventory redraw — rather than a compile error. Deleting
`Player.java:1065` is local, provably a no-op, and trivially reversible.

**Cost of the redundancy, for the record:** one extra sweep of four populations (level objects, gear, all store stock,
curse objects) plus a duplicate `EVENT_INVENTORY` / `EVENT_EQUIPMENT`. All idempotent, which is why upstream never
noticed. Currently free either way — the Java
`updateObjectKnowledge()` is still a stub.

**Amends yesterday.** The 260814 precis (§4, item 2) lists the second call as "C's redundancy, faithfully reproduced".
That is no longer the port's behaviour for brands.

## 2. Why `learnRune` should be package-private, not `private`

`player_learn_rune` is the **one** learning function absent from `obj-knowledge.h` — file-`static`, so nothing outside
that translation unit can call it, and nothing does.

All 17 exported entry points take `struct player *p` first (`player_learn_flag`, `object_learn_on_wield`,
`equip_learn_on_melee_attack`, `missile_learn_on_ranged_attack`, …). In Java that is `player.learnFlag(flag)`,
`player.learnOnWield(item)` — every wrapper lands in `middle.player` beside `learnRune` itself, and the
`object_curses_find_*` family (already `static` in C) becomes private helpers. Outside callers hit the public wrappers.
So nothing outside the package needs it, today or later.

**Package-private, not `private`, and the reason is tests.** `PlayerRuneLearningTest` is
`package uk.co.jackoftrades.middle.player` and drives `learnRune` directly to exercise each of the seven variety arms in
isolation. `private` would cost those; package-private still gives what C's `static` gives — the compiler refuses any
caller that skips a wrapper.

**The one thing that would break it** is writing a future wrapper on the object side — `item.learnOnWield(player)` in
`middle.objects` instead of `player.learnOnWield(item)`. Reads naturally in Java, and would force `learnRune` back to
public. Resist it: knowledge is player state (`p->obj_k`), the item is only the thing being read, and C's argument order
says the same.

## 3. `knowsRune` — a switch expression whose arm produced no value

The port of `player_knows_rune` failed to compile:

```
Player.java:1102: error: switch rule completes without providing a value
  (switch rules in switch expressions must either provide a value or throw)
```

`return switch(rune.getVariety()) {...}` is a switch **expression**, so every arm must produce a `boolean`. Six arms
did, their bodies being expressions. The `CombatKey` arm's body was a block containing a nested switch **statement**: it
dispatched on `key`, evaluated `itemKnowledge.toAIsKnown()` and threw the result away, then fell off the end of the
block with nothing yielded. The `yield false` in the `COMBAT_RUNE_MAX` arm belonged to the inner switch, so it could not
rescue the outer one.

Contrast `learnRune`, where the same nested shape is fine — that one is a switch *statement* whose arms assign to
`learned`, and nothing is required to produce a value.

Fixed by making the inner switch *be* the arm's value (an arrow arm takes any expression, and a switch expression is
one — the block braces were what discarded it). Also dropped the `default`: with a sealed `RuneVariety` and all seven
record patterns present it was unreachable, and it switched **off** the exhaustiveness check that yesterday's
sealed-interface set piece was bought for — an eighth variety would have been swallowed and answered `false`.

## 4. What `power` means on a curse — two fields, one struct

`player_knows_curse` reads `p->obj_k->curses[index].power == 1`, which reads oddly until you notice `power` means
different things in the two `curse_data` arrays.

**On a real object it is severity.** `apply_curse` (`obj-make.c:889`) rolls `randint1(9) + 10 * m_bonus(9, lev)` —
roughly 1–99, worse the deeper the item. Used as a quantity:

- **removal difficulty** — `uncurse_object` succeeds only if `strength >= curse.power`
  (`effect-handler-general.c:191`); below that the item turns `OF_FRAGILE`, and a second failure has a 1-in-4 chance of
  destroying it;
- **`>= 100` means permanent** (`:188`) — early return, unremovable at any strength; that is the sentinel behind
  `ui-curse.c:106`'s `< 100`;
- **valuation** — `obj-power.c:775` subtracts `power / 10`;
- **stacking** — `append_object_curse` (`obj-curse.c:200`) keeps the higher power.

**On `p->obj_k` it is a boolean in an int's clothes.** It exists only because C types `p->obj_k` as a whole
`struct object`. `player_learn_rune` writes a literal `1` (`obj-knowledge.c:1344`); `save.c:661` writes
`power ? 1 : 0`; `timeout` is never touched at all. Same pattern as `modifiers[]` and `el_info[].res_level` from 260814,
so `Map<Curse, Boolean>` loses nothing and `curseIsKnown` needs no `== 1`.

**Where they meet** — `player_know_object`, `obj-knowledge.c:1131`:

```c
if (p->obj_k->curses[i].power && obj->curses[i].power) {
    obj->known->curses[i].power = obj->curses[i].power;
```

The knowledge 0/1 **gates** whether the real severity is copied to the known object. So `obj->known->curses[i].power` is
a severity again — recognised curses show their true strength, unrecognised ones read as 0, which is why the removal
menu can only offer what has been learned. Worth having in view before implementing `updateObjectKnowledge`.

The split is already clean in the port: severity in `CurseData` (power + timeout, `setPower(0)` as removal), recognition
in `KnownObject`. C only conflates them because both sit in the same struct.

## 5. Accuracy review: `learnFlag`, `learnSlay`, `learnInnate`

**`learnSlay` — accurate.** Guard matches; `Rune.runeIndex(slay)` (`Rune.java:375`) matches on `sameMonsterSlain`, which
is C's `same_monsters_slain` (`obj-slays.c:40`: race flag first, then base, null-base cases handled) and *not* a name
match. Dropped trailing update is dead for the `learnBrand` reason.

**`learnFlag` — accurate.** Checked the one live caller, `player_learn_flag(player, OF_FRAGILE)`
(`effect-handler-general.c:203`): `object_property.txt:615` gives FRAGILE `subtype:bad`, and `init_rune` only skips
`OFT_NONE/LIGHT/DIG/THROW/CURSE_ONLY`, so it does have a rune and the lookup resolves. `KnownObject.learnFlag` →
`Flag.on` returns "was this new", exactly as `of_on` does.

Two divergences, both deliberate and now in the Javadoc:

- An **already-known guard was added**, which C does not have. Changes no answer (same test one call deeper), buys
  consistency with the siblings, and makes C's trailing update unreachable — which mattered only in that this was the
  single wrapper where it could have been the call that ran. This closes the second of yesterday's two new Outstanding
  items.
- `Rune.runeIndex(flag)` can answer `null` for the skipped subtypes; `learnRune` logs and returns. C hands
  `rune_index`'s `-1` straight to `rune_list[-1]`. **The port is safer, not merely different** — and the same is true
  for elements above `ELEM_HIGH_MAX` in `learnInnate`.

**`learnInnate` — one real divergence, found and fixed.** C is `p->race->el_info[element].res_level != 0`.
`PlayerRace.getResistKnowledge` was `resists.get(element) != null` — presence of a map entry, not a non-zero value.

The port's map is **sparse**: `PlayerRaceAssembler.java:237` creates an entry only for a `RES_` line actually present in
the data, where C reads a full `el_info[ELEM_MAX]` array in which an unmentioned element is simply zero. Checked
`p_race.txt`: the only entries in the shipped game are `RES_LIGHT[1]` (Elf, High-Elf), `RES_DARK[1]` (Half-Orc),
`RES_POIS[1]` (Kobold) — no zeros, no negatives — so this was latent, not live. `values:RES_ACID[0]` in a modded race
file would have made Java learn a rune C does not.

The first fix, `resists.get(element).getResLevel() != 0`, was the right *test* but **NPE'd on the sparse map** — Human's
map is empty, so `learnInnate` would have thrown on the very first element. Settled on the single-lookup null check:

```java
ElementInfo info = resists.get(element);
return (info != null && info.getResLevel() != 0);
```

Preferred over `containsKey(element) && get(element)...`: one hash probe instead of two, and the absent case stated
once. (They are only interchangeable because the assembler's `computeIfAbsent` never inserts a null value.)

**Non-zero, not positive** is the point worth keeping: a vulnerability is as learnable as a resistance, because the rune
names the element, not the sign.

The rest of `learnInnate` is sound — `ELEM_NONE`/`ELEM_MAX` skips (C has no former and excludes the latter by loop
bound), `message = false` on both loops, walking all of `ObjectFlag` where C's `of_next` walks only set bits (same set,
more iterations), and the dropped trailing update (no guard here, but each `learnRune` that learned has already updated,
and if the race knows nothing innately C's call recomputes an unchanged state).

## 6. What `curse->obj` is, and why it is not a `KnownObject`

`struct curse` has two members that both look portable as collections, and they are not the same thing:

```c
struct curse {          /* object.h:114 */
	bool *poss;         /* per object-kind: may this kind carry the curse? */
	struct object *obj; /* the curse's own properties, as a template object */
	...
};
```

`poss` is the one that ports to a list — `Curse.objectBases`. `obj` is a **value carrier**, and every field in it is
read as a quantity: `obj-util.c:303/322/341` sum `curses[i].obj->to_h / to_d / to_a` into the player's totals,
`obj-knowledge.c:1697` reads `modifiers[j]`, `:1739` reads `el_info[elem].res_level`. The parser writes them as plain
ints (`obj-init.c:1089-1091`, `parser_getint` — not dice).

So it is the opposite of `p->obj_k`, which is booleans wearing an object's clothes and is why `KnownObject` could
replace it with twelve fields. **`Curse` has already made the right port**: `combatToHit`, `combatDam`, `combatAC`,
`weight`, `effect`, `objectFlags`, `modifiers`, `elInfo` are exactly the fields C writes into `curse->obj`. C only wraps
them in a `struct object` because that is the container its flag/modifier/element machinery already knew how to read;
there is no separate entity being modelled.

`combatAC` being an `int` where `ItemObject.toAC` is a `Random` is the port being *more* accurate than the C-shaped
alternative, and it is what lets `cursesFindToA` work today while `equipLearnOnDefend`'s other arm cannot (§8).

**Where a `KnownObject` does belong on a curse.** `curse->obj` has its own known counterpart —
`obj-init.c:188` allocates it, and `obj-knowledge.c:1237` runs `player_know_object(p, curses[i].obj)` as the fourth of
the populations `update_player_object_knowledge` sweeps. So a `Curse` may eventually need a `KnownObject` **field**. The
curse's properties are not a `KnownObject`; they are the thing a `KnownObject` is computed about.

## 7. `object_curses_find_to_a` — two arrays at one subscript

The function reads two things that live apart, and C's loop hides it:

```c
if (!obj->curses[i].power || !curses[i].obj)
    continue;
if (curses[i].obj->to_a != 0) { ... }
```

`obj->curses[i]` is the **instance** data (`struct curse_data`: power + timeout) and `curses[i]` is the global
**definition**. They are parallel arrays indexed alike, so the same `i` addresses both. `CurseEntry` pairs them
directly, which is why the port needs no index arithmetic and no `1 .. curse_max` bound.

**Both of C's guards are artefacts of the dense array.**

- `!obj->curses[i].power` is what stops an array with a slot for every curse in the game from reporting curses the item
  does not have. Against a map holding only the ones it does, it is unnecessary — **but the test is kept anyway**,
  because `CurseData.setPower(0)` is how a curse is removed, so a zeroed entry can outlive the curse.
- `!curses[i].obj` is dead code upstream. My first reading of it — a curse with no property lines gets a null `obj` —
  was wrong: `parse_curse_name` (`obj-init.c:1041`) allocates the object at the `name:` line, before any property line
  is seen, so a propertyless curse gets a *zeroed* object. The only null in the array is index 0, the reserved no-curse
  slot the loop already skips. `write_curse_kinds` (`:181`) walks the identical range and dereferences
  `curse->obj->kind`
  with no check at all, which settles it.

**The bug the port fixed by accident.** C declares `int index` outside the loop and reassigns it inside:

```c
player_learn_rune(p, index, true);        /* to_a rune */
index = rune_index(RUNE_VAR_CURSE, i);    /* clobbers it */
```

On a second qualifying curse the first call learns the *previous curse's* rune instead of to-AC. Harmless upstream only
because to-AC is already known by then. Resolving the rune once, before the loop, makes it unexpressible — there is a
test for it.

**The port's own bug, found and fixed.** The first version walked `ObjectRegistry.getCurses()` — every curse in the
game — and guarded with `containsKey(curse) && getPower() == 0`. That skips only the case where the item carries the
curse at zero power, so a curse the item does *not* carry fell straight through to the AC test. Any item with a single
curse would have taught the to-AC rune plus the curse rune of every to-AC curse in `curse.txt`. Now the loop is over the
item's own entries and the question cannot arise.

## 8. `equip_learn_on_defend` — three sources, one not yet answerable

A property announces itself when it does its job: a blow that lands less heavily than it should is the evidence that
something is adding to the armour class. That is why armour is learned by being hit rather than by being examined, and
why this is the family's entry point rather than anything to do with inspection.

Three sources, checked in order, first success ending the method — the leading guard and the one at the foot of the loop
are the same test, so the rune is not announced again from every remaining slot.

1. **the item's own bonus** — `isBoostedToA()`, **stubbed `false`**;
2. **the item's curses** — `cursesFindToA` (§7), live;
3. **the assumed shape** — `PlayerShape.getToAc()`, a flat parsed `int`, live.

**Why arm 1 cannot be written yet.** C's `obj->to_a` is an `int16_t` on the instance, rolled once when the object is
made. `ItemObject.toAC` is the `Random` parsed from the data file — the dice the roll would be made *from*. Neither
substitution works:

- `toAC != null` says only that the data declared the field. `ego_item.txt` writes literal zeros there
  (`combat:d10:d10:0` and seven of `combat:0:0:d10`), and `Random.parseStr("0")` returns a Random with base 0, not
  null — so a Weapon of Extra Attacks would teach the to-AC rune to anyone who took a blow while wearing it.
- rolling here answers a fresh question each call, where C asks what this item rolled when it was created.

The stub returns `false`, which is the safe direction: the method learns nothing from an item's own bonus rather than
learning from items that have none.

**Two smaller divergences, both settled.** C's `assert(obj->known)` is a debug sanity check that the known counterpart
exists, on its own line — folding it into the learning condition (the first version did) turns a loud failure into a
silent skip, so it is gone. And C's `if (obj)` around the whole loop body is real: `slot_object` answers NULL for an
unworn slot, which is most of them for most characters. The shape branch drops C's
`lookup_player_shape(p->shape->name)`, which re-fetches by name the definition `p->shape` already points at.

## 9. A review failure, and the rule it bought

Three turns running, the review said `equipLearnOnDefend` "still" dereferenced `slot.getItem()` without a null check
after you had already added the guard. Each of those turns re-read `ItemObject.java`, verified it properly, and then
appended a bullet about `Player.java` from memory. You changed correct code, re-checked it, and burned turns asking — on
a claim that was never verified.

The mechanism is worth naming because it is not carelessness about the file, it is carelessness about *when*: a finding
is a fact about the moment it was made, and it expires the moment you edit anything. The closing summary is where stale
findings leak in, because that is the part written across all the files rather than about the one just read.

Now `CLAUDE.md` rule **2a**: never state the current condition of a file not read in the current turn. "Still",
"remains", "hasn't been" are the tell — all claims about now, sourced from then. A verify turn re-reads every file it
reports on, not only the one under discussion; no closing "still outstanding" list unless each item was re-checked that
turn. It is checkable from the transcript: a "still" with no `Read` above it in the same turn is the bug. Also written
as the `no-stale-findings` memory, so it survives a cold start.

## 12. Notes for the day

Three pre-existing warnings sit on `learnRune`'s switch — "pattern variable `property` / `projection` never used" on the
`ModKey`, `ResistKey` and `FlagKey` arms. Not introduced today; they surface in diagnostics whenever the file is edited,
because the Javadoc edits shift their line numbers. `knowsRune` now has the same three, for the same reason.

A pattern worth naming, since it came up three times today: **C's redundancies and C's undefined behaviour look alike
from inside the port.** The double `updateObjectKnowledge` (§1), `rune_list[-1]` on a failed `rune_index` (§5), and
`power` doing two jobs in one struct (§4) are all places where the C is not a design to be reproduced but a consequence
of C not having somewhere better to put something. Deciding which is which needs the call sites, not just the function.

The afternoon added a fourth and a fifth of the same species, and a sharper version of the rule. `!curses[i].obj` (§7)
and `if (index >= 0)` on a curse rune both read as defensiveness and are both unreachable; C's `assert(obj->known)` (§8)
reads as a condition and is not one. The rule that separates them: **ask what the C data structure forced.** A dense
array indexed by every curse in the game forces a "does this item actually have it" test; a map keyed by the curse does
not. A struct with one `power` field per curse forces the 0/1 reuse; two classes do not. Where the port's data structure
has removed the constraint, the guard should go — and where it has not, the guard is load-bearing and the resemblance is
a coincidence.

The other lesson is §9's, and it is about process rather than C: the review's confident closing summary is the least
trustworthy part of it.
