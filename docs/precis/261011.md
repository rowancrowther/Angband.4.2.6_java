# Precis — 2026-10-11

## Key points from the day

### `MonsterRace.java` re-checked against `struct monster_race` in `monster.h`, `lookup_monster` in `mon-util.c` and the friend and shape conversion in `finish_parse_monster` in `mon-init.c`, with the lore loading left aside

`MonsterRace` is the Java copy of one `monster.txt` record and the shared template behind every live monster, with the two second-pass methods that turn friend and shape names into races and bases. The accessors, both resolvers and the plain-assignment setters all still match C, but the `lore` field, `setLore` and `getLore` blocks said no production code ever attaches a lore record, when the lore-file reader does so for each race it names. Those three blocks now say that the lore-file reader is the only caller and that the race loader gives no race a record, which is the one place C's `finish_parse_monster` differs. `MonsterRaceResolutionTest`, `MonsterRaceLookupAgreementTest` and `MonsterRacePopulationAndLoreTest` already pin the resolvers, the lookup rules, the population setters and the lore reference, so the chapter 6 generation code can rely on `MonsterRace` as it stands.

## Things not to drop

- `MonsterSpell.java`: `RSF_ACID` to `RSF_MANA` (19 breath entries) duplicate `RSF_BR_ACID` to `RSF_BR_MANA` and have no counterpart in `list-mon-spells.h`, so the enum has 112 constants where C has 93 plus `NONE` and `MAX`, and every later ordinal differs from C's.
- `MonsterAssembler.java`: `hearing` is stored as written in `monster.txt`, where C's `parse_monster_hearing` multiplies it by `z_info->max_sight / 20`; the two agree only while `max_sight` is 20.
- `MonsterAssembler.java`: the friends, friends-base, drops, mimic and shape lists are built in file order where C builds them in reverse, which matters once `place_friends` and the drop code consume random numbers as they walk them.
