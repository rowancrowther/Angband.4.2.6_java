# Precis — 2026-08-15

## Key points from the day

### Combat bonuses retyped on `ItemObject`

C keeps to-hit, to-damage and to-AC as dice on the *kind* but as rolled integers on the *instance*, and the port was
holding the dice on the instance. That made it impossible to ask "does this item have a bonus", which blocked the first
arm of every `equip_learn_*` function, and it quietly broke stacking — `similar()` was comparing two parsed `Random`
objects by reference, so two identically enchanted swords refused to stack. The three fields were retyped to `int`,
deleting three stubs rather than implementing them. Everything downstream now reads a settled number, and the same fix
will serve the ego and artifact paths when they land.

### The `equip_learn_*` family, three more members

`on_ranged_attack`, `on_melee_attack` and `flag` all walk the worn equipment looking for a property that has just given
itself away. They needed four new pieces of `ItemObject` beneath them and one genuinely subtle predicate,
`hasStandardToH`, because body armour carries a to-hit penalty as standard equipment and a naive non-zero test would
teach the rune to anyone wearing chain mail. All three are ported with their curse-finding helpers. Only `element` and
`after_time` remain, and both follow patterns now established.

### The curse-finding family moved to `Player`

`object_curses_find_*` reads item state, so the port put it on `ItemObject` — which forced
`learnRune` public and lost the compiler's guarantee that nothing reaches past a learning wrapper. The tell was that all
six are `static` in the same C file as `player_learn_rune`: they are player-side helpers that take an object, not object
methods. All four moved to `Player` as package-private with their arguments turned round. The rule generalises — **C's
file boundary is this port's package boundary** — and it decides where the two remaining siblings go.

### Two process failures, both about time rather than files

Findings were reported as current after you had already fixed them: three times in chat, then twice written into
permanent Javadoc as `Outstanding` paragraphs. The second is the worse one, because a wrong claim in chat costs a line
to correct while a wrong comment gets committed and misleads every later reader. Both are now rules — re-read before
claiming a file's state, and re-read again before writing Javadoc that alleges a defect. The date stamps introduced
today make any such claim traceable to a commit, which raises the cost of getting one wrong.

### Javadoc gained dated provenance

Comments carried no indication of when they were written or whether the code was new. Each block now ends with a line
like `coded on 260815, commented in full on 260815`, sitting above the tags so it does not displace the summary
sentence. Git holds the real history; the stamp only says which commit to look at.

### What the day's bugs had in common

Six of the real defects were the same shape — a boolean test the wrong way round or using the wrong accessor, in code
that compiled and read plausibly. None would have been caught by reviewing the surrounding logic, which was correct
every time; all surfaced from tests written to name the C behaviour. The port breaks at its predicates, not its
structure, and tests aimed at predicates are what find it.

**Suite: 1940 tests, 0 failures** (1808 at the start of the day).

## Things not to drop

- `effectIsKnown` answers a different question from C's — C compares the whole effect chain by reference, the port asks
  whether the item's list contains each of the counterpart's, so an item with an unknown effect currently reads as
  effect-known.
- `nonCurseRunesKnown` walks the modifier and element maps with `get` followed straight by a dereference, which C can do
  safely against fixed-size arrays and Java cannot against a map.
- The `// TODO: Check that this test is the right way round` on that same method's closing subset comparison is still
  unanswered.
- `ItemObject.description` is a stub, and two live paths now feed its placeholder straight into a player-visible
  message.
- `object_curses_find_modifier` and `object_curses_find_element` are the last two of their family, and belong on
  `Player` as package-private like the four that moved.
- `updateObjectKnowledge` is still a stub, and the curse severity/recognition split from today's
  `power` work is what it will need to get right.
- `ItemObject` and `ObjectKind`/`Artifact` disagree about the shape of a curse map, and the same question covers whether
  `getBrands()` and `getCurses()` should hand out live collections or copies.
- `Player` has no setter for race, body or shape and `PlayerUpkeep` none for `playing`, so tests install all four by
  reflection until birth needs them properly.
- `ObjectUtils.equipLearnFlag` is dead code now, and can go once `equipLearnAfterTime` beside it is ported.
- `learnInnate` is written but unreachable, waiting on the birth sequence.
