# Precis — 2026-10-12

## Key points from the day

### `PlayerOptionTypes.java` checked against the option type enum in `option.h`, `option_type_name` in `option.c` and the type column of `list-options.h`

`PlayerOptionTypes` names the five option categories, and C uses each category's number as its options-menu page number. The constants had been declared in a different order from C, so `ordinal()` did not equal the C value, although nothing in Java depended on it yet. You reordered them to C's order, which made every comparison pass, and the class, each constant, the field, the constructor and `getName()` now carry Javadoc recording why the order must not change and which C constants (`OP_MAX`, `OPT_PAGE_MAX`, `OPT_PAGE_BIRTH`) have no Java equivalent. `PlayerOptionTypesTest` pins the ordinals, the names, the page boundary and the contents of each page against the C table. The later options-menu port can take the page index straight from `ordinal()` or from an explicit page list, and the test will catch any reordering.

### `GameInputHolder.java` checked against the `get_*_hook` pointers in `game-input.c` and their assignment in `textui_input_init()`

`GameInputHolder` is the Java stand-in for C's family of hook pointers, which all start `NULL` and are assigned together by the text front-end. Every middle-layer request for a direction, item, quantity or yes/no answer goes through it, so an unset or `null` holder would break all of them. The holder starts as a `DefaultGameInput`, which matches the unset-pointer fall-backs, rejects `null`, and `resetInstance()` is the equivalent of clearing the pointers. The class, fields, constructor and methods now carry Javadoc recording the two deliberate differences from C (the hooks swap as one object, and `null` is refused), and `GameInputHolderTest` pins the start-up state, the fall-backs, install, replace, reset and the `null` rejection. A front-end or test fake that overrides one hook extends `DefaultGameInput`, as the C tests override only `panel_contains_hook`.

### `ObjectFlag.java` checked against the object flag enum in `obj-properties.h` and `list-object-flags.h`

`ObjectFlag` is the Java form of C's `OF_*` list, whose order is the savefile layout and whose first five entries must stay in stat order for `sustain_flag()`. All 38 flags, their order, their display labels and both sentinels already matched C, so nothing in the code changed. Every constant now carries a one-line description, and the class and field Javadoc record that `OF_BLESSED` has a six-character label where C's header promises five. `ObjectFlagTest` gained a label-length check and a `Stats` to `SustainStat` to `ObjectFlag` chain check that pins all three orders to the stat-plus-one rule. The object-flag bitset and `OF_SIZE`-style helpers can build on this enum, and a five-column display must truncate `" Bless"` itself.

## Things not to drop

- The options-menu or `init_options` port needs a Java stand-in for C's `OPT_PAGE_MAX`, which is defined as `OP_SCORE` and so only works because of the type order; use an explicit page list (interface, birth, cheat) in whichever class holds `option_page`, not a constant on `PlayerOptionTypes`.
