# Precis — 2026-10-27

## Key points from the day

### MonsterBase (wideMonsterChar, getWideMonsterChar, isWideChar)

`MonsterBase` holds the default glyph of a monster family, standing in for the `wchar_t d_char` of `struct monster_base` in `monster.h`. A Java `char` cannot hold a code point above `0xFFFF`, and `MonsterBaseAssembler.java` rejected such a glyph, so a modded `monster_base.txt` with one would not load. Your new `wideMonsterChar` field and its two accessors split the glyph the way `AngbandDisplayCharacter` does, and the first draft of the assembler had the halves the wrong way round, which the new `noGlyphInTheRealFileIsWide` test caught on all 56 shipped bases. The assembler now puts a glyph up to `0xFFFF` in the narrow half and a supplementary one in the wide half, and the class, field, constructor and accessor Javadoc record the split and that C has no counterpart. Callers that need every glyph must check `isWideChar()` before trusting `getDefaultMonsterChar()`, and 9 new tests plus a rewritten astral reader test pin the boundaries at `0xFFFF` and `0x10000`.

### MonsterBaseAssembler.assemble

`MonsterBaseAssembler.assemble` turns each parsed `monster_base.txt` record into a `MonsterBase`, standing in for the `parse_mon_base_*` handlers in `mon-init.c`. It was the last assembler in the soft-errors-to-fatal sweep with a skip-and-continue branch, so a bad race flag dropped one base and let the other 55 load, where C stops the whole load, and it returned the bases in file order where C's chain runs from `Morgoth` back to `ancient dragon`. Your change makes an unknown flag throw `DataFileParseException` naming the flag, line and file, and puts each base at the front of the list. The class, logger and `assemble` Javadoc now record the fatal paths, the glyph split, the pain lookup and the reversed order, and the reader tests that assumed file order or a skipped record were rewritten, with new ones for `NONE`, `MAX`, a bad flag mid-list, pain serial 0 and a mixed narrow and wide glyph pair. The assembler now never writes to its `errors` list, and any caller that indexes the result by file position must count from the end.

### MonsterSpellAssembler.assemble

`MonsterSpellAssembler.assemble` turns each parsed `monster_spell.txt` record into a `MonsterSpellType`, standing in for the `parse_mon_spell_*` handlers in `mon-init.c`. It still had soft errors and disagreed with C in four places: `msgt:` was exact-case with no numeric form and let `NONE` through, a negative `hit:` loaded, a spell dropped for a bad level list was skipped, and the list ran in file order where C's chain runs last record first. Your change sends `msgt:` through `MessageType.lookupByName`, refuses a leading minus on `hit:` with `ParseUtils.minusFound`, throws on a `null` level list and adds each spell at the front of the list. The class, logger and `assemble` Javadoc now record the fatal paths, the `NONE` and `MAX` names, the reversed order and what the level assembler still gets wrong, and 11 reader tests that pinned the old behaviour were rewritten, with a new `MonsterSpellAssemblerTest` of 17 direct tests for each name, message, hit and ordering boundary. A repeated spell name now finds the later record on a first-match search, as `monster_spell_by_index` does, and the assembler never writes to its `errors` list.

## Things not to drop

- `docs/Assembler_Issues.md`: the `monsterbase/MonsterBaseAssembler.java` section on the list being in file order is now fixed, but is not marked closed and still names a renamed test.
- `MonsterBaseGrammar.g4` and `MonsterBaseLexer.g4`: fixed directive order, an empty `flags:` rejected, space-separated flags rejected and a leading minus accepted on `pain:`; recorded in `docs/grammar_issues.md`.
- `MonsterBase.java`: the seven-argument constructor checks neither that `wideMonsterChar` is within `0..0x10FFFF` nor that the narrow half is `'\0'` beside it, where `AngbandDisplayCharacter` refuses both.
- `MonsterBase.java`: `toString` leaves out `wideMonsterChar`.
- `docs/Assembler_Issues.md`: the `monsterbase/MonsterBaseAssembler.java` glyph section still says a glyph above U+FFFF is a soft error, and it names a test that was renamed.
- `MonsterSpellLevelAssembler.java`: a bad `power-cutoff:` appends a soft error and returns `null`, and an unknown lore colour (base, resist or immune) appends one and drops that level, where C reads an unknown colour as white.
- `MonsterSpellLevelAssembler.java`: no implicit level 0 is added, so a leading `power-cutoff:` or a record with no text has fewer levels than C's chain; the reader tests `aLeadingPowerCutoffLeavesNoImplicitLevelZeroHereWhereCKeepsIt` and `aRecordWithNoTextHasNoLevelHereWhereCAlwaysHasOne` pin it.
- `MonsterSpellParseRecord.java` and `MonsterSpellLevelAssembler.java`: Javadoc cites a `mon-init.c` line number, and the record's class Javadoc still calls a malformed `hit` a reported soft error.
- `docs/Assembler_Issues.md`, `docs/Issue_Approach_Order.md` and `docs/grammar_issues.md`: the `MonsterSpellAssembler.java` entries for the absent `hit:`, the `msgt:` lookup, the file-order list and the negative `hit:` are now fixed but are not marked closed, and the soft-error line numbers for `MonsterSpellAssembler.java` are not struck through.
