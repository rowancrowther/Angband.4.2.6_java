# Precis — 2026-09-06

## Key points from the day

### `resetStats` closes out the point-buy reset button, and verifying it caught two bugs along the way

`resetStats` puts every point-buy stat back to its starting value of 10, zeroes what's been spent, and reseeds each
stat's next-point cost, so the point-buy screen's reset button has something to call. Verifying it against the C
original found two problems: the point total it hands back was going nowhere, because C communicates the reset total
through a pointer the port has no equivalent for, and the increment-cost lookup was reading a different stat's value
than the one it was pricing. Both are fixed now — the total comes back as a return value instead of an out-parameter,
and the cost lookup reads each stat's own freshly-reset value. Seven tests cover the stat loop against leftover values a
caller's map might carry in, the sentinel guard, the return value regardless of what was passed in, and the
`updateDisplay` guard's two downstream calls, so the reset button has a working implementation ready to be wired up
without carrying either bug into its first caller.

### `buyStat` closes out the point-buy screen's buy button, alongside its own private result type

`buyStat` spends a single point-buy point raising one stat, the buy button `resetStats` was ported alongside earlier
today. Verifying it against the C original found a stat choice outside the valid range was indexed into the stat enum
before that range was ever checked, so a malformed choice threw instead of answering the same "nothing spent" result C
gives for the same input. The choice is now validated before it indexes anything, so out-of-range input degrades the way
C's does rather than crashing. Thirteen tests cover the ordinary purchase, every flavour of invalid choice, a stat
already at the cap, a mismatched cost, too few points, the one point where the port deliberately parts from C rather
than following it past the end of an array, and the `updateDisplay` guard's call order — which turned out to be the
opposite of `resetStats`'s own, since C's two functions do it differently — so the buy button now has a working
implementation with the same "nothing wired up yet" status as the reset button.

### `sellStat` closes out the point-buy screen's sell button, catching a bug the first verify pass alone didn't clear

`sellStat` refunds a single point-buy point by lowering one stat, the mirror of the buy button ported earlier today. The
first verify pass found the stat was never actually lowered, so a sale refunded points without touching the value it
claimed to be selling, and the increment-cost refresh read the stat's value from before that missing decrement rather
than after, which would have read past the end of `birthStatCosts` once the decrement was restored. Both are fixed now —
the stat drops first, and the cost refresh reads its new, lower value, landing back inside the table even at the top of
the range. Eight tests cover the ordinary sale, the floor guard that stops a stat falling below 10, the boundary that
used to misread past the cost table, and the `updateDisplay` guard's call order, so the point-buy screen's three
buttons — reset, buy and sell — are all now ported and waiting on the same wiring.

### `generateStats` closes out the point-buy screen's auto-generate button, catching three bugs across two verify passes

`generateStats` drives the buy and sell buttons through a five-step heuristic to pick reasonable starting stats for
whatever race/class combination is being born, the last of the point-buy screen's buttons after today's reset, buy and
sell work. Verifying it against the C original found three problems: the step that should keep buying a stat until it
can't afford any more was instead buying it once and then selling it straight back down, a stat's "maxed" flag was only
being set when an incidental sell happened to succeed rather than unconditionally, and the fallback for a class with no
spells pointed at the wrong sentinel. All three are fixed now, the last two on a second verify pass after the first
round of fixes. Three tests cover the fixed buy-to-ceiling step in isolation, a full non-caster run whose breakpoint
tracking is worked out from the real blows-per-turn tables, and a full caster run exercising the spell-stat's own
allowance past the usual cap, so the point-buy screen's four buttons — reset, buy, sell and auto-generate — are all now
ported and waiting on the same wiring.

### Five read accessors close out the birth-quickstart field pairs, plus a cleanup in two setter tests

`getAUBirth`, `getWeightBirth`, `getHeightBirth`, `getStatBirth` and `getFullName` round out the read side of the
quickstart-copy fields — the birth gold, height, weight and stats the roller keeps so a save can reopen at the character
it started as, and the character's name, whose writing half isn't ported yet. The height and weight tests had been
reading their private fields by reflection because no getter existed when they were written; now that real getters
exist, those tests read through them instead, and the reflection workaround is gone from both files. All five were
single-line field reads matching C's own direct struct access at every call site, confirmed against C's
`save_roller_data` and its already-ported Java counterpart, so nothing needed fixing before it was documented and
tested. `getFullName` is the one loose end: every test exercising it still has to write the field by reflection, since
the port has no `setFullName` yet, so a real writer is what character naming will need before this accessor sees a
caller outside a test.

###
`saveRollerData` closes out the birth-quickstart snapshot, catching a stat-map crash and a history-field mixup along the way

`saveRollerData` copies the currently-rolled character into a `Birther` record, the snapshot the birth process keeps for
undo and quickstart. Verifying it against the C original found two problems on the way to a clean pass: `Birther`'s stat
map was never initialised, so every stat copy would have thrown the moment the method actually ran, and the
background-text handoff was reading one field but nulling a different one entirely, a mixup traced to two accessors
sharing a name across unrelated data. Both are fixed now — the map is built in the constructor, and the background text
has its own correctly-typed field and accessor pair the read and the null-out both agree on. Twelve tests cover the
ordinary snapshot, each field's birth-copy-not-live distinction, the stat loop's sentinel bounds, and the history
handoff surviving a second roll, closing out the last of the fields `save_roller_data` touches and leaving the
quickstart record ready for whatever calls it first.

### `Birther` gets its full Javadoc pass, plus the background-text accessor pair it hands off to

The birth-quickstart snapshot record itself, `Birther`, had working code but no Javadoc anywhere in the class; alongside
it, the two plain `Player` accessors it reads from and writes to, `getHistoryBirth` and
`setHistoryBirth`, needed the same pass. Every field and accessor in `Birther` is a bare struct-to-object port, so
verifying it against C surfaced no new bugs — the work was documenting a class nobody had described yet, and confirming
that the naming quirk `saveRollerData`'s own tests already caught, where the setter's name follows the field it reads
from rather than the one it stores into, is deliberate rather than left over. The solution was a full class-and-accessor
Javadoc pass on `Birther` and the two `Player`
methods, each carrying its own C cross-reference and dated provenance line, backed by a new `BirtherTest`
covering every field's round-trip and the two divergences worth pinning down — the stat map's missing sentinel guard,
and the name field's missing length cap. `Birther` and its one caller, `saveRollerData`, are now fully documented and
tested end to end, so the class is a clean read for whoever picks up
`load_roller_data` or the undo/quickstart wiring next.
