# Precis — 2026-09-09

## Key points from the day

### `SwingUI.JPanelArea.erase` and
`Window.erase` documented and covered, giving the row-blanking screen primitive a verified base

`erase` blanks a run of cells in one row of the character grid, the port of C's `Term_erase`, with `Window.erase`
the thin wrapper that reaches the panel and repaints once the row is updated - the same two-step shape
`Window.clear()` already uses. It's one of the handful of screen primitives the birth roadmap's D2 stage calls a shared
dependency: any screen the game draws needs it, not just birth's. The first two verification passes each caught the
out-of-range guard checking the wrong one of the grid's two dimensions against `x` and `y` - first missing entirely,
then checking each coordinate against the other's bound - before a third pass matched C's
`Term_gotoxy` guard exactly. Two new test suites, one for the panel and one for the window wrapper, pin the ordinary
run, the width clamp at the row's edge, the zero- and negative-length no-ops, and all four out-of-range coordinates, so
the primitive the rest of D2's screens will build on now has a settled, checked shape underneath it.

### `SwingUI.JPanelArea.getDisplayWidth` and `getDisplayHeight` documented and covered

These two getters expose the character grid's own dimensions - 80 columns, 24 rows - split from C's `Term_get_size`,
which reports both through a pair of out-parameters in one call and falls back to 80x24 when its global term pointer is
unset. `Window.gotoXY` already leans on both getters to bounds-check a coordinate before placing the cursor, the same
purpose `Term_get_size`'s callers put it to. The verification pass matched the two split getters against
`Term_get_size` clause by clause and found no divergence - the grid has no unset state of its own, so it always returns
the same 80x24 that C's fallback does - so the fix was straight Javadoc and a small test class rather than any code
change. With these settled, `Window.gotoXY`'s own bounds check now rests on a documented and tested foundation rather
than an unverified pair of getters.

### `Term.gotoXY` and the terminal/window wiring around it documented and covered

`gotoXY` places the cursor and is the caller `TermWin`'s cursor setters and `Window`'s character-size getters exist for;
`TermData`'s `getTerm`/`clear`/`setWindow`/`getWindow` and `SwingUI`'s active-terminal tracking are the surrounding
wiring that gets a `Term` a window to draw into in the first place. A verification pass on `gotoXY`
found its bounds check reading the front end's live window size rather than the terminal's own stored dimensions - a
real divergence from `Term_gotoxy`, since the two can differ once a window resizes independently of the terminal it
backs. With that fixed, `gotoXY` and its whole supporting cast now check clean against the C original. Five new test
classes, twenty-three cases between them, cover the ordinary path, every boundary, and the "illegal requests do not move
the cursor" guarantee `Term_gotoxy`'s own comment states, mostly by reflection since several of the wrapped classes
expose no getters of their own. The terminal/window boundary birth's screens will draw through now rests on a settled,
tested base rather than one with an unverified coordinate source at its centre.

### `TermData.dispose` documented and covered

`dispose` releases one terminal's platform window by handing off to the window's own `dispose()`, and is the method
`SwingUI.closeDown()` now calls once per terminal instead of walking a separate list of raw windows. It's the piece that
replaced today's earlier `SwingUI.windows` bug: with `windows` gone, `closeDown()` needed a way to reach each window
through the `TermData`s it already owns, and this is that way. No C function of its own backs it - the nearest
equivalent sits inline inside `hook_quit`'s shutdown loop, which destroys each window directly rather than through a
named function - so the Javadoc records that provenance rather than a one-to-one mapping. A new case in the existing
`TermData` test class confirms a window stops being displayable once `dispose` runs, the same check
`SwingUITest` already makes for `closeDown` itself. With this documented and tested, the shutdown path `closeDown`
walks is now covered end to end, not just the loop that drives it.

### `Region` documented and covered

`Region` is the drawing-helper layer of the new UI panel architecture set out in `UIPanelArchitecture.md` - a rectangle
into a `CellGrid` that lets an event draw at (0,0) without knowing where it sits on screen or being able to scribble
outside its box, with no C original behind it: verification worked against the design doc's clip contract instead. It's
the base the rest of that architecture - `Frame`, `Screen`'s flush point, and eventual hit-testing - builds on, so a
coordinate bug here would resurface in everything drawn through it. Several rounds of verification caught a string of
bugs that a single always-zero-offset region had been masking: a missing translation between region-local and grid
coordinates, a bounds check comparing translated coordinates against the region's own untranslated size, swapped
row/column axes, and an `erase()` that briefly became a total no-op through a
`StringBuilder` capacity mix-up, each narrowed down until `put`, `erase`, and `clear` matched the clip contract exactly.
`Region` is now documented and covered by a 26-case test suite built around a deliberately offset region, pinning the
ordinary path, every clip boundary, and the deliberate divergence from the old `Term`-derived `erase`
(which rejects an out-of-range column outright rather than clipping it).

### `Frame` documented and covered

`Frame` is the immutable snapshot the UI panel architecture hands from the UI thread to the event dispatch thread - the
record pairing a `CellGrid` with its live `Hotspot`s, with no C original behind it since this too is new architecture.
It's the piece `Screen.frame()` builds and the panel will eventually receive, so pinning down its equality and copying
guarantees protects the invariant the whole Option B design rests on: once handed to the EDT, that grid must never be
mutated again. Verification found nothing to fix, so the work was Javadoc recording what the record does and does not
guarantee - it trusts its caller to have already made both components safe, and does not defensively copy them itself -
plus a five-case test suite pinning the accessors and the asymmetric equality
`CellGrid` having no `equals` of its own produces. With `CellGrid`, `Region`, and now `Frame` documented and covered,
the whole non-Swing half of the drawing architecture is settled ahead of the `JPanelArea` cutover this pass exists to
prepare for.

### `Hotspot` documented and covered

`Hotspot` is the clickable-rectangle record the UI panel architecture publishes alongside a `Frame`, so that a click at
a given row and column can be interpreted against the same screen that was actually painted, with no C original behind
it since this too is new architecture. It's the last of the three plain-data types - `CellGrid`, `Frame`, and now
`Hotspot` - the design doc lists as needed before hit-testing can be built, so pinning down its equality now means the
eventual hit-test code has a settled contract to rely on rather than an implicit one. Verification found nothing to fix,
so the work was Javadoc recording the record's purpose and fields plus an eight-case test suite pinning the accessors
and the per-component equality, including the reference-vs-value split a bare `Object` event produces against a `String`
one. With `CellGrid`, `Region`, `Frame`, and now `Hotspot` documented and covered, the whole non-Swing half of the
drawing architecture the design doc set out is settled.

### `CellGrid` documented and covered

`CellGrid` is the plain data layer of the UI panel architecture set out in `UIPanelArchitecture.md` - a
`[row][col]` grid of `AngbandDisplayCharacter` cells with no Swing and no drawing logic of its own, with no C original
behind it since this too is new architecture. It's the base every other piece of the drawing layer sits on - `Region`'s
translation, `Frame`'s snapshot, `Screen`'s ownership - so a structural-copy bug here would resurface in all of them.
Verification found the implementation matching the design doc's decisions exactly - the throw-on-`set`/null-on-`get`
split, the unguarded `cols()`, and the structural, not deep, `copy()` - so the work was Javadoc plus a new eighteen-case
test suite pinning every boundary and the copy's independence guarantee. With `CellGrid` itself now documented and
covered alongside `Region`, `Frame`, and `Hotspot`, the whole non-Swing half of the drawing architecture the design doc
set out is built and tested.

### `Screen` documented and covered

`Screen` is the owner of the UI panel architecture's live state and the sole boundary between the thread that composes a
screen and the thread that paints it, with no C original behind it since this too is new architecture. It's the piece
that ties the rest of the drawing layer together - `root()`
hands out the whole-grid `Region` everything draws through, and `frame()` is the one place the Option B invariant of
never letting the EDT see a still-mutating grid gets enforced. Verification found the implementation matching the design
doc exactly, so the work was Javadoc plus a six-case test suite pinning the write-through behaviour of `root()` and the
independence of `frame()`'s copies from whatever the live grid and hotspot list go on to do afterwards. With `Screen`
now documented and covered alongside `CellGrid`, `Region`, `Frame`, and `Hotspot`, the whole non-Swing half of the
drawing architecture the design doc set out is built and tested.
