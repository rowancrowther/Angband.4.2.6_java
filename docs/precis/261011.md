# Precis — 2026-10-11

## Key points from the day

### `MonsterRace.java` re-checked against `struct monster_race` in `monster.h`, `lookup_monster` in `mon-util.c` and the friend and shape conversion in `finish_parse_monster` in `mon-init.c`, with the lore loading left aside

`MonsterRace` is the Java copy of one `monster.txt` record and the shared template behind every live monster, with the two second-pass methods that turn friend and shape names into races and bases. The accessors, both resolvers and the plain-assignment setters all still match C, but the `lore` field, `setLore` and `getLore` blocks said no production code ever attaches a lore record, when the lore-file reader does so for each race it names. Those three blocks first said that the lore-file reader is the only caller; they were rewritten again once the race loader began giving every race a blank record (see the lore point below). `MonsterRaceResolutionTest`, `MonsterRaceLookupAgreementTest` and `MonsterRacePopulationAndLoreTest` already pin the resolvers, the lookup rules, the population setters and the lore reference, so the chapter 6 generation code can rely on `MonsterRace` as it stands.

### `MonsterBlow.java`, `MonsterLore.java`, `MonsterDataLoader.loadMonsters` and `MonsterRegistry.java` re-checked against `struct monster_blow` in `monster.h`, `struct monster_lore` in `mon-lore.h`, the `l_list` allocation in `finish_parse_monster` in `mon-init.c` and the blow-count rule in `mon-attack.c`

Every loaded race now carries a blank lore record with one blank blow per race blow, so `getLore` can be called on any loaded race, and the registry lookups and counters still match C under the 261009 deviation. The `MonsterBlow` and `MonsterLore` blocks cited `monster.h` for the lore struct, left most fields and every getter undocumented, and the `MonsterRace` lore blocks and `logger` block still described a loader that attached no lore and a `getLore` that returned null. All of those blocks were rewritten, and `MonsterBlowConstructionTest` and `MonsterLoreBlankRecordTest` were added beside the existing blow, `initblows`, loader and registry tests, with the full suite green at 8708 tests and 19 skipped. The one deliberate difference, that each lore sizes its blows to its own race's count where C uses the global maximum, is now written into the `MonsterLore` class block and the `loadMonsters` block, so the lore reader can be ported later knowing where its blow-index bound differs.

### `MonsterShape.java` checked against `struct monster_shape` in `monster.h` and `parse_monster_shape` in `mon-init.c`

`MonsterShape` is the Java copy of one `shape:` line of a monster, holding the name and, once resolved, either a base to draw a random race from or one specific race. The three fields and the plain-assignment setters match C, but the `setRace` and `setBase` blocks said each one cleared the other, when neither does and `MonsterRace.resolveShapes` clears the unused one itself. The class, field, constructor and accessor blocks were rewritten to say that, to name C's missing `next` pointer and the base lookup that moves to the second pass, and `MonsterShapeTest` was added beside the resolver tests with the full suite green at 8715 tests and 19 skipped. The shapechange code can now rely on exactly one of the two targets being set after loading, with the file-order difference already recorded under the open items.

### `ObjectProperty.java` re-checked against `struct obj_property` in `obj-properties.h` and the `object_property` handlers and `finish_parse_object_property` in `obj-init.c`

`ObjectProperty` is the Java copy of one `object_property.txt` record, holding the category, subtype, id type, payload, power, multipliers, strings and UI bindings the power and knowledge code read. Every field and accessor matches C, including the type multiplier defaulting to 1 and the zero-filled defaults, but the `adjective`, `negAdjective` and `description` blocks did not say that an absent line is `NULL` in C and the empty string here, or where C reads each one. Those three field blocks were rewritten to say so, and `ObjectPropertyStructFidelityTest` was added to walk all 79 records against the data file, with the full suite green at 8722 tests and 19 skipped. The stat-wording and knowledge-menu chapters can now see that the three string fields have no accessor yet and add them when `desc_stat` and `ui-knowledge.c` are ported.

### `EquipSlot.java` checked against `struct equip_slot` in `player.h`, `parse_body_slot` in `init.c` and `player_embody` in `player-birth.c`

`EquipSlot` is the Java copy of one place on the body that can hold an item, with a kind, a name and the item worn there. The constructor, the three getters and the item setter all match C, including the slot starting empty, but the `name` block gave "wielding" and "on left hand" as examples when the name is the plain `body.txt` word such as "weapon" or "left hand", and the getter blocks and the `setItem` block cited C line numbers. The class, field, constructor and accessor blocks were rewritten to separate the slot's own name from the wording `slot_table` supplies, to say C's `next` link became the body's list, and to name functions instead of lines, and `EquipSlotConstructionTest` was added beside `EquipSlotSetItemTest` with the full suite green at 8739 tests and 19 skipped. The wield, take-off and equipment-description code can now rely on the name being what `equipped_item_by_slot_name` compares and not what is shown to the player.

### `PlayerHistoryChart.java` checked against `struct history_chart` in `player.h`, `parse_history_chart` and `finish_parse_history` in `init.c` and `get_history` in `player-birth.c`

`PlayerHistoryChart` is the Java copy of one numbered step in the background-history graph, holding the entries that can be rolled there and the chart that follows. The chart number, the entry order and the hoisting of the successor from each entry up to the chart all match C, and all 44 charts in `history.txt` do have one successor, ascending rolls and a last roll of 100. The class block cited a C line range and the field, constructor and accessor blocks said nothing of C's `idx`, `isucc` and `succ` or of C's reversed entry list, so they were rewritten to name those fields, to say that a null successor does not always mean end of chain, and to drop the line range, with `PlayerHistoryChartTest` added beside `HistoryReaderTest` and `PlayerBirthGetHistoryTest`, reading the expected values straight from the data file, and the full suite green at 8755 tests and 19 skipped. The race and birth code can now rely on `getSuccessorNumber` to tell a terminal chart from one whose successor failed to resolve.

## Things not to drop

- `MonsterSpell.java`: `RSF_ACID` to `RSF_MANA` (19 breath entries) duplicate `RSF_BR_ACID` to `RSF_BR_MANA` and have no counterpart in `list-mon-spells.h`, so the enum has 112 constants where C has 93 plus `NONE` and `MAX`, and every later ordinal differs from C's.
- `MonsterAssembler.java`: `hearing` is stored as written in `monster.txt`, where C's `parse_monster_hearing` multiplies it by `z_info->max_sight / 20`; the two agree only while `max_sight` is 20.
- `MonsterAssembler.java`: the friends, friends-base, drops, mimic and shape lists are built in file order where C builds them in reverse, which matters once `place_friends` and the drop code consume random numbers as they walk them.
- `LoreGrammar.g4`: `monsterLore` ends with `race.setLore($lore)`, which replaces the race's lore record where C's `lore_parser` fills `l_list[race->ridx]` in place, so once blank records exist a lore entry that omits a field would drop the blank's value for it (noted in `LoreReaderTest.java`'s class comment, parked with the reader).
- Savefile chapter: `src/main` has no counterpart of `wr_monster_memory` in `save.c` or `rd_monster_memory` in `load.c` (searched 26-10-11), so when it is ported, write only races with non-zero `pkills` or `thefts`, reset every `max_num` from race index 1 to 100 (1 for uniques) before reading, restore both counts, set `max_num` to 0 for a unique with a kill count, and check whether the reader's `continue` on an unknown race name skips the next `rd_string`.
- `LoreGrammar.g4`: the `@after` block of `monsterLore` builds `MonsterLore` with a 19-argument list that matches no constructor in `MonsterLore.java`, so the grammar and the class have drifted apart (parked with the reader).
- `LoreGrammar.g4` and `MonsterLore.java`: the lore reader will size blows per race where C's `parse_lore_blow` accepts any blow index below `mon_blows_max` and `finish_parse_lore` zeroes the count for a non-blow, so a hand-edited lore file with a high index would behave differently.
- `MonsterLore.java`: `caseInnate` is a slip for C's `cast_innate`, a rename for whenever the field is next touched.
- `ObjectPropertyAssembler.java`: a `subtype:` line on a non-flag record is rejected, where C's `parse_object_property_subtype` accepts it on any type; no shipped record does this, so it is inert for now.
- `ObjectPropertyAssembler.java`: a record with no `code:` line is reported as an invalid code and dropped, where C keeps it with index 0; every shipped record has a code, so it is inert for now.
- `ObjectProperty.java`: `adjective`, `negAdjective` and `description` have no getters, for `desc_stat` in `effect-handler-general.c` and the menus in `ui-knowledge.c` to use once they are ported.
- `BodyAssembler.java`: a `slot:NONE:` or `slot:MAX:` line is accepted because `EquipmentSlotsEnum.valueOf` finds both, where C's `lookup_flag` starts at index 1 and its table has no MAX, so `parse_body_slot` rejects `NONE` and cannot see `MAX`; no shipped body does this, so it is inert for now.
- `HistoryAssembler.java`: a non-zero successor that names no chart is reported and the chart keeps a null successor, where C's `finish_parse_history` fails the whole load; so a bad `history.txt` would load and end a biography early rather than stop the game. No shipped chart does this, so it is inert for now.
