# Precis — 2026-10-17

## Key points from the day

### `FileModeEnum` checked against `file_mode` in `z-file.h`

`FileModeEnum` is the Java form of C's `file_mode` enum, naming the three kinds of access `file_open` accepts. It already matched C, with the same three constants in the same order, but the enum and its constants carried only one-line comments that said nothing of the `fopen` mode each one stands for. The enum and each constant now carry Javadoc naming the `z-file.c` open behaviour (create, truncate, keep, fail on missing, the `FTYPE_SAVE` exclusive open) and `FileModeEnumTest` pins the order, the ordinals, the names and each mode's effect on a real file against values traced from `file_open`. `FileHandler` and `AngFile`, which switch on the enum, can now be read against a record of what each mode is meant to do.

### `FileTypeEnum` checked against `file_type` in `z-file.h`

`FileTypeEnum` is the Java form of C's `file_type` enum, naming what kind of file `file_open` is writing. It already matched C in names and order, but its Javadoc was one-line stubs, and the one on `FTYPE_NULL` claimed it was returned when a file does not exist, which nothing does. The enum and each constant now say what `z-file.c` does with the type (only `FTYPE_SAVE` with a write changes the open, to an exclusive owner-only create), that `ordinal()` is one lower than C's values, and that `FTYPE_NULL` is an unused placeholder after C's four. `FileTypeEnumTest` pins the order, the names and each type's effect on a real file against values traced from `file_open`, so `FileHandler.open` can be read against a record of what the type is meant to change.

### `Savefile.savefileGetDescription` partly ported from `savefile_get_description` in `savefile.c`

`savefileGetDescription` is the lookup the savefile picker uses to label each file, and until today it returned an empty string whatever the path. Every entry the picker listed therefore carried a blank description, and a file that could not be opened looked the same as one that could. The method now opens the file for reading, closes it, and returns `null` where C returns `NULL`, and `SavefileTest` pins that open step against `file_open`'s read behaviour. The header check, the block scan and the 119-character cap are still unported, so every file that opens gets an empty description, and the two tests that need `check_header` are disabled with the C result they are waiting for.

### `BlowEffectReader` checked against the blow-effect parser in `mon-init.c`

`BlowEffectReader` is the bridge that feeds `blow_effects.txt` through the grammar and assembler into `BlowEffect` objects, standing in for `run_parse_eff` and `finish_parse_eff`. It already matched C: records come back in file order, a missing file is an `IOException` where C quits, and the shipped file's 30 records all load. Its Javadoc was generic and did not name the C counterparts, so the class, the logger and the three methods now say which C function each stands in for and where the port deliberately differs (the `record-count:` header, partial results, no blank trailing slot). `BlowEffectReaderTest` gains tests for file order against the upstream file, the two error channels, duplicate names and directive order, so the reader's own contract is pinned and not only the assembler's.

## Things not to drop

- `learnInnate` is called from `PlayerBirth.doCmdAcceptCharacter`, but `CommandProcessor.java` registers
  `CMD_ACCEPT_CHARACTER` with a `null` handler, so nothing dispatches `doCmdAcceptCharacter` and `learnInnate` is still
  unreachable in a running game. C points that row of `game_cmds[]` at `do_cmd_accept_character`; the other birth
  commands in the same block of `CommandProcessor.java` are `null` too. Carried forward from the 260815 precis.
- `nonCurseRunesKnown` in `PlayerKnowledge.java`: the 260815 precis carried a
  `// TODO: Check that this test is the right way round` on the closing subset comparison. That comment is no longer in
  the file. The line now reads `knownFlags.isSubset(itemFlags)`, which has the same argument order as C's
  `of_is_subset(obj->known->flags, obj->flags)`, and `Flag.isSubset` tests that every flag of its argument is in the
  receiver, so the order looks right. Nothing records that as checked. Also left in the method:
  `if (knownSlays == null) return false;`, which its own Javadoc calls a leftover that can never fire, because
  `ItemObject.getSlays()` answers an empty set. Carried forward from the 260815 precis.
- `savefile.c` block reader: `check_header`, `next_blockheader`, `skip_block`, `load_block` and `rd_string` have no Java yet, so `Savefile.savefileGetDescription` cannot return a real description or `"Invalid savefile"`.
- `SavefileGetterImpl.java` passes the result of `Savefile.savefileGetDescription` to `setDescription` without a null check, though the method now returns `null` for an unopenable file.
- `BlowEffectGrammar.g4`: a record must carry at least one directive after `name:`, so a name-only record is a syntax error, where C's `parse_eff_name` accepts it.
- `BlowEffectGrammar.g4` and `BlowEffectAssembler.java`: a repeated `desc:` keeps the last value, but C's `parse_eff_desc` appends to it, and the grammar comment wrongly says every directive overwrites. No shipped record repeats `desc:`.
- `BlowEffectAssembler.java`: an unknown `resist:` name is a soft error that skips the record, where C's `parse_eff_resist` silently stores -1.
- `BlowEffectAssembler.java` and `BlowEffectReaderTest.java`: the class blocks cite C line numbers (`mon-init.c:388-400`, `project.c:60`) and the assembler's says "seams" rather than "boundaries".
- `GrammarDriver.java` and `MonsterDataLoader.java`: C's `parse_file` looks for a customised data file in the user directory before the gamedata one, and the Java loaders open only the gamedata path.
- `PitProfile.java`: the class block says `struct pit_profile` is in `src/mon-make.h`, but it is declared in `generate.h`.
- `lib/gamedata/monster_base.txt`, `constants.txt`, `projection.txt` and `player_property.txt`: a comment reads "gameEngine" where the upstream file says "game" (`monster_base.txt` has "in-gameEngine"), the look of a global rename of "game" that reached data-file comments.
