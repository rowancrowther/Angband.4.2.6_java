# Precis — 2026-09-18

## Key points from the day

### How `ui_entry.txt` builds and then overrides entries — the embryo's real job

The "embryo" in `ui-entry.c` turned out not to be a comparison device at all: it is a per-block accumulator plus a
single `exists` flag, and the only comparison anywhere is a name lookup against the registry of entries built so far,
done once when a `name:` line opens a block. A block whose name is already in the registry *edits that entry in place*
and inserts nothing; a block whose name is new builds a fresh entry which, at the end of the block, fans out into one
entry per element or stat if the block was parameterized. This is what makes the shipped data work — the generic
`resist_ui_compact_0` block fans out into `<ACID>` through `<DISEN>`, and the blocks that follow it name those generated
entries directly to add their labels and screen categories. The consequence for the port is that the lookup-and-decide
has to happen *before* the record's fields are interpreted, because whether an entry already exists changes how its
`parameter:`, `category:` and
`priority:` lines are read; the current assembler builds the entry first and consults the embryo afterwards, which is
the wrong way round.

## NOTES

### `struct ui_entry` (C) vs `UIEntry` (Java) — field comparison

Most fields already reconcile cleanly: `name`, `categories`, `renderer_index`/`combiner_index`
(resolved to `UIEntryRenderer`/`CombinerName`), `default_priority`, `flags`, `label`. C's manual array bookkeeping
(`n_category`, `nalloc_category`, etc.) is correctly dropped — `List` makes it meaningless.

Two real gaps remain unported. `obj_props`/`bound_object_property` and
`p_abilities`/`bound_player_ability` (`ui-entry.c:100-101,61-74`) — the bindings that drive an entry's *value*, set from
`bindui:` lines in `object_property.txt`/`player_property.txt` — have no Java equivalent yet, and can't until that
`bindui:` grammar exists.

The shortened-label fallback (`fill_out_shortened`, `ui-entry.c:1717-1752`) was the other gap; this is now addressed —
`UIEntry` has gained a `shortenedLabels` map (see below) since the field comparison was first raised today.

### Shortened-label storage

C's `shortened_labels[MAX_SHORTENED=10]` is keyed by character-count minus one: `label2:` writes index 1, `label5:`
writes index 4 (`parse_entry_shortened_label`, `ui-entry.c:2073-2098`). The full
`label` field is never part of this array — it's the fallback source when nothing longer is set.

Unset slots are filled once, at parse-finish, by `fill_out_shortened`: for each unset index it walks *upward* to the
nearest longer already-set slot (not necessarily the longest) and truncates that string down, falling back to the full
`label` only if nothing longer was ever set. For the shipped `ui_entry.txt` this always resolves to one of `label`,
`label2`, or `label5`, since no other
`labelN:` is ever used in the data — but that's a fact about the current data file, not a property of the algorithm.

Java's new `shortenedLabels` field (`UIEntry.java`) is a `Map<Integer, String>` keyed the same way as the write side
(`1` → `label2`, `4` → `label5`). The fill-forward walk itself isn't ported yet — only explicit `label2`/`label5` are
stored, so a length with no explicit entry (e.g. length 4, which
`ui-equip-cmp.c:1361` actually requests) has no computed fallback to return.

### `param_index` — two different meanings sharing one C field name

On the *embryo* (`embryo->param_index`, set by `parse_entry_parameter`, `ui-entry.c:1998-2009`)
it's an index into `name_parameters[]` — which *kind* of parameter: 0 = none, 1 = element, 2 = stat.

On the *finished* `ui_entry`, `hatch_embryo` (`ui-entry.c:1770-1854`) overwrites it to mean something else: which
*specific* stat/element this entry is. A parameterized record (e.g.
`parameter:element`) fans out into one freshly-allocated `ui_entry` per element, each cloned from the embryo with its
own `<ACID>`-style name suffix and `param_index = i` for that specific element. The loop only runs `n-1` times because
the last variant reuses the embryo's own entry struct in place rather than allocating one more; an unparameterized entry
gets `param_index = -1`.

This finished `param_index` is genuinely consumed later, not just administrative — e.g.
`parse_entry_priority` (`ui-entry.c:2159-2162`) calls a named priority scheme's function with it to compute a
per-variant priority.

Java's `UIEntry` splits this pair into two already-resolved fields instead of a raw index:
`statOrElement` mirrors the embryo's kind, `parameter` (`ElementEnum`) mirrors the finished index — but only for the
element case. There's no equivalent field recording *which* stat when
`statOrElement == STAT`.

### `UIEntryAssembler` vs. `ui-entry.c` — everything but `buildCategories`

- Field-resolution block (`UIEntryAssembler.java:111-244`) is structurally close to the parser callbacks
  (`parse_entry_name`/`_template`/`_parameter`/`_renderer`/`_combine`/`_priority`/`_flags`,
  `ui-entry.c:1881-2235`), just collapsed into one pass over an already-fully-parsed
  `UIEntryParseRecord` instead of C's per-line accumulation onto one embryo.
- STAT/ELEMENT expansion (`UIEntryAssembler.java:203-237`) is a hand-rolled substitute for C's real parameterization
  path (`name_parameters[]`, `embryo->param_index`,
  `parse_entry_parameter`/`ui-entry.c:1982-2011`) — covers only those two kinds, discards all but the loop's last
  `uiEntry`, and never sets `embryo.parmIndex`, so it duplicates rather than routes into
  `hatchEmbryo`.
- `hatchEmbryo` (`UIEntryAssembler.java:275-338`) is a faithful shape-for-shape port of
  `hatch_embryo` (`ui-entry.c:1755-1862`) — but **unreachable**: it's only called from

  except a branch nested inside that same check. So every record past the first falls into the no-op `else`
  (`UIEntryAssembler.java:259-261`), and `assemble()` returns an empty `results` for any file with more than one record.
- Even if reached, `parameteriseCategoryList` (`UIEntryAssembler.java:357-372`) would throw
  `IndexOutOfBoundsException` on any record with ≥1 `category:` line — it iterates
  `embryo.getCategories()` up to `embryo.getUiEntry().getCategories().size()`, but the embryo's list is hardcoded to

  `search_categories`/`search_embryo_categories`
  (`ui-entry.c:1377-1561`) anywhere in the file.
- `embryoHasMatch` (`UIEntryAssembler.java:374-384`) has no C counterpart — C's actual check in
  `parse_entry_name` is `streq(new_name, embryo->entry->name)` (`ui-entry.c:1888`), a same-name repeat-line check, not a
  category-name lookup. Also unreachable on its own terms since the list it searches is always empty.
- No port exists of C's "modify an existing entry" path — `ui_entry_lookup` +
  `embryo->exists = true` (`ui-entry.c:1906-1913`) plus the template category-merge (`parse_entry_template`,

- Faithful pieces: `uiEntryInsert`'s duplicate-name throw (`UIEntryAssembler.java:340-347`) matches

  `copyShortenedLabels` is a reasonable simplification of
  `copy_shortened_labels`/the `MAX_SHORTENED` buffer scheme for `String` vs. packed `wchar_t`.

### Where the create/override decision belongs, and the algorithm it implies

The comparison is a lookup against *the list being built*, not against the previous record, so it belongs in
`UIEntryAssembler` over its own `results` list — the only place that holds both the record stream in file order and the
running output. The loader stays as it is: `UIDataLoader`
hands `result.items()` to `UIRegistry.setUIEntries` afterwards. C's `entries[]` maps onto
`results`, `ui_entry_lookup` (`ui-entry.c:1193`) onto a name search of it, and `ui_entry_insert`
(`ui-entry.c:1204`) onto `uiEntryInsert`.

Because the grammar already hands over a whole block as one `UIEntryParseRecord`, C's per-line accumulation disappears
and the embryo collapses to three jobs: look up, edit-or-create, expand at the end. Per record: search `results` by
name; if found, reject any `parameter:` outright (`ui-entry.c:1994`), apply the template, overwrite the simple fields
the record sets, insert any category not already present, and resolve `index`/`negative_index` priority immediately
against the existing entry's own `param_index` — adding nothing to `results`. If not found, build the entry, reject the
record if it has no `combine:`, then emit `n` entries (1, `ELEM_MAX` or `STAT_MAX`), each named `name<PARAM>`, each with
its priority and category priorities resolved at that index, labelled from the record's label or else the parameter
name.

A third pass over everything is needed after the loop, per `finish_parse_ui_entry`
(`ui-entry.c:2281`): any entry with no label takes its name as the label, `fillOutShortened` fills the abbreviation
slots, and any category whose priority was never set takes the entry's default priority.

### Two-file parse: C shares one registry, the Java deliberately does not

`run_parse_ui_entry` (`ui-entry.c:2260`) parses `ui_entry_base.txt` into the *same* `entries[]`
array, hatches the last embryo, flags every entry `ENTRY_FLAG_TEMPLATE_ONLY` so it can never be displayed directly, and
only then parses `ui_entry.txt` into that same array. So `template:` and
`name:` in C hit one table. The Java splits these into `List<UIEntryBase>` and `List<UIEntry>` with separate readers,
which means the `name:` lookup only has to search the entry list and `template:`
only the base list. That divergence is safe for the shipped data — no name appears in both files — but it is a fact
about the data, not a guarantee of the format.

### Smaller mismatches found while reading the parameter/priority helpers

`UIEntryPriorityScheme` names its third scheme `"negative index"` where C's `priority_schemes[]`
(`ui-entry.c:157`) uses `"negative_index"`. Nothing reads that string today, since the assembler string-compares the raw
record text instead, but it will mismatch the moment the lookup routes through the enum.

`HelperFunctions.getElementCount()` returns `values().length - 1` while `getElementName` rejects index 0, so the valid
indices are 1..len-2 against a count implying 0..len-2. C's `element_names[]`
is a dense 0-based array of exactly `ELEM_MAX` entries, and the fan-out loop in `hatch_embryo`
indexes it from 0.

`UIEntryAssembler.embryo` is a `private static` field on a class whose `assemble` is an instance method.

### The embryo is not a comparison device ###

- It compares nothing against the previous entry. It is a per-block accumulator plus one bit:

    struct embryonic_ui_entry {
      struct  ui_entry *entry;                       /* the entry under construction OR an existing one */
      struct  embryonic_category_reference *categories;  /* only used when !e */
      int     param_index;        /* index into name_parameters[]: none / elemen stat */
      int     psource_index;      /* index into priority_schemes[]: none / index negative_index */
      int     last_category_index;/* -1 until the first category: line */
      bool    exists;            /* true == we are EDITING an entry already in entries[] */
    };

- The only lookup is a name search of the global registry, done once, at the
  `name:` line — `ui_entry_lookup` (`ui-entry.c:1193`), a binary search over      
  `entries[]`, which is kept sorted by name by `ui_entry_insert`
  (`ui-entry.c:1204`).
- Your grammar already does the embryo's other job (gathering `label:`,
  `category:`, `priority:` … across lines into one `UIEntryParseRecord`). What survives the port is only: look up,
  edit-or-create, expand at the end.

### The three modes at `name:` (`ui-entry.c:1881`) ###

- **Same name as the embryo in hand** → return immediately, keep accumulating into the same embryo. Degenerate; doesn't
  occur in the shipped data.
- **Name found in `entries[]` → `embryo->entry = entries[ind-1]; embryo->exists = true`**. The block is an **override of
  an entry already built**. Nothing is created; the existing object is mutated in place.
- **Not found** → fresh zeroed entry, `exists = false`.
- Either way: a *previous* embryo is hatched first, and `categories/param_index/psource_index` are reset,
  `last_category_index = -1`.

The real-world case is `lib/gamedata/ui_entry.txt:83` — `name:resist_ui_compact_0 + parameter:element`
hatches into `resist_ui_compact_0<ACID>` … `<DISEN>`; then `ui_entry.txt:99` onwards names those generated entries
directly to add `label:` and `category:CHAR_SCREEN1`. That is the "combining" you're seeing.

### What *exists* changes ###

- `parameter:` is **rejected** (`PARSE_ERROR_INVALID_OPTION`, `ui-entry.c:1994`) — you cannot re-parameterise a
  specialization.
- `category:` goes to `entry->categories` (final `category_reference`) when exists, to `embryo->categories`
  (`embryonic_category_reference`, carrying `psource_index`) when not. Both sorted by name, binary search,
  insert-only-if-absent (`ui-entry.c:2113`).
- `priority:index` resolves *immediately* against the entry's own `param_index` when exists; when not, the *scheme* is
  stored and resolution is deferred to hatch (`ui-entry.c:2132`).
- `priority:` before any category: sets `default_priority` + `psource_index`; after one, it sets the priority of
  `last_category_index` only
- Hatch does nothing but free the category scratch (`ui-entry.c:1755`).

### Hatching (only when `!exists`) ###    

1. `combiner_index == 0` → destroy the whole entry, return failure. Combiner is the one mandatory field.
2. `n = name_parameters[param_index].count_func() — 1, ELEM_MAX, or STAT_MAX`.
3. For `i = 0 .. n-2`: build a new entry named `name<PARAM_i>`; priority = `scheme(i)` if a scheme is set else the
   embryo default; categories via `parameterize_category_list(…, i, entry)`; label = embryo's label, or the parameter
   name if none; copy shortened labels; `ui_entry_insert`.
4. For `i = n-1`: **reuse the embryo's own entry object** (rename, label, `param_index = n-1`, priority), then insert.
5. Unparameterised → `n == 1`, loop body never runs, `param_index = -1`, single insert.

### The registry is shared across both files ###

`run_parse_ui_entry` (`ui-entry.c:2260`) parses `ui_entry_base.txt` into the same `entries[]`, hatches, flags every
entry `ENTRY_FLAG_TEMPLATE_ONLY`, then parses `ui_entry.txt` into that same array. So
`template:` (`ui-entry.c:1945`) and `name:` hit one table. Your Java splits these into
`List<UIEntryBase>` and `List<UIEntry>` with two readers — a deliberate divergence, but it means your
`name:` lookup only needs to search the entry list, and `template:` only the base list. That is fine and arguably
cleaner, because no shipped name appears in both files (I checked: `comm -12` on the two name lists is empty).

### `finish_parse_ui_entry` (`ui-entry.c:2281`) — a third pass over everything ###

- Any entry with no label gets its name as the label.
- `fill_out_shortened` fills each of the 10 abbreviation slots from the next-longest set slot, or truncates the full
  label.
- Any category whose `priority_set` is false gets the entry's `default_priority`, and is marked set.

### Q1 — where the comparison belongs ###

The **assembler**, over its own accumulating `results` list.

- The comparison is a lookup against *the list being built*, not against the previous record. It has to live wherever
  that list lives.
- The assembler is already the only place holding both the record stream in file order and the running output —
  `UIEntryAssembler.java:113` builds `results` and `UIEntryAssembler.java:114`
  already keeps embryo state.
- `ui_entry_lookup` ≡ "search `results` by name"; `ui_entry_insert` ≡ your `uiEntryInsert` at

  `UIRegistry.setUIEntries`.
- Putting it in the loader would mean mutating `UIRegistry` mid-load and splitting one algorithm across two classes, for

### Q2 — the algorithm, in record terms ###

Because the grammar hands you a whole block at once, the per-line accumulation disappears and it becomes:

                      otherwise      -> last category, resolving      
                                        index/negative_index against  
                                        existing.paramIndex NOW

        else:                                                                   
            # ---- CREATE PATH ----                                             
            build an embryo: blank UIEntry + embryonic category list carrying   
                             each category's unresolved priority scheme         
            apply template, then r's own fields (template first, r overrides)   
            if combine is absent -> error, skip record                          
            n = parameterCount(r.parameter())            # 1 / ELEM_MAX / STAT_MAX                                                                    
            for i in 0 .. n-1:

                                          else priority 0 + prioritySet=false)
                results.insert(entry)                    # sorted, reject duplicates
    # ---- FINISH PASS, after the loop ----
    for each entry in results:                                                  
        if label empty -> label = name                                          
        fillOutShortened(entry)

                                               prioritySet = tru
