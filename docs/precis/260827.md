# Precis — 2026-08-27

## Key points from the day

### The two review subtrees were cleared, and their documents deleted

Every finding in the `objectPower` and `noticeStuff` reviews was worked through and verified against the C original, and
the review documents were removed once nothing in them was outstanding —
`calcInventory_review.md`, `calcInventory_c_functions.md`, `objectPower_review.md`,
`objectPower_c_functions.md`, `objectPower_outstanding.md`, `noticeStuff_outstanding.md` and
`NoticeStuffBuglist.md`. Two things in those files were never defects and so were never fixed; they are recorded below
because the deletion leaves them without a written home.

### Two call sites are waiting on level generation

`Player.setCave` and `Chunk.setCurrentLevel` both exist and are both uncalled. In the original the player's known level
is allocated inside `prepare_next_level` — `p->cave = cave_new(chunk->height,
chunk->width)` at `generate.c:1241`, and the arena equivalent at `generate.c:1100` — which sizes it from the chunk,
copies the depth across, and reallocates and clears its object array. The port has not reached that function: the level
is still a hand-built stub in `GameEngine`, under its own TODO. When `prepare_next_level` is ported, both calls belong
at that allocation: `player.setCave(...)` for the new known level, and `setCurrentLevel(...)` on it for the real one,
the counterpart of the call
`GameEngine` already makes for the cave itself. Worth knowing that the original replaces the known level on every level
change and nulls it across the persistent-level swap, so code that reaches it has to keep tolerating an absent one.

### An object's origin had no starting value

`ItemObject`'s origin field was left unset by the no-argument constructor, where the original's is zero — the "no origin"
value. Nothing depends on it today: the full constructor sets it, the copy carries it across, and the one place that
compares two origins now uses identity rather than equality, so an unset value cannot throw there. It would begin to
matter if some objects reach the origin merge with the explicit "no origin" value and others with nothing set, because
the merge would read the two as different and mark the result mixed where the original would see them as the same.
Giving the field the "no origin" value was the whole of it, and the no-argument constructor now does so, with two tests
pinning that both construction routes agree.

### A unit-test pass over thirty-three classes, and the suite made to build again

Every method in the thirty-three named classes now has a test. The suite went from 2437 tests to 2802, in twenty-nine
new test classes, and finishes green.

It could not start until the existing tests compiled. They did not: twenty-seven errors across a dozen files, all of
them drift between the tests and the code they exercise. The curse constructor had changed one argument from a list to a
flag set, the flag class had renamed its membership test, and the pack had become a fixed-size array where it used to be
a growable list. The last of those was not a mechanical fix — four tests were written around adding to the pack, and had
to be rewritten around writing into a numbered slot, because a position in that array is the letter the player types
rather than a place in a queue. One genuine failure surfaced behind the compile errors, where a test compared a list
against a flag set and had been passing only because it never ran.

### What the tests are shaped around

The classes divide into three kinds, and each wants a different sort of test. The data holders — the power tables, the
archery rows, the object property — are mostly several same-typed integers in a row, where a transposed constructor
argument would compile, load and silently misprice everything; those get every field read back through its own accessor,
with values distinct enough that a transposition cannot pass. The classification methods get their whole membership
asserted rather than one member, because the risk is a missing case rather than a wrong answer. And the methods with
real behaviour get their edges: what happens at the boundary, what happens when the thing is absent, and what happens on
the path the code takes when it is not the obvious one.

The scalar constants were the largest single block — sixty-eight accessors, each a two-hop delegation into one of
thirteen records, several of which repeat a field name. Rather than transcribe them, the delegations were read out of
the source and the assertions generated from that, with every constant in the whole structure given a distinct value so
that a single mis-delegation fails and names itself.

### Five things the tests found in the code, all now settled

A real defect in monster compaction: the loop that excises dead monsters starts one past the end of the array and runs
one too far at the other end as well, so it throws on a level with no monsters at all — even when asked to compact none.
The original starts one lower and stops one higher, because its slot zero is the "no monster" entry and is never
compacted. Recorded as a test asserting the throw, so it fails the day the bounds are corrected and becomes a test of
what compaction does.

Two divergences from the original, both recorded the same way. Browsability asks whether an object is a book of any kind
with a matching sub-type, where the original asks whether it is *that* book — so a prayer book sharing a sub-type with a
mage's spellbook reads as browsable. And the flavour load reads the table but never attaches a flavour to anything, so
every potion is nameless where the original would have shuffled the colours out from a fixed seed.

A missing `return` in the spellbook's sub-type resolution, which sets a sentinel for the not-found case and then falls
straight through to dereference the thing it did not find.

And a family of methods that assume a fully loaded game and dereference straight through: the item copy needs its dice,
the absorb needs the player's rune knowledge, the object kind's copy needs a dozen members the parser fills in
afterwards. None is wrong, but each is a precondition nothing states, and the fixtures now say so in a comment at the
point they satisfy it.

### Three of my own comments were wrong, and are corrected

The notice dispatcher does not leave a combine pending for the next turn, as its comment claimed:
the combine block sits after the ignore block, so the combine that the ignore pass asks for is carried out in the same
pass. What clearing each flag before its work actually buys is the ability for an action to re-raise its *own* flag.

The pack ordering comparison is fully ported, not "only the readable-book rule" — the whole chain is there, and the
comment now lists it in order.

And an ego's ignore categories are not sparse: the constructor fills every one of them, which is what makes the
accessor's direct unboxing safe.

Each was written earlier the same day, from a reading of the code rather than from running it. That is the lesson worth
keeping: a comment describing behaviour is a claim, and a test is the only thing that checks it.

### What the tests deliberately do not cover

Six methods await their subsystems and are tested only to the extent of recording that they do nothing — the
timed-effect sink and the three that funnel through it, the turn-loop entry points, and the level's monster placement.
Where a stub makes a written method inert, the test says so: the decrement of a timed effect computes the right answer
and then hands it to an unported sink, which looks like a broken method rather than a waiting one.

### The five defects the tests found were worked through

Every open defect from the morning's test pass was taken in turn, checked against the C original and either fixed or
deferred with its reasoning written down. Four are closed and one — the flavour work — turned out to be a subsystem
rather than a fix, and went to the roadmap instead.

Each fix replaced the test that had recorded the divergence with tests of the corrected behaviour, so nothing that was
asserted "as it behaves" is still standing. The suite went from 2802 to 2808 and stayed green throughout.

### Monster compaction had four faults, not the two that were recorded

The excise loop was recorded as having both bounds wrong; reading it beside the original turned up two more. The index
it hands to the move was one too high as well, and the test that decides which slots to fill was the wrong way round —
it skipped the holes and relocated the live monsters, which is the opposite of what compaction is for.

All four are corrected. The test that asserted the crash is now three tests of what the loop does, though what they can
observe is limited to the high-water mark, because the move itself and the deletion beneath it are both still stubs.

### An unused test rules out nothing

Browsability compared "is this a book of any sort" where the original compares "is this *that* book", so another realm's
book with a matching sub-type read as readable. The right comparison already existed a few files away, in the method
that resolves a carried book to its class entry.

Both halves of the pair are now matched, and the type test that stood in for the missing half has gone. What made the
old test weak is worth keeping in view: it asserted one true case, where the risk was a second case wrongly answering
true, so the replacement asserts the refusals as well as the acceptance.

### One fixture where there were seven

Seven test classes each built a loaded item by reflection, with field lists that had begun to drift apart, and six of
them separately filled an object kind's dice. The methods they were all working around are the ones that assume a
loaded game and dereference straight through.

There is now a single builder in `testsupport`, and all seven use it. It builds through the data-file constructor
rather than by reflection, which resolves the dice strings the parser would have resolved — so the copy's precondition
stops existing rather than being satisfied by hand, and a new test asking about items starts from a neutral one instead
of rediscovering the list.

### Reading a deferred item is still worth doing

The flavour work was too large to take on and was written up for chapter 7. Reading it properly first was what turned up
its two blockers — the flavour seed is declared but has no accessor, and there is no counterpart to the second RNG the
original switches to — and a defect beside it, where an object kind's copy dereferences a flavour that is optional by
design.

The roadmap entry carries all of it, split into the pieces the original runs in order, so the work can be picked up cold.
The defect is listed separately because it is wrong today rather than waiting on anything.

## Things not to drop

- `Player.setCave` and `Chunk.setCurrentLevel` are wired but uncalled; both calls belong in the port of
  `prepare_next_level`, at the point the known level is allocated.
- The known level is replaced on every level change and nulled across the persistent-level swap, so this subsystem must
  keep tolerating an absent one rather than assuming it exists once generated.
- The test suite is 2808 tests and green; the whole of it must compile before any of it runs, so drift in one test file
  blocks the lot.
- Chapter 7 of the roadmap now carries everything deferred today — the spellbook's missing call site, the four pieces of
  flavour assignment, the flavour seed's two blockers, and the unguarded flavour copy — and is the only place they are
  tracked.
- The flavour copy is the one of those that is wrong today rather than blocked on anything, so it is the obvious first
  move next session.
- `MagicBook.setSVal` is now correct and public but still called from nowhere, so every book's sub-type reads zero until
  the call site lands.
- Compaction's move and the deletion beneath it are both still stubs, so its tests can watch the high-water mark and
  nothing else.
- `testsupport/ItemFixture` is the one place a loaded item gets built; a new test that needs one should reach for it
  rather than write another reflective builder.
- A comment describing behaviour is a claim: three of mine were wrong until a test checked them.
