# Precis — 2026-09-29

## Key points from the day

### Javadoc and tests for the EVENT_MONSTERHEALTH sidebar row

Today's pass finished the port of the sidebar's monster health bar - C's `prt_health`, `prt_health_aux` and
`monster_health_attr` - covering the new `EventDataMonsterInfo` payload, `eventSignalMonInfo`, the `PR_HEALTH` arm in
`PlayerCalcs.redrawStuff`, `RedrawRouter.setMonsterHealth`, the twelve monster fields on `SidebarModel`, and the drawing
logic in `HandlersHolder`. A verify pass caught that the healthy colour at 100 per cent was `COLOUR_GREEN`
where C uses `COLOUR_L_GREEN`, and `HandlersHolderTest` still counted seventeen side-handler rows. Rowan fixed the
colour and the new `HealthBarTest` pins the star-count thresholds, colour boundaries and timed-effect override order to
C's values, with the stale row-count test updated to twenty. The row is now documented, tested and green, so the next
sidebar rows, speed and depth, inherit both the twelve-field payload pattern and its test template.

### Javadoc and tests for the EVENT_PLAYERSPEED sidebar row

The sidebar's speed row - C's `prt_speed` and `prt_speed_aux` - now runs on the message path, through the new
`EventDataPlayerSpeed` payload, `eventSignalPlayerSpeed`, the `PR_SPEED` arm in `PlayerCalcs.redrawStuff`,
`RedrawRouter.setPlayerSpeed`, four `SidebarModel` fields and the drawing in `HandlersHolder`. The verify pass matched C
clause by clause, and the extract-energy table in `ChannelRegistry` matches `game-world.c` across all 200 entries. The

two row-count tests that predated the row were updated to twenty-one. Only `prt_depth` is left in the table, and the
next dispatcher port must draw this row only on its own event, because the model starts at speed zero.

### Javadoc and tests for the UIPlayer character-sheet panels and `cnvStat`

This pass verified `UIPlayer`, the port of C's `ui-player.c` character-sheet driver - the five `getPanelX` builders, the
panel helpers, `configureCharSheet`, `displayPlayerStatInfo` and `cnv_stat`. The verify pass found that `cnvStat`'s
`len` truncation was first one character too generous and then, after a first fix, threw on every call, so it would have
crashed the stat rows in `displayPlayerStatInfo` and `HandlersHolder`. Rowan changed the bound to `len - 1`, matching
`strnfmt`'s reservation of the terminator byte, and the Javadoc now records that plus several stale claims that the
builders were stubs. Nine `CnvStat` tests, four of them new, pin the truncation at lengths 1, 2, 6, 7, 32 and 80 to
`strnfmt`'s behaviour, so the next port that calls `cnvStat` with a real buffer size inherits a checked boundary.

### Javadoc and tests for `UIEntryAssembler`

This pass verified `UIEntryAssembler`, the second stage of the `ui_entry.txt` pipeline, against C's `hatch_embryo` and
the `parse_entry_*` callbacks. The verify pass found that the create path dropped each record's own flags, so all
thirteen `resist_ui_compact_0<TAG>` entries lost `TIMED_AS_AUX`, and Rowan's first fix then threw a NullPointerException
on every create until it copied the incoming entry's flags instead. Sixteen new tests, taking the class to 28, pin
flags, combiner rejection, label and priority defaults, template inheritance and the override merge to C's values, so
the remaining latent divergences listed below are the only known gaps between the assembler and C.

### Javadoc and tests for `UIEntryReader`

`UIEntryReader` is the thin first stage of the `ui_entry.txt` pipeline, and it has no single C original: it covers the
`ui_entry.txt` half of `run_parse_ui_entry`, while `UIEntryBaseReader` and `UIDataLoader` carry the base-file read and
the ordering between the two. The verify pass found no divergence, and the class, its logger and all three methods now
say so, including that a hard syntax error returns an empty list and the assembler seeds from `UIRegistry`. Five new
tests pin the record-count check, the `parse`/`parseWithResults` agreement, the missing-file `IOException` and the
fail-closed path without depending on the assembler's disabled insert cases, so the reader's own contract no longer
waits on those three skips.

## Things not to drop

- `Monster.setHp`/`setMaxHp`/`updateCached` still write the legacy `PlayerEventStatusUpdate` cache; they go when the
  cache-to-messages migration removes it.
- `UIEntryAssembler.parseEachEntry` has latent divergences from C that no shipped `ui_entry.txt` record reaches: on the
  override path, a `priority:` before any category sets a category's priority instead of the default, `index` on a
  non-parameterised entry gives 0 where C gives -1, and template flags are never copied.
- On the create path, the template's default priority and each template category's priority and `priority_set` are
  replaced by the record's own values, and a template's flags overwrite the record's own instead of being OR'd with
  them.
- `UIEntryAssembler` also keeps categories in insertion order where C sorts by name, throws on an out-of-range
  `priority:` where C clamps, emits one "no combiner" error per element where C emits one, and quotes `getFirst()` in
  the bad-flag message.
