# Precis — 2026-10-19

## Key points from the day

### `TerrainReader` checked against the terrain parser in `init.c`

`TerrainReader` feeds `terrain.txt` through the grammar and assembler into `Feature` objects, standing in for `init_parse_feat`, `run_parse_feat` and the list-building half of `finish_parse_feat`. It already matched C: all 25 records load in file order with every code and name agreeing with the upstream file, eight carry the shop flag and one mimics, and a missing file is an `IOException` where C quits; the committed `TerrainFeatureLexer` and `TerrainFeatureGrammar` parser has the same ATN as a fresh generation, so nothing needed regenerating. The class, the logger and the three methods now say which C function each stands in for, which half of `finish_parse_feat` lives in the assembler and the loader, and where the port deliberately differs, and `TerrainReaderTest` grows from 12 to 39 tests that pin the contract, a 25-row table and each difference found. The grammar differences are written up in `docs/grammar_issues.md`, `TerrainFeatureAssembler` needed no new note, and the terrain reader is the twelfth of batch 3 in `docs/ReaderPort.md`.

### `WorldReader` checked against the world parser in `init.c`

`WorldReader` feeds `world.txt` through the grammar and assembler into `World` records, standing in for `parse_world_level` and `run_parse_world`, with `finish_parse_world` done by `WorldDataLoader`. The check found an unguarded parse of the `record-count:` header that let a huge number escape as a raw `NumberFormatException`, and a hard count check that no other reader makes. The header now goes through the shared `GrammarDriver.checkRecordCount`, so a bad count is a soft error and the levels still load, while an overflowing level number stays hard. The class, logger and methods now say what each stands in for and where the port differs, `WorldReaderTest` grows from 5 to 26 tests that pin the soft and hard cases and each place C is more lenient, and the grammar differences are written up in `docs/grammar_issues.md`; `WorldAssembler` needed no new note.

### `GameConstantsReader` checked against the constants parser in `init.c`

`GameConstantsReader` feeds `constants.txt` through the grammar and `GameConstantsAssembler` into one `GameConstantsData`, standing in for `init_parse_constants`, `run_parse_constants` and `finish_parse_constants`. It already matched C: the real file loads clean, an empty or comment-only file loads all zeroes as C's zeroed struct does, any error means no constants, and a missing file is an `IOException` where C quits. The class, logger and both methods now say which C function each stands in for, where the cutoff check lives and where the port differs, and `GameConstantsReaderTest` grows from 6 to 24 tests that pin the contract, the cutoff rule and each difference found. The grammar differences (a field after the value, indents, hex and octal values, lower-case message names, a last-line comment with no newline) are written up in `docs/grammar_issues.md`, and the assembler's acceptance of negative values and its overflow wording in `docs/Assembler_Issues.md`.
