# Precis — 2026-10-13

## Key points from the day

### `DungeonLoader.java` checked against `run_template_parser` in `generate.c`, `finish_parse_profile` and `parse_file_quit_not_found`

`DungeonLoader` reads the dungeon profiles, room templates and vaults, the three parsers C runs from `generate_module`. Its Javadoc still said an unreadable file was "logged and swallowed" and that data problems were never fatal, although each loader now throws a `RuntimeException` naming the file on an `IOException` or on a parse that leaves errors and no records. You had already made that change in the code, so the class, the logger and all three methods now carry Javadoc recording the throw, the one deliberate softening of C (records that survive soft errors are installed) and the user-directory lookup that C's `parse_file` makes and the port does not. `DungeonLoaderTest` pins the nine profiles, 500 templates and 162 vaults against C's data in file order, the recorded profile count, the vault `max-depth:0` rewrite, a reload replacing rather than appending, and a missing file or a soft-error-only file stopping each loader before the registry is written. A later change to the failure handling, or to the order the loaders run in, will show up in that test.

### `MiscDataLoader.java` checked against `run_parse_flavor`, `run_parse_hints`, `run_parse_names` and `parse_file_quit_not_found`

`MiscDataLoader` reads `flavor.txt`, `hints.txt` and `names.txt` into `MiscRegistry`, standing in for the three C parsers that `init_arrays` runs. Its loaders used to log an unreadable file and carry on, which left the registry unset until something read it, where C quits as soon as the file cannot be opened. You changed all three to throw a `RuntimeException` naming the file, on an `IOException` or on a parse that leaves errors and no records, so the class, the logger and the three methods now carry Javadoc recording that throw, the one softening of C (records that survive soft errors are registered) and the user-directory lookup the port does not make. The names test now pins the throw instead of the swallow, and new hint and flavour tests pin the good file, the missing file, the hard grammar error and the soft-error path against the registry, with the shipped `hints.txt` checked against C's 99 hints. Your change to `HintGrammar.g4`, letting a hint file hold zero hints as C does, made the `loadHints` Javadoc and its empty-file test wrong, so both now record that a `record-count:0` file loads an empty list while a header promising missing hints still stops start-up. You then made the same change to `NamesGrammar.g4`, so an empty names file and a `section:` with no words now load as in C, and the names test pins both. A change to how a failed load is handled, in any of the three loaders, will show up in those tests.

### `MonsterDataLoader.java` checked against the `finish_parse_*` functions in `mon-init.c`, `mon-summon.c`, `ui-visuals.c` and `parse_file_quit_not_found`

`MonsterDataLoader` reads the nine monster-domain files into `MonsterRegistry` and gives every race its lore record, standing in for the nine C parsers that `init_arrays` and the visuals module run. Its Javadoc still said six of the loaders logged and swallowed an unreadable file, that only pain, bases and summons rethrew, and that a failed visuals parse reached `getFirst()`, although each loader now throws a `RuntimeException` on an `IOException` or on a parse that carries errors and no records. The class and all nine methods now record that single rule, the one softening of C (records that survive soft errors are registered), and you then removed the `throws IOException` clauses from `loadPain`, `loadMonsterBases` and `loadSummons`, which could never throw it. A new failure-paths test pins a missing file for all nine loaders and the three outcomes of the error check, and a registry test pins 624 races, 12 pain sets, 19 blow methods, 30 effects, 40 pits and a blow maximum of nine against C's data. A later change to how a monster file failure is handled, or to what the second pass resolves, will show up in those tests.

## Things not to drop

- `GameConstants.java`: the comment on the `loadPitProfiles` call says it depends on the spell types, but the pit assembler resolves `spell-req:` and `spell-ban:` against the `MonsterSpell` enum.
- `DungeonLoader.java`: the three loaders read only the gamedata directory, where C's `parse_file` tries a customised copy in the user directory first, so a hand-edited file there is ignored.
- `MiscDataLoader.java`: the same user-directory lookup is missing from the three misc loaders.
- `NamesGrammar.g4`: a `word:` line before any `section:` line is still a hard error, where C files it under section zero.
