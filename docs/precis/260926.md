# Precis — 2026-09-26

## Key points from the day

### UIPlayer.showAdvanceExperience verified and ported

A `/port` pass targeted `UIPlayer.showAdvanceExperience`, the mid-left panel's "Adv Exp" value. The first verify pass
found two real discrepancies against C's `show_adv_exp`: an off-by-one indexing the experience-to-level table at the
player's level instead of level minus one, and a format string with no `%` conversion at all, so the computed figure was
never actually written into the returned string. Both were fixed by Rowan, and a re-verify found the method matching C
clause for clause.

Full Javadoc was written for the method, plus a new `ShowAdvanceExperience` nested group in `UIPlayerTest` covering the
ordinary path, the level-1 off-by-one boundary, C's truncating integer division, and both edges of the level cap.
Getting the suite green afterward also required updating five pre-existing call sites across three other test files that
hadn't caught up with `PlayerCharSheetView`'s new `expFactor` field, plus a fixture gap in `UIPlayerTest`'s
`Constructor` group that the fix's real array access exposed.

The character sheet's "Adv Exp" line now reports the correct figure instead of a broken literal, and carries regression
coverage tying it to C's own formula, so a future change to the experience-to-level table's shape will be caught
immediately.

### Panel.space verified and ported

A `/port` pass targeted `Panel.space()`, the character sheet panel builder's blank-row spacer. The first verify pass
found the method only incrementing its row count without ever adding a row to the backing list, so the two silently fell
out of step and every row appended after a spacer would land in the wrong slot instead of after the blank one — a real
discrepancy against C's pre-zeroed array, where `panel_space` simply walks past a slot that already exists. Rowan fixed
it by having `space()` append an explicit blank row of its own, and a re-verify found the method matching C clause for
clause.

Full Javadoc was written for the method itself plus the class and fields it touches (`len`, `max`, `lines`), and a new
`SpaceMethod` nested group was added to `UIPlayerTest` covering the blank row it appends, row ordering around a spacer,
and the capacity guard it shares with `panelLine`.

No renderer reads a `Panel`'s rows yet, so the bug had caused no visible harm so far, but it would have silently
misaligned every row placed after a spacer the moment `display_panel` is ported; that risk is now closed and carries
regression coverage of its own.

### UIPlayer.getPanelMidLeft and UIPlayer.showDepth verified and ported

A `/port` pass targeted `UIPlayer.getPanelMidLeft` and its "Max Depth" helper, `showDepth`. The first verify pass found
one real discrepancy: the Burden row's label was misspelled and its value format string carried no valid conversion at
all, so building the panel would have thrown at runtime the first time it ran; `showDepth` itself already matched C's
`show_depth` clause for clause. Rowan fixed the label and format string, and a re-verify found the method matching C's
`get_panel_midleft` row for row.

Full Javadoc was written for both methods, plus several now-stale cross-references elsewhere in the file that had
described `getPanelMidLeft` as still a partial stub. Getting the suite green afterward also required updating six
pre-existing call sites across three test files, plus a static-initializer default-value check, that hadn't caught up
with `PlayerStatusView`'s new `maxDepth` field.

New `GetPanelMidLeft` and `ShowDepth` nested groups were added to `UIPlayerTest`, checking all nine of the panel's rows
in C's order with matching colours and formatted values, and both of `showDepth`'s branches. The mid-left panel now
builds cleanly instead of throwing, and both methods carry regression coverage tying them to C's own formula.

### UIPlayer.getPanelMisc verified and ported

A `/port` pass targeted `UIPlayer.getPanelMisc`, the character sheet's age/height/weight/turn-count panel. The first
verify pass found one real discrepancy: the Height row's format string dropped C's trailing literal inch mark, so a
height like 5'11" would have rendered as 5'11 with no closing quote at all. Rowan restored the missing mark, and a
re-verify found the method matching C's `get_panel_misc` row for row.

Full Javadoc was written for the method. Getting the suite green afterward required updating eighteen pre-existing call
sites across four test files that hadn't caught up with `PlayerStatusView`'s three new turn/energy/resting-turn fields
and `PlayerCharSheetView`'s three new height/weight/age fields, plus a handful of now-stale cross-references elsewhere
in `UIPlayerTest` that had described `getPanelMisc` as still a stub.

A new `GetPanelMisc` nested group was added to `UIPlayerTest`, checking all seven of the panel's rows in C's order with
matching colour and formatted value, including the restored inch mark. The misc panel now builds cleanly with the
correct display format, and carries regression coverage tying it to C's own formula; three of the five character sheet
panels (top-left, misc, mid-left) are now fully ported, leaving only combat and skills as stubs.

### UIPlayer.getPanelCombat verified and ported

A `/port` pass targeted `UIPlayer.getPanelCombat`, the character sheet's armour/melee/ranged panel. The first verify
pass found three real discrepancies against C's `get_panel_combat`: the ranged to-hit figure was missing the same
`* 10` scaling C applies before dividing by `BTH_PLUS_ADJ`, the Blows row's format string used a full stop instead of a
forward slash before "turn", and the melee To-hit label carried a stray capital H not present in C's own string. Rowan
fixed all three, and a re-verify found the method matching C row for row; the equipped-weapon lookup C performs inline
was confirmed to belong further upstream, where `PlayerCharSheetView`'s combat fields are populated, keeping this method
a pure formatter like its three already-ported siblings.

Full Javadoc was written for the method. Getting the suite green afterward required updating eight pre-existing call
sites across three test files that hadn't caught up with `PlayerCharSheetView`'s ten new combat fields, a
static-initializer default-value check with the same gap, and one `UIPlayerTest` fixture and assertion that still
described `getPanelCombat` as a null-returning stub. The suite run also turned up an unrelated architecture-boundary
failure — a leftover unused import naming a middle-layer type from `UIPlayer.java` — which Rowan approved removing.

A new `GetPanelCombat` nested group was added to `UIPlayerTest`, checking all nine of the panel's rows in C's order with
matching colour and formatted value, chosen deliberately to catch a regression on either of the two original formatting
bugs. Four of the five character sheet panels (top-left, misc, mid-left, combat) are now fully ported, leaving only
skills as a stub.

### UIPlayer.likert verified and ported

A `/port` pass targeted `UIPlayer.likert`, the shared rating-and-colour helper the skills panel calls for its Stealth
row. The first verify pass found two real discrepancies against C's `likert`: the "Good" and "Very Good" bands were
coloured green and blue respectively, where C colours both of them yellow. Rowan fixed both, and a re-verify found the
method matching C's `switch` clause for clause.

Full Javadoc was written for the method and for the `StringAndColour` record it returns, which stands in for C's
string-return-plus-out-parameter pair. A new `Likert` nested group was added to `UIPlayerTest`, checking the negative-
skill early return, the non-positive-level guard, every one of the eleven rating bands with its correct colour, and C's
truncating integer division. Getting the suite green also required Rowan to finish an in-progress edit to
`getPanelSkills` blocking compilation, and to drop two calls to `PlayerCharSheetView` accessors (`saveSkill`,
`stealthSkill`) that don't exist on that record yet.

The skills panel's Stealth rating now uses the same colours as the original for its two middle bands, and `likert`
carries regression coverage tying every band to C's own formula; `getPanelSkills` itself remains unfinished and is not
part of this pass.

### RedrawHandlers, EventsHandler.eventSignalStat, PlayerCalcs.redrawStuff and Core.gameLoop verified and ported

A `/port` pass targeted the first slice of the redraw-to-message migration: the new `RedrawHandlers` class,
`EventsHandler.eventSignalStat`, `PlayerCalcs.redrawStuff`'s `PR_HP` special case, and `Core.gameLoop`'s wiring of the
new handler. None of these has a single C function to diverge from — C's UI handlers read hit points straight off the
shared player global rather than receiving them — so the verify pass checked each against the existing `InitHandlers`/
`eventSignal*` patterns instead, and found every one matching.

Several pre-existing Javadoc blocks had gone stale under the new code: `redrawStuff`'s doc still claimed the map was the
only event carrying data, and `Core`'s doc on `coreChannel` and `gameLoop` still described the core sender reaching only
`InitHandlers` and only twice over. All were rewritten, alongside full new Javadoc for `RedrawHandlers` and
`eventSignalStat`.

Regression coverage was added in three places: a new `RedrawHandlersTest`, a new stat-signal case in
`EventsHandlerSignalTest`, and a new case in `PlayerRedrawStuffTest` tying `PR_HP`'s payload to the player's actual hit
points. The full suite (5,521 tests) is green.

`EVENT_HP` is now proven end to end across the new core-to-front-end message boundary, the template the rest of
`PlayerRedraw`'s flags will follow as their own payload records get ported.

### RedrawRouter, SidebarModel, UILoop.loop () and UIPlayer.getPanelTopLeft () verified and ported

A `/port` pass targeted the front-end half of the `EVENT_HP` slice: the new `RedrawRouter` and `SidebarModel` classes,
`UILoop.loop()`'s routing arm, and `UIPlayer.getPanelTopLeft()`'s HP row. The routing classes have no single C function
to diverge from, but tracing the HP row's real source all the way back through `PlayerCalcs.redrawStuff` to `Player`
confirmed `getPanelTopLeft` still matches `get_panel_topleft` row for row, so the verify pass found no discrepancies.

Full Javadoc was written for `RedrawRouter` and `SidebarModel`, both previously undocumented at class, field and method
level, and a stale sentence in `getPanelTopLeft`'s own block - written before today's change, still describing HP as
coming from the same cached view as the other rows - was corrected and re-dated. This is today's first field moved off
the shared-cache view onto its own front-end model, the pattern the rest of `PlayerStatusView`/`PlayerCharSheetView` is
expected to follow as it is architected out.

New `RedrawRouterTest` and `SidebarModelTest` classes were added, plus a `RoutingGameEvents` group in `UILoopTest`
exercising an `EVENT_HP` message end to end into the model. The existing `GetPanelTopLeft` fixture in `UIPlayerTest` was
corrected to install its expected HP through `SidebarModel` rather than the now-bypassed `PlayerStatusView`, with a
deliberately wrong HP pair left in the view fixture so a regression back to reading it from there would be caught. The
full suite (5,528 tests) is green.

The read side of the `EVENT_HP` message path is now proven end to end alongside the write side proven earlier today, and
the corrected fixture is the template for updating `UIPlayerTest`'s other panels as their own fields migrate off the
shared-cache views.

### PlayerCalcs.redrawStuff, RedrawHandlers, RedrawRouter, SidebarModel, UIPlayer.getPanelTopLeft () and UILoop.loop () extended for
`EVENT_MANA`

A `/port` pass verified the second slice of the redraw-to-message migration, run alongside the `EVENT_HP` one above:
`redrawStuff`'s `PR_MANA` case, `RedrawHandlers`' `eventSP` handler, `RedrawRouter.setSP`, `SidebarModel`'s SP pair, and
the SP row in `getPanelTopLeft`, all wired through `UILoop.loop()`'s `EVENT_MANA` arm. The whole chain already existed
in code by the time this pass started, and the verify found it matching C's `prt_sp`/`get_panel_topleft` exactly,
mirroring the already-proven HP path field for field.

The Javadoc across all five classes had not caught up with the code, still describing each as wiring `EVENT_HP` alone,
and `UIPlayerTest`'s `GetPanelTopLeft` fixture had not been updated either: it only seeded `SidebarModel`'s HP pair, so
the SP row it asserted on was silently reading whatever the previous test had left behind rather than its own fixture
value. Every stale block was rewritten, and the fixture was corrected to seed both pairs independently, with a
deliberately mismatched SP value left in the bypassed view so a regression back to reading it from there would be
caught.

New SP-side tests were added to `RedrawRouterTest`, `SidebarModelTest`, `RedrawHandlersTest` and `UILoopTest`, mirroring
each file's existing HP coverage. The full suite (5,538 tests) is green, and `EVENT_MANA` is now proven end to end
alongside `EVENT_HP`, leaving the remaining `PlayerRedraw` flags to follow the same now-twice-proven template.
