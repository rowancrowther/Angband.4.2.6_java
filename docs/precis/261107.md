# Precis — 2026-11-07

## Key points from the day

### ArtifactAssembler.assemble

`ArtifactAssembler.assemble` builds each `Artifact` from its parsed record and finds or makes the special kind behind its `base-object:` line, standing in for the `parse_artifact_*` handlers and `write_dummy_object_record` in `obj-init.c`. It matched C on every input walked through. The one difference found, a numeric `base-object:` sval naming no kind, could not come from a file, because the grammar refuses a numeric sval first. That difference was recorded as an accepted deviation and the `assemble` Javadoc was rewritten around it, with the dead `levelFirst`/`baseObjectLevel` links replaced and the `msg:` null note corrected. A test for C's name-versus-character graphics colour match was added, and the no-`base-object:` test now expects "no assigned bases". `ObjectKindAccessorsTest` now expects the zero `Random` a bare kind holds in place of `null`. A later change to the kind lookup or the grammar's `base-object:` rule should re-check that accepted deviation first.

### EgoItemAssembler.assemble

`EgoItemAssembler.assemble` builds each `EgoItem` from its parsed record, standing in for the `parse_ego_*` handlers in `obj-init.c` and the numbering in `finish_parse_ego`. It matched C on every input walked through, so no code changed. The one place the two differ in shape, an element flag word skipping the object and kind flag lookups that C also runs, cannot be reached because no object or kind flag name reads as an `IGNORE`/`HATES` word followed by an element. The `assemble` Javadoc now records that, and the blank-slot note for the brand, slay and curse lookups, and `EgoItemReaderTest` gained a test for the 40-character dice limit that C's `find_value_arg` sets on `values:` brackets. A new flag or element name shaped like `IGNORE_<element>` would make that skipped lookup matter and should re-check it.

### ObjectRegistry.java

`ObjectRegistry` holds the object-domain tables and the lookups standing in for `lookup_kind`, `lookup_sval`, `lookup_curse`, `lookup_obj_property`, `findact` and `max_runes`, plus the `obj-power.h` constants. Every lookup, counter and constant matched C on the inputs walked through, so no code changed, but the `getObjectBases` Javadoc carried the wrong method name, and the `lookup_kind` note claimed a (tval, sval) pair is never shared when kinds with no base share one. The class comment now records the accepted blank-slot deviation, and the affected blocks were rewritten against what C does, including `ordinary_kind_max`, `act_max` and the two sentinels C resolves that this class does not hold. `ObjectRegistryFirstMatchTest` was added for the kind ceiling, first-match-wins on duplicate names, and leading-blank and blank-only references. A change to how `addObjectKind` indexes base-less kinds, or to where the ceiling is recorded, should re-check that note.

### ObjectKind.java

`ObjectKind` is the port of `struct object_kind`, with three live constructors standing in for `write_book_kind` and `finish_parse_object`, and a run of setters that now build the kind behind a special artifact in place of the old `write_dummy_object_record` constructor. Every field, constructor and setter matched C on the inputs walked through, so no code changed, but the class comment still described the commented-out artifact constructor, and the no-argument constructor, `time`, `copy` and `setTval` blocks said things the code no longer does. The class, field and affected method blocks were rewritten, six undocumented setters were given Javadoc, and the `getCharacter` stamp that named the wrong function was corrected. `ObjectKindSetterContractTest` was added for the no-argument shell, the naming, base, flag and element setters, and the aware-bit setter, and the stale `halfBuiltKindCannotBeCopied` comment was corrected. A change to how `ArtifactAssembler` builds the special kind, or a return of the artifact constructor, should re-check those blocks.

### TValue.java

`TValue` is the port of `list-tvals.h` and `obj-tval.c`: the 36 `TV_*` constants, the `tval_is_*` and `tval_can_have_*` predicates, `tval_find_idx`, `tval_find_name` and the two kind counters. The constants, predicates, number path, `findName` and both counters matched C on the inputs walked through, but `changeArmour` rewrites the wrong `armour` when a capitalised one comes first, and `fromName` accepts a constant's identifier where C returns -1. Neither is reachable from shipped data, so both were accepted as deviations and recorded under "Tval" in `docs/Accepted_Deviations.md`; no code changed. The `changeArmour` and `fromName` Javadoc now state both deviations and the corrected count of British spellings in the data files, and `TValueLookupTest` gained cases for `-0`, a sign with no digits, two lowercase `armour`s, and the two deviations. A change to the identifier path or to how `changeArmour` finds its match should re-check those entries.

### ParseUtils.java

`ParseUtils` is the shared number and text reader behind every assembler: the `strtol`/`strtoul` base 0 and fixed base 10 readings, the sign and digit tests, the trimmers, `grabElementFlag` and the glyph reader. It matched C on every input walked through, including a fresh run of `strtol` over the awkward prefixes, but its Javadoc named the wrong callers for `cTrim`, `trimRearOnlySpaceAndTab` and the `Radix` form, said `parser_getint` reads the text when `parser_parse()` does, and left `parseADCGlyph` and `GlyphCharacter` undocumented. Those blocks are corrected and the glyph reader is described against C's `PARSE_T_CHAR` reading, with the stale claim about the 0 to 255 `alloc:` check narrowed to ego items and artifacts. A new test class covers the glyph reader and six `strtol` inputs the main table lacked, so the caller lists in the Javadoc are now the thing to keep in step when an assembler changes.

### ParseUtils.parseADCGlyph

`parseADCGlyph` turns the glyph text of an artifact's `graphics:` line into the `GlyphCharacter` that `ArtifactAssembler` stores as a kind's display character. Its Javadoc and one test said text after the first code point was ignored, while the code returns `null` for more than one code point, so the test failed and a precis note recorded a divergence that did not exist. The code was right: C's `parser_parse()` fails the line with `PARSE_ERROR_FIELD_TOO_LONG` when anything but a colon follows the first character, and the glyph token reaches Java without one, so both refuse. The Javadoc now says "refused" and a parameterized test pins `"ab"`, a letter with a combining mark, and a supplementary glyph with a letter either side. Going forward, the three refusals (too long, empty, `null`) arrive at the caller as the same `null` and the same fatal message.

### ObjectBaseAssembler.assemble

`ObjectBaseAssembler.assemble` turns the parsed `object_base.txt` records into `ObjectBase`s, standing in for the `parse_object_base_*` handlers and the zeroed slot `finish_parse_object_base` leaves. It matched C on every input walked through, but its Javadoc said a flag with an element-style prefix and no such element is fatal "where C would go on to the other two tables", when the code goes on to them too, and it did not say that a record with no colour is dark. The two paragraphs are corrected, the Javadoc also names the one colour name (`Shade`) that resolves differently, and `ObjectBaseAssemblerTest` gained cases for an empty, blank and padded colour, flags that start like an element keyword (`HOLD_LIFE`, `INSTA_ART`) and repeated flags, with the `NONE` message expectation moved to the corrected "sentinel" spelling. A change to the order the three flag tables are tried in should re-check the flag paragraph.

### ArtifactParseRecord.java

`ArtifactParseRecord` carries the raw text of one `artifact.txt` entry from the grammar to `ArtifactAssembler`, standing in for the values C's `parse_artifact_*` handlers read into `struct artifact`. Every component matched C, but the Javadoc still described `levelFirst` and `baseObjectLevel`, which stopped being components when the per-line level moved into the nested base-object record, left `baseObjects` and the nested record undocumented, and described `curse` as a name-to-power map when it is a list of records. The class block and every component are rewritten to say what an absent directive leaves behind (`""`, an empty list or map, and `null` for `desc` alone), how `msg:`, `desc:`, `values:` and the list directives accumulate, and why each base-object line keeps the level in force at that line. `ArtifactParseRecordTest` pins each of those claims against the grammar's output with eight cases, and the full suite is green. Going forward, a change to the grammar's defaults or to the accepted two-base-object deviation should re-check the class block.

### ItemObjectAssembler.assemble

`ItemObjectAssembler.assemble` turns the parsed `object.txt` records into `ObjectKind`s, standing in for the `parse_object_*` handlers and `finish_parse_object`. Every directive matched C on the inputs walked through, but the class Javadoc said C ignores the extra characters of a glyph token and that the object-flag and kind-flag tables share no name apart from their sentinels, when C refuses a longer glyph (the lexer does here) and both tables end in `MAX`, which C takes and Java takes too. The class, field and method blocks are rewritten to say that, and to record the sentinel handling of flags and modifiers, the base-10 reading of `RES_` figures, and the registry and curse-index ordering of brands, slays and curses. `ItemObjectReaderTest` gained fourteen cases pinning the flag and modifier sentinels, case sensitivity, resistance figures, the ordering, `type:none`, colour names and codes, base-0 integers, the attack dice and the pile pair, and the full suite is green. A change to how the three flag tables are tried, or to the registry order, should re-check the flag and ordering paragraphs.

### ItemObjectParseRecord.java

`ItemObjectParseRecord` is the raw capture of one `object.txt` record, standing in for the fields the `parse_object_*` handlers fill on C's `object_kind`. Every directive C registers has a component and nothing is missing, but the class Javadoc said all absent directives arrive as empty strings when `msg:`, `vis-msg:` and `desc:` arrive as `null`, as C's zero-filled pointers do, and it described `curse` as a name-to-power map when it is a list of `FullCurseDataParseRecord`. The class and the `effects`, `brand`, `slay` and `curse` tags are rewritten to say that, to name the fields C derives elsewhere (`sval`, `kidx`, `flavor`), and to record that the grammar fills the curse `timeout` with `"0"`. `ItemObjectParseRecordTest` is new, with nine cases driving the grammar for the component set, the absent-directive sentinels, every directive's landing place, text joining, last-write-wins, repeated brands and slays, effect folding and per-record line numbers, and the full suite is green. A new `object.txt` directive or a change to the grammar's seeds should re-check the component-set case and the sentinel case.

### ElementEnum.java

`ElementEnum` is the port of C's `ELEM_*` list, with per-constant `isBase`, `isHigh` and `hasResistRune` flags standing in for the `ELEM_BASE_*` and `ELEM_HIGH_*` ordinal ranges of `object.h`. A new element or a reordering of `list-elements.h` should re-check the flag run and the projection correspondence.

### ObjectKindFlag.lookup

`ObjectKindFlag.lookup` is the port of C's `lookup_flag` over the `kind_flags` name table in `obj-init.c`, which `grab_flag` uses for each `flags:` token of an object kind. It matched C: `KF_NONE` is never found because the search starts at index 1, `KF_MAX` is found because the table is built from the whole list, and the match is exact and case-sensitive. The method had no Javadoc and the class block still said every assembler used `valueOf`, so both now describe the `null`-for-not-found contract, the two sentinel cases and which assembler calls which. `ObjectKindFlagTest` gained five cases covering every real flag, the `NONE` and `MAX` slots, near-miss and `null` names, and the data-file tokens, and the full suite is green. Anything that rejects the `NONE` and `MAX` sentinels has to do it in the caller, since `lookup` leaves `MAX` resolvable as C does.

### ObjectFlag.lookup

`ObjectFlag.lookup` is the port of C's `lookup_flag` over the `obj_flags` name table, which `grab_flag` uses for each `flags:` token of an object kind, and the rest of `ObjectFlag` was checked alongside it. The order, labels and `getSustainStatFlag` all matched C, and `lookup` matched too: `OF_NONE` is skipped because the search starts at index 1, `OF_MAX` is found, and the match is exact and case-sensitive. The class block wrongly said the data file cannot name either sentinel, and `lookup` had no Javadoc, so both now describe the `null` contract, the `NONE` and `MAX` cases and how `code_index_in_array` differs. `ObjectFlagTest` gained seven cases covering every real flag at its C index, the two sentinels, near-miss, label and cross-table names, and `null`, and the full suite is green. A caller that must refuse `OF_MAX` has to do it itself, as `lookup` leaves it resolvable as C does.

### ObjectBase.java

`ObjectBase` is the field-for-field port of C's `struct object_base` from `object.h`, the record `ObjectBaseAssembler` builds and `ObjectKind` inherits its flags and element info from. It matched C on every field, on the `num_svals` start of 0 and on the absent-name `NULL`, and the synthetic `TV_NONE` base matches the zeroed `kb_info` slot that `object_base.txt` never fills. The `setElementInfo` Javadoc claimed nothing in `src/test` calls it, which was wrong (`ObjectBaseTest` does), so that block is corrected and records the by-reference storage. `ObjectBaseTest` gained a case for an absent name and one pinning the synthetic base against the shipped file, and its section headers were put back over the tests they describe. Anything that starts using `setElementInfo` in `src/main` should update that note.

## Things not to drop

- `ObjectRegistry.java` (`addObjectKind`): a kind with no base takes sval 0 and the (TV_NONE, 0) slot of `kindsByTvalSval`, so a later base-less kind displaces an earlier one from the index while both stay in `objectKinds`. C's `lookup_kind` scans `k_info` and returns the earliest, so `lookupObjectKind(TValue, int)` can answer with the later kind where C answers with the earlier. Documented in both Javadoc blocks and pinned by `twoKindsWithNoBaseCollideInTheIndex`, but not resolved.
- `ColourEnum.java` (`fromCode(String)`): the name `Shade` resolves to `COLOUR_SHADE`, where C's `color_text_to_attr` has no named row for it and answers white, so `graphics:Shade` in `object_base.txt` would load a different colour; no shipped data uses it.
- `ItemObjectAssembler.java` (`assemble`): `modifiers` and `elInfo` are `HashMap`s, so their iteration order is unspecified, where C walks index-ordered arrays; curses are already re-ordered by `ObjectKind`'s constructor. Whether any consumer iterates the two maps has not been checked.
- `ItemObjectAssembler.java` (`values:`): modifier figures go through `Random.parseStr`, where C reads them with `dice_parse_string` and not `parse_random`; whether the two accept the same text has not been compared.
