# Precis — 2026-09-25

## Key points from the day

### UIPlayer.getUIEntryLabel verified and ported

A `/port` pass targeted `UIPlayer.getUIEntryLabel`, the label formatter the resistance-panel layout calls while building
the character sheet. The first verify pass found two real discrepancies against C's `get_ui_entry_label`, both since
fixed by Rowan: a missing `length == 0` no-op guard and an off-by-one in the padding count.

A re-verify this session found both fixed and matching C clause for clause, so nothing further needed changing in
`UIPlayer.java`.

Full Javadoc was written for the class, its two static fields (`firstCallOfGetEntryLabel`, `spc`)
and the method itself, plus a new `GetUIEntryLabel` nested group in `UIPlayerTest` with nine cases derived from the C
branches — the no-op guard, the empty-buffer case, both padding sides, the
`MAX_SHORTENED + 1` cutoff on both sides of its boundary, truncation, and the exact-width edge. The full suite is green.

The resistance-panel label formatter now has documentation and regression coverage tying it to its C original, so a
future change to padding or truncation there will be caught immediately.

### UIPlayer.configureCharSheet verified and ported

A `/port` pass targeted `UIPlayer.configureCharSheet`, the method that builds the resistance-panel layout the previous
entry's label formatter feeds into. The first verify pass found the layout's supporting data classes, `CharSheetConfig`
and `CharSheetResist`, did not have anywhere to hold more than one resist entry per panel region, which crashed or
silently dropped data depending on which region ran; several iterations were needed to reshape that storage correctly.

`CharSheetResist`'s label became a plain string instead of a fixed array, and `CharSheetConfig` picked up a proper
per-region, per-entry lookup so every matching entry in a region is retained rather than only the last one written. A
re-verify walked the method against C clause by clause once that settled and found it matching throughout.

Full Javadoc was written for the method, its `CharSheetConfig`/`CharSheetResist` fields and helper predicate, and both
supporting classes in full, plus a new `ConfigureCharSheet` nested group in
`UIPlayerTest` covering region layout, the stat-modifier and row-fit clamps, and the multi-entry retention the fix was
about. The full suite is green.

The resistance panel can now correctly display more than one resistance, ability, hindrance or modifier per region — the
whole point of the panel — where before it silently could not, so future work building the actual on-screen rendering
has a layout cache to trust.

### UIPlayer.cnvStat verified and ported

player's natural-maximum stats. The first verify pass found one real discrepancy against C's `cnv_stat`: the three-digit
threshold used `bonus > 100` instead of C's inclusive `bonus >= 100`, so a bonus of exactly 100 rendered with a stray
leading space instead of the plain `"18/100"` C produces. Rowan fixed the comparison, and a re-verify found it matching
C clause for clause across every branch and boundary.

Full Javadoc was written for the method, and a new `CnvStat` nested group in `UIPlayerTest` with six cases covering the
plain-number branch, both sides of the padded/three-digit boundary, and the `"18/***"` cap. The full suite is green.

The stat-panel's value formatter is now documented and pinned against the C source at its one previously-wrong boundary,
so the character-sheet rendering work still to come there can trust its output at every stat value.

### UIPlayer.panelRegions verified and ported

first verify pass found a real discrepancy against C's anonymous `panels[]` element struct: the third field held a

Full Javadoc was written for the class, its three fields, constructor and three accessor methods, all tying back to the
`panels[]` element struct they stand in for. No new tests exercise the class itself: it is a private, non-static nested

`Panel`/`PanelLine` was extended to cover it too. The full suite is green.

This layout-table entry now has the same shape as C's `panels[]` element and documentation tying it back to that struct,
so the still-unported five-element table and its `get_panel_*` builders have a correctly-shaped type to land on rather

### UIPlayer.Panel.panelLine verified and ported

A `/port` pass targeted `Panel.panelLine`, the row-filler that turns `panelAllocate`'s empty panel into the actual
name/race/HP-style rows the character sheet draws. Two verify iterations found real discrepancies against C's
`panel_line`: the first port stored the formatted value with no length cap at all, then a fix attempt crashed on any
value under twenty characters, then a second fix attempt capped at the wrong length; each was reported and left for
Rowan to correct in turn until the cap matched C's `vstrnfmt` exactly.

The fixed version clamps every formatted value to nineteen characters before storing it, reproducing the fixed
twenty-byte C buffer with one byte reserved for a null terminator Java strings don't carry. Several existing doc blocks
elsewhere in `Panel`/`PanelLine` had asserted that no Java code filled rows or incremented `len` yet; those were
rewritten alongside the method's own new Javadoc rather than left to go stale now that `panelLine` is real.

Full Javadoc was written for the method, its constructor call into `PanelLine`, and corrections to five other blocks
across `Panel` and `PanelLine` that the fix made inaccurate, plus a new `PanelLineMethod` nested group in
`UIPlayerTest` with six cases covering ordinary appends, call ordering, the nineteen-character boundary either side, and
the full-panel guard. The full suite is green.

The row-filler every `getPanelX` builder needs is now documented, truncation-safe, and pinned against C's buffer
behaviour, so the character-sheet builders being written now have a verified primitive to call rather than one that
would silently overflow or crash on ordinary input.
