## Key points from the day

### FlickerTable.getAttr

`FlickerTable.getAttr` looks up the colour a flickering monster shows at a given frame, standing in for `visuals_flicker_get_attr_for_frame` and the `visuals_flicker_get_color` read in `ui-visuals.c`. It matched C on every input walked through, so no code changed, but the class Javadoc wrongly said an absent key stood for C's `BASIC_COLORS` sentinel and that the getter would yield `null`. C's table is zero-filled, so an unwritten base attribute reads as dark at every frame, which is what the Java returns. The class, field, constructor and `getAttr` Javadoc now say so, and the new `FlickerTableTest` checks the wrap, the absent key, and every `flicker:` block of the shipped `visuals.txt`. Anything that treats an absent key as "no cycle" or `null` would now be wrong, and so would the tier 3 fallback in `do_animation` ever firing for an in-range base colour.
