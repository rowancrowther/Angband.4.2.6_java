# Precis — 2026-10-02

## Key points from the day

### `ArtifactSetData` checked against `struct artifact_set_data` and `artifact_set_data_new`

`struct artifact_set_data` in `obj-randart.h` holds what the randart generator learns from a set of artifacts, and
`artifact_set_data_new()` in `obj-randart.c` builds it zeroed, with six hand-set start and increment values.
`ArtifactSetData` is the Java form, built by `ObjectRandart.artifactSetDataNew`. All thirty members, the six defaults
and the zeroed key sets match C, but the class, fields, constructor and sixty accessors had no Javadoc. Every
declaration now carries a block naming its C member and the `obj-randart.c` function that fills it, and the new
`ArtifactSetDataTest`
pins the defaults, every getter/setter pair, single-key writes and C's `+=` idiom. The later `store_base_power` and
frequency ports can use the accessors directly, as long as every artifact is loaded before construction, because a late
artifact has no entry and its getters throw.

### `ArtifactIndex` checked against the `ART_IDX_*` enum

The `ART_IDX_*` enum in `obj-randart.h` is built from the X-macro list `list-randart-properties.h`, and names the 95
learned-probability slots in `art_probs`, sentinel included. `ArtifactIndex` matches it name for name, in order and with
the same supercharge column, but carried no Javadoc at all. Every constant now says which `obj-randart.c` tally fills it
and what floor or halving `adjust_freqs()` applies, and the new `ArtifactIndexTest` pins the order, the ordinals and the
supercharge flags. The flag is unread in C and in Java, so it only matters if a later port finds a use for it; the
item-group arrays (`art_idx_bow` and the rest) are the next piece the frequency code will need.

### `GameConstantsData` checked against the `parse_constants_*` handlers and `check_critical_levels`

`GameConstantsData` and its builder are the Java form of the `constants.txt` half of `struct angband_constants`. C fills
that half through the `parse_constants_*()` handlers in `init.c`, then `finish_parse_constants()` checks the critical
cutoffs with `check_critical_levels()`. The builder now zeroes missing constants and lets a later line overwrite an
earlier one, as C does. Three `GameConstantsReaderTest` cases that still expected missing-constant and duplicate errors
were rewritten to match. Every declaration now has Javadoc naming its `z_info` field and C handler, and the new
`GameConstantsDataTest` pins the defaults, the label-to-field wiring, the level-row checks and every
`check_critical_levels` case. The one Java-only rule, rejecting a `-1` cutoff in the middle of a level list, is
documented and pinned as a deliberate divergence. Values above 65535 are kept, where C's `uint16_t` fields would
truncate them, so that difference will show up only if a data file ever goes that high.

### `TValue` checked against `obj-tval.c` and `list-tvals.h`

`TValue` is the Java form of C's `TV_*` list and of `obj-tval.c`: the type predicates, the name lookup
`tval_find_idx` with its `de_armour` helper, and the kind counters `tval_sval_count` and `tval_sval_list`. The
predicates and counters already matched C. The lookup did not: `findIndex` threw on an unknown name, and British
spellings and C's whitespace rules were handled differently. `fromName` now follows C's `armour` rewrite and its leading
and trailing whitespace rules, `findIndex` returns `-1`, every declaration carries Javadoc, and the new
`TValueLookupTest` pins the C-derived results for numbers, armour spellings, display names and the Java-only identifier
form. All 23 British-spelled armour lines in `lib/gamedata` now resolve as they do in C, and any later port that needs a
tval number can call `findIndex` without guarding against an exception.

### `TValue.findName` checked against `tval_find_name`

`tval_find_name` in `obj-tval.c` is the reverse of `tval_find_idx`: it turns a numeric tval into its `list-tvals.h`
name, or `"unknown"` if the number is not a tval. It was the one function in that file the port lacked, so code holding
only a number had no safe way to name it. The new `TValue.findName` indexes by ordinal behind a bounds check, which
matches C's table search, and `TValueLookupTest` now pins both ends of the range, `"unknown"` and the round trip with
`findIndex`. Every function in `obj-tval.c` now has a Java port.

### `IgnoreType` checked against `ignore_type_t` and `list-ignore-types.h`

`ignore_type_t` in `obj-ignore.h` is built from the X-macro list `list-ignore-types.h`, and names the kinds of item that
quality and ego ignoring work by, each with its menu name. `IgnoreType` matches it row for row, in order and with the
same names, but had no Javadoc at all. Every declaration now says which tvals and kind-name matches from
`quality_mapping` give it, and the new `IgnoreTypeTest` pins the order, the ordinals and the names. `getName` returns
the empty string for `ITYPE_NONE` and `ITYPE_MAX` where C's `ignore_name_for_type()` returns `"unknown"`, so a port of
that function will need its own guard rather than calling `getName` directly.

### `ItemObject` batch 1: pack ordering, stacking checks and merge helpers

This pass covered the first batch of `ItemObject.java`: `earlierObject`, `similar`, `checkElementStacking`,
`cursesAreEqual`, `runesKnown`, `effectIsKnown`, `isFullyKnown`, `originCombine` and `distributeCharges`, against
`earlier_object`, `object_similar`, `curses_are_equal`, `object_origin_combine`, `distribute_charges` and the
`object_*_known` functions in `obj-knowledge.c`. The verify pass found that modifiers and curses were compared by key,
so a zero entry differed from an absent one where C reads both as zero, that the shared static `player` could be null or
stale, and that making `earlierObject` an instance method made `calcInventory` throw on a null `first` and then, after a
first guard, never fill the pack. Rowan's fixes compare by value with zero equal to absent, refresh the player on every
call to `earlierObject` and `similar`, and route the `calcInventory` calls through a throwaway `ItemObject` so a null
`first` still wins; the class, the twenty-one fields these methods touch and every method now carry Javadoc, and 31 new
tests across `ItemObjectSimilarTest`, `ItemObjectOrderingTest` and the new `ItemObjectMergeHelpersTest` pin the
C-derived values. Batches 2 to 9 are listed in `docs/ItemObject_port_batches.md`, and the differences from C left in
this batch are under "Things not to drop" below.

### `ItemObject` batch 2: stackability, absorb, split and copy

This pass covered the second batch of `ItemObject.java`: `mergeable`, `objectStackable`, `objectAbsorb`,
`objectAbsorbMerge`, `nullKnown`, `objectSplit`, `copy`, `objectIsInQuiver`, `objectWeightOne`, `checkForInscription`
and
`verifyObject`, against `object_mergeable`, `object_stackable`, `object_absorb`, `object_absorb_merge`, `object_split`,
`object_copy`, `object_weight_one`, `check_for_inscrip`, `verify_object` and `object_is_in_quiver`. The verify pass
found that `objectAbsorb` read a stale `player` snapshot, that `objectSplit` skipped C's alignment of the known count
before sharing out charges, and that `mergeable` tested the wrong object for ammunition. Rowan fixed all three, and the
class, the fields these methods touch and every method now carry Javadoc without C line numbers. The new
`ItemObjectCopyTest` and extra absorb, split and curse-ordering cases pin the C-derived values, and the suite is green
after bringing the Wipe, Weight, Stacking and FlavourAware tests into line with the current codebase. Stores will need
`object_copy_amt` in Chapter 8, and `verifyObject` prints a placeholder name until `description` lands in Chapter 7.

### `ItemObject` batch 3: `objectValue`, `objectValueBase` and `objectValueReal`

This pass covered the pricing trio in `ItemObject.java` against `object_value`, `object_value_base` and
`object_value_real` in `obj-power.c`: the player's price, the flat guess for an unidentified object, and the real price
from power or from cost and charges. All three already matched C clause for clause, including the overflow clamps, the
ammunition and torch rescale, the lift of a zero price to one, and the round-up of charges, so nothing in the code
changed. The existing Javadoc cited C line numbers and said a cursed object's price "comes out negative", which the
stack total never does, so the three blocks and the seven fields they read were rewritten, and the new
`ItemObjectValueTest` pins 43 C-derived cases across the three routes. The pricing the shops will use in Chapter 8 needs
no further porting, and the variable-power route is now covered end to end, ready for batches 4 to 6 to extend.

### `ItemObject` batch 4: `objectPower`, `nonStandardWeightPower`, `cursePower` and `applyCurseAttributes`

This pass covered the driver and curse plumbing of the power calculation in `ItemObject.java` against `object_power`,
`nonstandard_weight_power` and `curse_power` in `obj-power.c` and `apply_curse_attributes` in `obj-curse.c`, together
with the `freeSlays`, `freeBrands` and `freeCurses` helpers and the curse overloads that stand in for C's curse objects.
All of them already matched C clause for clause, including the step order, the three `INHIBIT_POWER` returns, the
truncating divisions, the clamp of a curse's strength between 20 and 100, and the resistance-combining table with its
both-at-once state, so nothing in the code changed. The blocks cited C line numbers, said the curse merge adds flags and
left out the base-armour step C performs, so the methods, the helper methods, the curse overloads and the fields they
touch were rewritten, and the new `ItemObjectPowerCursesTest` pins 58 C-derived cases. Batches 5 and 6 can now rely on
the driver and the curse pricing being settled, and only the individual power terms remain to be checked.

## Things not to drop

- `ItemObject` batch 1 differences from C: `checkElementStacking` is stricter than C when an element is recorded on one
  object and absent on the other, because the element maps are sparse.
- `cursesAreEqual` treats an empty curse map and a map of zero-power entries as equal, where C treats a null curse array
  and an all-zero one as different.
- `similar` assumes both modifier maps exist and, in `OSTACK_LIST` mode, that both items have a known counterpart; C
  also dereferences `known`, but it has no null maps.
- `earlierObject`, `similar` and `objectAbsorb` overwrite the receiver's `player` on every call, while the partial
  absorb, the slot lookups and the power calculations still read the snapshot taken at construction.
- `earlierObject` is an instance method only to refresh `player`, so `calcInventory` calls it on a throwaway
  `new ItemObject()` and the receiver plays no part in the ordering.
- `similar` carries an explicit `tValue` equality test that C lacks, which the kind test already implies.
- The `removeCurse` Javadoc in `ItemObject` still says nothing is stored at power zero and credits that for how
  `cursesAreEqual` works, which is no longer true.
- `ItemObject` batch 2 differences from C: `copy(false)` leaves `known` null where C's `object_copy` copies the pointer,
  and `objectAbsorbMerge` ignores an empty absorbed note, which C does not test for.
- `objectWeightOne` would apply a curse twice if two curses on one item shared an index; real curses never do.
