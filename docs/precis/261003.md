# Precis — 2026-10-03

## Key points from the day

### `Random.Zero()` and `Random.One()` checked against the `random_value` literals in `z-rand.c` and its callers

C has no named zero or one `random_value`: it writes `{ 0, 0, 0, 0 }` wherever it needs "no dice", and never names a
`1d1` at all. `Random` now carries both as shared prototypes handed out as copies by `Zero()` and `One()`, and the zero
one already backs the recharge interval in `ItemObject`, which used to be null where C holds a zeroed struct. Both
constants roll 0 and 1 under every aspect and level when worked through `randcalc()`, `damcalc()` and `m_bonus_calc()`,
and each declaration now has Javadoc naming that C reference; the new `RandomConstantsTest` pins every aspect and level,
the valid and varies answers, and that changing one copy cannot change the next. `Zero()` can serve any later port that
starts from a zeroed `random_value`, while `One()` has no C counterpart and so has no caller yet.

### Stage 1 mismatches 1 to 4: element stacking, curse power, recharge dice and message tags

The Stage 1 sweep of `ItemObject` found four places where the port was stricter or looser than `object_similar`,
`print_custom_message` and the `obj->curses` and `obj->time` accesses in C. Left alone, sparse element maps would have
refused stacks C allows, `setCursePower` would have lost a curse a future `append_object_curse` added, a caller could
have rewritten an item's recharge dice through `getTime`, and a tag like `{names}` would have left stray text in the
message. Each now matches C: `checkElementStacking` walks every element and reads a missing entry as level 0 with no
flags,
`setCursePower` adds a curse that was absent and removes one at power zero, `getTime` returns a copy of a dice field
that is never null, and `MessageTag.getTag` matches on opening letters with the message printer skipping to the closing
brace. The Javadoc and tests were brought into line, and `similar` now calls the element check once, so the later ports
of curse appending and the rod and activation commands can rely on these four reading as C does.

### Out-of-scope matters from the Stage 1 sweep: `copyCurses`, `canBrowse`, `Slay` equality and the curse element maps

The sweep left five matters outside `ItemObject` itself, checked here against `copy_curses` and `obj_kind_can_browse` in
C. Left alone, `copyCurses` would have stored power-zero curses C skips, a class built without magic could have thrown
out of
`canBrowse`, a `Curse` with no element map could have thrown in three readers, and a copied `Slay` would never have been
found in an item's slay set. Each now matches C: `copyCurses` skips power-zero entries and merges in a `LinkedHashMap`,
`PlayerClass` turns a null magic into `ClassMagic.NONE`, `Curse.getElInfo` answers an empty map and `setKnownElInfo` no
longer overwrites the real map, and `Slay` has value `equals` and `hashCode`. The Javadoc was brought into line and
`SlayEqualsTest`, `ObjectKindCanBrowseTest` and the curse and class tests pin each case, so the later ports of curse
appending and the knowledge screens can rely on these reading as C does.

### `ItemObject.getCurses()` checked against the `obj->curses` reads in `obj-curse.c` and `game-world.c`

C has no accessor for an object's curses: it reads the `obj->curses` array pointer directly, treats `NULL` as "no
curses", and walks the array from slot 0 up. The port's `curses` field became an index-ordered `TreeMap` while this was
being checked, which left 105 tests that set a `LinkedHashMap` through reflection failing, and exposed that `copy`
shared each `CurseData` with the original where C duplicates the array. `getCurses()` already matched C, so the work was
to rewrite the Javadoc on the field, the comparator, the factory and the accessor for the ordering and the null guard,
and to move the tests to `clearAndPutCurses` and index order, with `copy` now rebuilding each `CurseData`.
`ItemObjectGetCursesTest` pins the empty, ordered, unmodifiable and live-value behaviour, so later curse ports can rely
on `getCurses()` walking in C's index order.

### `Command` checked against the `cmd_*` argument functions in `cmd-core.c`

`Command` carries what C kept as `struct command` and the `cmd_set_arg`, `cmd_get_arg` and `cmd_get_*` family, and every
method read as C does, including the shared item pointer in `clone`, the 79-character string limit, and the way a failed
direction cancels the repeat while a failed aim does not. Two Javadoc blocks had drifted from the code:
`getEffectFromList` still described an `Optional<Integer>` return after it became an `EffectChoice`, and `getSpell`
claimed non-casters short-circuit when the prompt is in fact still opened. Both are rewritten along with the class, the
`player` field, `clone`, `setArg`, `getItem`, `getString`
and the two spell helpers, and `CommandSpellItemRepeatTest` now covers `getSpell`, the shapechange mask, the
repeat-cancel rule and what
`clone` shares. The `player` captured at construction and the unreferenced private `playerObjectToBook` are the two
things to revisit when the birth commands and the spell-browsing ports arrive.

### `PlayerKnowledge.knowObject` checked against `player_know_object` in `obj-knowledge.c`

`knowObject` rewrites an item's known counterpart from what the player has learned to read, and it is the step every
rune learned runs over everything in play. The brand and slay blocks looped over the kind's own brands and slays and so
could never learn one carried by an ego, a stale entry survived on the counterpart, a null brand set threw, and the "On
the ground" report tested the player's remembered level where C tests the real one. The port now walks the registry like
C, keeps only what the item carries and the player can read, edits the counterpart through the item's own mutators, and
judges the report on the real level; the full stop, the sentinel modifier entries and the missing-element crash are
fixed with it. `PlayerKnowledgeKnowObjectTest` pins the cases, so the later ports of the store walk and item description
can rely on the counterpart reading as C's does.

### `ItemObject.setNoticeOn` and `setNoticeOff` checked against the `obj->notice` bit operations in `ui-object.c` and
`ui-wizard.c`

C has no function for raising or lowering a notice flag, only `obj->notice |= flag` and `&= ~flag` written inline, so
these two methods are the port's named stand-ins for those operators. Both already behaved as the C does, idempotent and
touching only the one flag, so no code changed; the Javadoc on both methods, the `notice` field and the class now
records the C operator each one replaces, the boolean return that C does not have, and that `orNotice` duplicates the
raising side.
`ItemObjectNoticeMutatorsTest` pins raise, lower, repeat, isolation from the other three flags, the ignore/unignore
round trip and the detached copy from `getNotice()`, so callers ported later can use either name and rely on
`getNotice()` never being a way in.

### `ItemObject.getNoticeHas` checked against the `obj->notice & OBJ_NOTICE_x` reads in `obj-desc.c`, `obj-ignore.c` and
`obj-knowledge.c`

C has no function for testing a notice flag, only the bit-AND written inline at each reader, so `getNoticeHas` is the
port's named stand-in for that test. It already matched, a single flag read from the item's own set with no copy, so no
code changed; the Javadoc on the method, the `notice` field and the class now records the C operator it replaces and
that most C readers test the known half, so a caller passes `getKnown()` for those. `ItemObjectNoticeHasTest` pins the
fresh item, each flag in isolation, all four together, lowering, the known half staying separate, copy independence and
the wipe reset, so the ports of the ignore and description readers can use `getNoticeHas` instead of copying the set
through `getNotice()`.

### `PlayerKnowledge.createObjFlagMask` checked against `create_obj_flag_mask` in `obj-properties.c`

`createObjFlagMask` selects every flag property whose id type, or whose subtype, is one of a list, and
`objectLearnOnWield`
calls it to find the flags that become obvious on wielding. It already matched C for the empty list, the non-flag skip
and the
`OFID_NONE` and `OFT_NONE` defaults, though the Java list has no zeroed slot 0 to step over and a value from the wrong
family selects nothing where C would compare bare integers, so no code changed. The Javadoc on the method now records
those divergences and the difference between the two meanings of the first argument, and
`PlayerKnowledgeCreateObjFlagMaskTest` pins each id type, each subtype, the union, the partition of the flags and the
fresh result per call. The two later callers in C, the wield and timed learning passes, can use it as it stands.

## Things not to drop

- `Random.randCalc` with the randomised aspect reads the world list through `WorldRegistry.getMaxRandDepth()`, where C
  uses the fixed `MAX_RAND_DEPTH`, so `Random.Zero()` cannot be rolled randomised until the world data has loaded;
  `RandomConstantsTest` seeds the list to get past it.
