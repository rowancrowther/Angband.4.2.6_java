# Precis — 2026-10-07

## Key points from the day

### `PlayerKnowledge` checked against every function it ports from `obj-knowledge.c` and `create_obj_flag_mask()` in
`obj-properties.c`

`PlayerKnowledge` holds the rune-learning, knowledge-propagation and equipment-learning code, including the private
curse overload of `player_know_object()` that `update_player_object_knowledge()` reaches through `curses[i].obj`. The
check found that the curse overload built its modifier map over every `ObjectModifier` value, so a curse's known object
carried `OM_NONE` and `OM_MAX` keys that C's `0 .. OBJ_MOD_MAX - 1` loop never has and that the item overload already
left out. You skipped both sentinels in the curse overload, and `equipLearnElement` now names the item through
`ItemObject.description` like every other caller. The curse overload's Javadoc records the sentinel rule, two blocks
lost a stale home-of-the-family claim and a stale stamp, and the new `PlayerKnowledgeKnowCurseObjectTest` pins the
combat, modifier, element and flag gating and the map's keys against figures derived from C, so the curse side of
knowledge can be relied on to behave like the item side.

### `ObjectUtils` checked against every function it ports from `obj-gear.c`, `obj-util.c`, `obj-make.c`, `obj-slays.c`,
`obj-curse.c` and `obj-knowledge.c`

`ObjectUtils` holds the gear, quiver, flavour, `object_prep` and flag-knowledge helpers, with four stubs still waiting
on later chapters. The check found no result that differs from C for any input the game data or the callers can produce;
the divergences left are the ones the Javadoc records, such as the null-item guard in `gearToLabel` and the
one-block-per-type assumption in `flavourAssignRandom`. Fourteen tests in
`ObjectUtilsObjectPrepTest` and `PlayerQuiverCapacityTest` had been failing because `copyCurses` and `cursesAreEqual`
now read `ObjectRegistry.getCurses()`, which throws while the curse table is unloaded, so those fixtures now seed an
empty one, the class Javadoc lost a stale `Player.slotByName()` example, three blocks recorded the divergences above,
and
`PlayerQuiverCapacityTest` gained four `preferredQuiverSlot` cases derived from C's `@` scan. Any new test that reaches
`objectPrep` or `objectStackable` has to seed the curse table the same way, and the one-block-per-type assumption is the
thing to revisit if `flavor.txt` ever grows a second block for a type.

### `ObjectUtils` checked again after `Flag.andNot` replaced the quiver-mode test in `invenCanStackPartial`

You gave `Flag` an `andNot` and moved `invenCanStackPartial` onto it, so `ObjectUtils` was run against the same six C
files a second time. The stack-mode test now follows C's `mode2 & ~OSTACK_QUIVER` for every mode set, which retired the
mode divergence the morning's Javadoc recorded, and four blocks turned out to describe code that has since moved:
`combinePack` said C has no count realignment when it does, both curse overloads of the knowledge checks linked to
`Curse` methods that no longer exist, and `flavourAssignRandom` said it ended in `System.exit` when `quitFmt` throws.
Those blocks were rewritten against the code as it stands, and two new `ObjectUtilsGearTest` cases start the known
counts out of step to pin C's "Ensure numbers align" lines in `combinePack`. `Flag.andNot` carries no Javadoc block of
its own, so it is the one declaration this pass touched without documenting.

### `ObjectModifier` checked against the `OBJ_MOD_*` enum that `obj-properties.h` builds from `list-stats.h` and
`list-object-modifiers.h`

`ObjectModifier` is the enum of numeric modifiers an object can grant, from the five stat bonuses through to extra
moves. The check found all sixteen constants in C's order with `OM_NONE` and `OM_MAX` as the only additions, so no
caller is affected, but its class Javadoc described a commented-out block and a set of elemental resistances that are
not in the file. The class block was rewritten to record the savefile-order rule, the stats-first layout behind
`OBJ_MOD_MIN_STAT`, and the one-place ordinal shift that `OM_NONE` causes, and every constant gained a doc line.
`ObjectModifierTest` pins the order against the two C headers, so any future caller that indexes by `ordinal()` has a
written warning and a failing test if the list is reordered.

### `Flag` checked against every function it ports from `z-bitflag.c`

`Flag` is the `EnumSet` wrapper behind every C `bitflag` array in the port, and `andNot` is the newest method on it. The
check found one result that differs from C: `copyFrom` wiped the receiver before reading the source, so copying a set
onto itself emptied it where C's `memcpy` leaves it alone. You made `copyFrom` take a snapshot of the source before the
wipe, and the class, `copyFrom`, `union`, `diff`, `count`, `isEmpty`, `next` and `andNot` blocks now record the C
semantics, the padding divergence and the self-argument behaviour. Eleven new `FlagTest` cases pin self-copy,
self-union, self-diff and `andNot` against C's results, so a caller can hand a `Flag` to its own mutators without
checking first.

### `ItemObject` construction, copy, wipe and the curse, brand and slay editors checked against `object_new`,
`object_copy`, `object_wipe` and the curse functions of `obj-curse.c`

This is Part A of the second `ItemObject` pass: the two constructors, `copy`, `wipe`, `initCurses` and the editors that
stand for C's `bool` and curse arrays. The check found `copy` building `HashMap`s where the rest of the class uses
ordered maps, and `setCurses` and `clearAndPutCurses` emptying the item before throwing on `null`, where C's
`copy_curses` returns early. You fixed both, plus the full constructor's `null` flags and notice, and the code now
matches C for every input the callers can produce. About a dozen blocks that still described `LinkedHashMap` curse maps,
a null
`time` and by-reference curses were rewritten, the `getGrid` and `Loc.zero` notes were added, and the new
`ItemObjectConstructionTest` pins the blank-item defaults, copy order and sharing, null arguments and the places
`addCurse` and `removeCurse` deliberately differ from `append_object_curse` and `remove_object_curse`. A later port of
those two functions, which `apply_curse` will need, now has tests that fail on purpose when it changes those answers.

### `ItemObject` pack order, stacking, absorb and split checked against `earlier_object`, `object_similar`,
`object_stackable`, `object_mergeable`, `object_absorb`, `object_absorb_partial`, `object_split`,
`distribute_charges` and `object_is_in_quiver`

This is Part B of the second `ItemObject` pass: the pack-order comparison, the similarity and capacity tests, the whole
and partial absorbs, the split and the helpers they share. The check found no result that differs from C in any of the
fourteen methods, including `objectAbsorbPartial`, which had no earlier baseline, so no caller is affected. Two Javadoc
blocks were wrong rather than the code: `nullKnown` said `ObjectUtils` clears both halves where C clears only the
absorbed stack, and `objectAbsorbPartial` said the size left in the pack must fit `max_stack` where C requires it to be
strictly below. Both were corrected, and the new `ItemObjectEarlierObjectRulesTest` pins usable ammunition, flavour
awareness, light fuel, ammunition-versus-other value ordering, `objectIsInQuiver` and `nullKnown`, with two
empty-inscription cases added to `ItemObjectStackingTest`. The `objectSplit` exception message still says "more than"
where the legal range is below the stack size, which is text only and yours to change when you next touch that method.

### `ItemObject` value and the power driver checked against `object_value`, `object_value_base`, `object_value_real`,

`nonStandardWeightPower` and `cursePower` overloads, and `applyCurseAttributes`. The check found no result that differs
from C in any of them, and it showed that the curse-visiting-order divergence the first pass accepted has closed itself,

`ItemObjectPartCRound2Test` pins the `MULTIPLY_WEIGHT` of exactly 100 as an ordinary curse, both passes of `cursePower`,

their ported stamp from the first pass, so nothing needed stamping, and the one open design question is the identity
comparison of the held-back curse in `applyCurseAttributes`, which differs from its `CURSE_ORDER` neighbours.

### `ItemObject` power components checked against `effects_power`, `element_power`, `flags_power`, `modifier_power`,

## Things not to drop

- `equipLearnElement`, like the other messages here, prints `{DESCRIPTION_TAG}` for the item name until
  `ItemObject.description` is ported in Chapter 7, and `ObjectUtils.objectDesc` is a second stub returning an empty
  string that nothing in `PlayerKnowledge` calls any more; decide which of the two survives when the description
  subsystem is ported.
- C's `object_learn_unknown_rune`, `object_find_unknown_rune`, `object_learn_on_use`, `shape_learn_on_assume` and
  `missile_learn_on_ranged_attack` have no Java port yet, and `equip_learn_after_time` exists only as a stub in
  `ObjectUtils`.
- `applyCurseAttributes` uses (`curse == curseToIgnore`), while its neighbours go through `CURSE_ORDER`, Flagged in part
  C.
- C line numbers remain in the Javadoc of `ObjectRegistry.java`, `FlagSet.java`, `ElementSet.java` and
  `ElementPowers.java` (Part D's report lists them); strip them when you next touch those files.
- Open decisions from the `ItemObject` second pass (`docs/ItemObject_round2/summary.md`), none made yet: whether
  `applyCurseAttributes` should compare through `CURSE_ORDER` (the bullet above); whether the `Curse` overloads of
  `objectPower`, `nonStandardWeightPower` and `cursePower` stay hand-reduced or call `objectPower` on
  `Curse.getItemObject()` as C does; and whether the five `objDescNameFormat` divergences join the batch 8 accepted
  list.
