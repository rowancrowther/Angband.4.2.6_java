# Precis — 2026-10-01

## Key points from the day

### `CriticalLevel` retired in favour of `MeleeCriticalLevelData`

`CriticalLevel` was the Java form of `struct critical_level` in `init.h`, but nothing constructed it, because the parsed
tables were already held as `MeleeCriticalLevelData` and `RangedCriticalLevelData` records. Rowan deleted the class, so
the records are now the only Java form of that struct, and `O_CriticalLevel`'s Javadoc points at the melee record
instead. `MeleeCriticalLevelDataTest` loads the shipped `constants.txt` and pins every melee and ranged row. The future
`critical_melee` and `critical_shot` ports can read the lists on `GameConstantsData` directly, and still need
`check_critical_levels` ported alongside them.

### `Chunk.caveFindDecoy` ported from `cave_find_decoy`

`cave_find_decoy()` in `cave.c` returns the grid of the player's decoy, or `loc(0, 0)` when there is none. `ChunkUtils`
already called `caveFindDecoy()`, so the Java method existed, but it carried no Javadoc and the `decoy` field's block
wrongly said nothing read it. The method returns the stored `Loc` directly, which matches C's by-value return because
`Loc` is immutable. `ChunkFindDecoyTest` pins the zero default, a placed grid, and a grid with a single zero coordinate.
The `decoy` field is never assigned after construction, so it stays `Loc.zero` until the decoy-placing code is ported.

### `ChunkUtils.projectionPath` ported from `project_path`

`project_path()` in `project.c` traces the grids a bolt, beam or thrown object passes through, using a fixed-point walk
with its own range rule. The first Java version had a wrong `half`, a mis-parenthesised and mis-counted range check, a
vertical `INFO` off-by-one, an enum where C takes a bitmask, and a vertical branch that never advanced on an exact
straight line. The method now takes a `Flag<ProjectEnum>`, tracks the shorter-axis step count the way C's `k` does, and
returns a list instead of filling an array. `ChunkUtilsProjectionPathTest` holds paths worked out by hand from the C,
including the slant tie and the three range limits. `isProjectable` and later `project()` callers can build on it,
though the `PROJECT_INFO` branch is untested until the player's remembered cave is easy to set up.

### `ChunkUtils.isProjectable` ported from `projectable`

`projectable()` in `project.c` answers whether a bolt cast from one grid arrives at another, and it decides what the
player can easily target and whether a monster can target the player. The first Java version checked the second-to-last
grid of the path, had the equality test the wrong way round, and took one `ProjectEnum` where C takes a bitmask, so
`Target.targetable` had to change to pass a `Flag<ProjectEnum>`. The method now takes a `Flag<ProjectEnum>` and tests
the last grid of the path for passability and for being the requested grid, as C does.
`ChunkUtilsIsProjectableTest` covers the empty, adjacent, wall, range-limit and covered-tracks cases, with the range
swapped in through the constants table. `Target.targetable` can now be checked against `target_able` in `target.c`.

### `Target.setTargetMonster` and `targetable` ported from `target_set_monster` and `target_able`

`target_set_monster()` and `target_able()` in `target.c` decide whether a monster can become the player's target and
what happens to the target when it cannot. The first Java version left out C's `m->race` test, took the monster index as
a second argument where C reads `mon->midx`, and left a stale monster reference behind in the fixed-target branch. The
method now takes only the monster, reads its own index, checks the race, and clears the reference in both non-target
branches. `TargetTest` pins each link of the `target_able` chain, the fixed and unfixed branches, and
`getTargetMonster`, with the target's private statics reached by reflection. Later `target.c` ports such as
`target_okay` and `target_release` can build on these fields, and the extra `monster` reference has no C counterpart.

### `ProjectEnum` checked against the `PROJECT_*` enum in `project.h`

`project.h` defines the `PROJECT_*` flags as bits of an `int` mask, and `ProjectEnum` is their Java form, used through
`Flag<ProjectEnum>` by `projectionPath` and `isProjectable`. All 17 names and their order match C, and the bit values
are dropped because the set is an `EnumSet`. The one divergence is that C's `PROJECT_NONE` is an empty mask while the
Java constant is a real member, so a set built from it has a count of one. You chose to keep it, as the other enums do,
and the Javadoc now records it. `ProjectEnumTest` pins the names, order and C bit values, and the non-empty `NONE` set.
Later `project()` ports should not use `isEmpty()` or `count()` to test for "no flags".

### `Effect.isAim` ported from `effect_aim`, with `isValid`, `getInfo` and `getDescription` checked

`effect_aim()` in `effects.c` reports whether an effect, or any effect after it in the chain, must be aimed, and the
three small accessors beside it read the effect table behind a validity guard. The first Java version ignored `this`,
tested the whole list, and had no guard for an invalid head, so `[EF_NONE, bolt]` answered true where C answers false.
`isAim` now finds this effect in the list, answers false at once if it is invalid, and walks from that position to the
end, inclusive. `EffectAccessorsTest` gains an `IsAimChain` group covering the inclusive start, earlier effects, the
invalid head, an invalid effect mid-chain and an effect outside the list. `effect_do` is still a stub, so the callers
that need aim answers can use `isAim` now and the effect handlers wait for Chapter 6.

### `EffectSubTypeWrapper` checked against `effect_subtype`

`effect_subtype()` in `effects.c` turns an effect's sub-type string into one `int` that each handler reads back as
`context->subtype`, and `EffectSubTypeWrapper` is the Java form that keeps a typed payload and a discriminator instead.
`getProjectionWrapper` tested a caller-supplied argument rather than the wrapper's own discriminator, so a
non-projection wrapper answered with null, and every getter threw a `NullPointerException` instead of the intended
exception when the discriminator was null. The projection getter now takes no argument and checks the field, and all
thirteen getters report "got null" for an unresolved wrapper. `EffectSubTypeWrapperTest` replaces the test that pinned
the old behaviour and gains cases for the null discriminator, `EST_NONE` and a shallow copy. Later effect handlers can
rely on a wrong read failing with `InvalidParameterException`, and `copy()` shares its `Summon` and `PlayerShape`
references.

### `EffectEnum` checked against `list-effects.h`

`list-effects.h` is the C table of every effect, and `EffectEnum` is its Java form, read by `Effect`, `EffectAssembler`
and the effect description code. All 112 rows match on aim, info label, argument count, info category, description and
menu text, and every sub-type agrees with `effect_subtype()` in `effects.c`. Two descriptions had been mangled to
`_%s percent),` and `_unresistable),` where C has brackets, and you fixed them. `EffectEnumTest` reads the C header
itself and compares every row, then pins the order, the sentinels, the sub-type switch and the 22 aimed effects. Every
constant, field and accessor now carries a Javadoc block, and the C `effect_kind` table drops the argument count and
info category, so those two columns stay Java-only data.

### `MessageType` checked against `list-message.h`

`list-message.h` is the C table of message types and their sound keys, and `MessageType` is its Java form, read by the
parsers and the message code. All 154 rows match on name, order and sound key, with `MSG_MAX` keeping `null` for C's
`NULL`. You chose to keep the Java-only `MSG_NONE`, which shifts every ordinal up by one, and the Javadoc now records
that and fixes a citation of a C file that does not exist. `MessageTypeTest` holds the C table transcribed in order and
checks every row, the count, the ordinal shift and the null sentinel. Later ports must not use `ordinal()` as the C
`MSG_*` number.

### `Stats` checked against `list-stats.h`, `stat_name_to_idx` and `stat_idx_to_name`

`list-stats.h` fixes the five stat indices that savefiles depend on, and `player.c` turns stat names into indices and
back. `Stats` is the Java form, read by the parsers, the wizard stat editor and every stat-indexed array. All five
indices, the `MAX` entry and both lookups match C, with the Java-only `STAT_NONE` standing in for C's -1. The class,
both fields, the constructor and `getStatString` gained Javadoc, and the C line numbers came out of the existing blocks
and `StatsTest`. Later ports can bounds-test against `STAT_MAX` as C does, and `getStats` answers `null` where C would
read past the array.

### `TrapEnum` checked against `list-trap-flags.h`

`list-trap-flags.h` is the C table of trap flags, and `TrapEnum` is its Java form, read by `TrapAssembler`, `Trap`,
`TrapKind` and `Square`. All 15 flags and the `TRF_MAX` sentinel match in name and order, but the `TRF_MAGICAL`
description had an underscore where C has an opening parenthesis and a stray trailing comma, and you fixed it.
`TrapEnumTest` holds the C table transcribed in order and also reads the real header when the C tree is present. The
class, field, constructor, sentinel and accessor now carry Javadoc, and later code can treat the ordinals as C's
`TRF_*` numbers.

### `Hint` checked against `struct hint`, `parse_hint` and `random_hint`

`struct hint` in `hint.h` is one line of shopkeeper advice plus a `next` pointer, and `Hint` is its Java counterpart.
The port matched C, but its Javadoc named `GameConstants` as the owner of the list when it is `MiscRegistry`, said hints
appear on entering or browsing a store when only entering a non-Home store triggers one, and gave a one-in-three chance
that is really one in six overall. The class, field, constructor and accessor now carry corrected Javadoc, and the new
`HintTest` pins verbatim text, trailing whitespace and file order. The port keeps file order where C's prepending list
reverses it, which `random_hint`'s uniform reservoir sample cannot detect, so a later `random_hint` port can index the
list directly.

### `Name` checked against `struct names_parse` and `parse_names_word`

`Name` is the Java form of one section of the name file, which C builds into `name_sections` in `finish_parse_names`.
The port matched C, and `Name` itself carries no logic, but its two fields had no Javadoc and the class doc did not say
that section zero is accepted here as it is in C. The class and both fields now carry full Javadoc, and the existing
`NameTest` already pins the raw section, file order, empty list and unmodifiable view. Section zero is rejected later by
`RandnameType.fromIndex`, which differs from C only for a data file that does not exist.

### `NameCreator` checked against `randname_make`, `build_prob` and `player_random_name`

`randname.c` holds W. Sheldon Simms' Markov-chain word generator and `player.c` wraps it to name a new character, and
`NameCreator` is the Java form, read by the scroll flavour code and the birth screen. The control flow, bounds, vowel
and length conditions, and table layout all match C, with the empty-word skip and the per-call table rebuild as the only
divergences, both already recorded. The class and its four fields had no Javadoc and `buildProbs` had three empty
`@param` tags, and all now carry full blocks. `NameCreatorTest` adds a two-word list that distinguishes the pair context
from a last-letter chain, beside the existing `randnameMake`, `buildProbs` and `playerRandomName` tests. Later callers
such as artifact naming can use `randnameMake` as it stands.
