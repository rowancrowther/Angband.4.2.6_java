# Precis — 2026-10-16

## Key points from the day

### `AngFile` checked against the `file_*` and `dir_*` functions in `z-file.c`

`AngFile` is the Java form of C's `ang_file` handle: open and close, skip, single-byte and block reads and writes, line reads, text and formatted writes, and directory exists and create. Its behaviour already matched C apart from the accepted deviations, but the write methods carried unreachable lazy-open blocks, and the Javadoc and the class comment still claimed a lazy open that C never does. The class, both fields and every method now carry Javadoc naming the C function and each accepted deviation, and say that only the three read methods open the file themselves. Three new test classes pin the open modes, the `FTYPE_SAVE` exclusive open, the raw-byte reads, the verbatim writes and the `file_getl` line, tab and 1023-byte rules against values traced from C, and `putFormattedLine` now formats with `Locale.ROOT` so a non-English default locale cannot change the digits or decimal point it writes. The format-syntax deviation of `putFormattedLine` is now in `docs/Accepted_Deviations.md`, so each `file_putf` call site still to be ported (`borg/borg-log.c`, `obj-randart.c`, `ui-player.c`, `ui-prefs.c`, `wiz-spoil.c`, `wiz-stats.c`, `z-textblock.c`) needs its `%lu`, `%ld` and `%*s` forms rewritten as it arrives.

### `FileHandler` checked against the `file_*` functions in `z-file.c`

`FileHandler` is the Java form of the file-level half of `z-file.c`: delete, move, exists, savefile naming, newer, and the stream I/O that `AngFile` sits on. Its behaviour already matched C apart from the accepted deviations, but its Javadoc was thin or stale (a parameter that no longer existed, a "string" where the code takes bytes, no mention of the deviations), `fileNewer`, `fileExists`, `getFileMode` and the open-failure edges had no tests, and `exhaustedRetriesReturnLastCandidate` was failing because the savefile tests seeded the game's generator and not the handler's own. The class, every field and every method now carry Javadoc that names the C function and each difference from C, `FileHandlerPathAndModeTest` pins the untested behaviour against values traced from `z-file.c`, and the savefile tests fix `FileHandler.seed` and `FileHandler.debug` instead. A reader of `FileHandler` can now tell which results come from C and which come from the lazy open or the single-stream design, and the differences that are written in the Javadoc but not yet in `docs/Accepted_Deviations.md` are listed below for a decision.

## Things not to drop

- `FileHandler.java`: there is no counterpart for `file_lock`, `file_unlock` or `file_open_hook`.
- `FileHandler.java`: `file_lock`'s only caller is `highscore_write` in `score.c`, so decide when the *Death & scores* port starts whether to add a lock to `FileHandler` (with a thin `AngFile` method over it, opening the write side through a `FileChannel`) or to record its absence as an accepted deviation; `file_unlock` has no caller and need not be ported, since closing the lock file releases it.
- `FileHandler.java`: `getLine` keeps a NUL byte in the returned `String`, where C's buffer is a C string and the line ends at the NUL; shipped data has none.
- `FileHandler.java`: `file_get_tempfile` has no Java counterpart and needs porting when its callers come up in the roadmap (`z-textblock.c` and `ui-prefs.c`); it builds `base.ext` from a base name and an extension, and `FileHandler` is where it belongs next to `fileGetSavefile`.
