# Precis — 2026-08-18

## Key points from the day

### `timedGradeEq` took three passes, and each one was the same mistake in a different place

A timed effect is one counter, but the status the player sees is a band of it — stunning runs Stun, Heavy Stun, Knocked
Out — and `player_timed_grade_eq` answers which band the counter is in. The port searched every band whose maximum
covered the value instead of stopping at the first, so a lightly stunned player answered true to "Knocked Out", and the
zero guard that C opens with had been dropped because the map is pre-populated with a zero for every effect. Both are
fixed, and the loop now returns on the first covering band whether it matched or not. It is the predicate lesson again
from a different angle: the walk was right and the stopping condition was wrong, which is exactly the shape that reads
plausibly and compiles.

### The pre-commit review found a silent stub, and everything else checked out

Twelve files were read against the C original before committing. `ImmutableFlag` was the only real hazard — every method
returned false, null or zero with no Javadoc and no stub marker, in a repo where forty-odd unfinished methods are all
labelled. It has since been deleted. Everything substantive verified clean: all eighteen `StatTables` arrays are
element-for-element identical to `player-calcs.c`, the fifty-three `TimedEffect` rows match `list-player-timed.h` in
order and flags, and `decreaseTimeouts`, the curse tick, the digestion block and `decTimed` are exact ports. The audit
habit from the 16th paid off again: the fault it found was the one that would never have thrown.

### `FlagView` gave the port back something C had and Java did not

C passes flag arrays as `const bitflag *` wherever a function only reads them, so the compiler enforces read-only at
every call site; Java handed callers a mutable `Flag` and relied on intent. The new interface restores that, and the
day's work was drawing the line in the right place — not "queries take views, mutators take flags", but argument versus
receiver: `union`, `inter`, `diff` and `copyFrom` all mutate their receiver and only read their argument, so all four
now take views. `inter` was the one that could not simply be re-typed, since `retainAll` needs a `Collection`, and its
replacement had to keep answering the narrow "was a flag actually cleared" question its Javadoc promises and C's own
`flag_inter` does not. Two read-only sites in `Player` were unblocked by the change, and a reflection test now fails if
a mutator is ever added to the interface.

### The redraw flags needed a third option that neither instinct offered

Returning the live set and returning a read-only copy both looked reasonable until `redraw_stuff` was read properly: C
takes a snapshot, narrows its own copy when the map is not on screen, acts, then clears from the live set only the bits
it handled. A view breaks the narrowing step and a wipe drops any flag raised mid-repaint, so neither instinct survived.
`getRedrawFlags` now hands back a deliberately mutable snapshot the caller owns and `clearRedrawFlags` takes a
difference, which is C's four steps one for one. Worth carrying forward that `update_stuff` does *not* work this way —
it tests and clears one flag at a time against the live field — so the two sets should not be made symmetrical for
tidiness.

### A view is not an immutable value, and saying so changed three comments

The distinction surfaced from a question about `copyFrom` and turned out to matter in several places: a `FlagView`
withholds mutation from whoever holds the view, but says nothing about whoever holds the underlying `Flag`. Where the
underlying set is final and never written after construction — the `TimedEffect` constants — the view alone is enough
and the defensive copies were dropped. Where it changes constantly, as the upkeep's pending redraws do, the copy is
still what provides a stable value. Three Javadoc blocks that described copies which no longer happen were corrected as
the code moved under them.

### Ninety-five tests were written for the parts that changed

Nine test classes, covering the widened mutators through view-typed references, the band-selection rule and all of its
guards, the snapshot-and-difference contract, the two registry lookups, and the two hand-transcribed C tables. Several
are guarding decisions rather than behaviour — the interface's method list, the no-copy choice on the enum accessors —
because those are the ones a later tidy-up would undo without any test noticing.

### `flagsTimed` was right first time, and the interesting part was why `TMD_TRAPSAFE` is left out

The port of `player_flags_timed` matched C conjunct for conjunct — nonzero counter, `oflag_dup != OF_NONE`, and the
`TMD_TRAPSAFE` exclusion — and the supporting facts held up too: the constructor seeds the map with every
`TimedEffect`, so iterating its keys covers the same population C's `0`-to-`TMD_MAX` index loop does, and the assembler
defaults `oFlagDup` to `OF_NONE` rather than null, so the guard is the whole test and `flags.on` cannot be handed a
null. The exclusion is the one piece that cannot be read off the code: C calls it a "Hack" and explains that finding
`OF_TRAP_IMMUNE` in the flags has to mean *equipment*, because that is the cue to learn the trap-immunity rune from an
item — fold the potion in and walking over a trap teaches a rune the player has no item for. The method also returns
`void` now rather than handing back the set it was given, which is the same self-assignment trap `copyFrom`
documents.

### Nineteen more tests, and four of them are about the exclusion rather than the rule

The straightforward cases are the ordinary path and the union-not-replace contract, the latter pinned by a dormant
effect that must *not* clear a flag the equipment granted — the case a "recompute the set" rewrite would break. The
`TMD_TRAPSAFE` section is four tests because the exclusion can be written two ways that pass a naive test: keyed on the
effect, which is right, or keyed on the flag, which would also filter out an item's `OF_TRAP_IMMUNE`. Two tests exist
only to tell those apart. Real data supplied the other awkward case — three effects name `PROT_FEAR`, so setting an
already-set flag has to be a quiet no-op.

### `flags` needed a parameter C does not have, and the reason is the port's own doing

`player_flags` gathers the object flags a player has innately — race, class, and fear immunity for a Warrior at level
30 — and reads the bravery flag straight off the player's calculated state. The port did the same and it was wrong here
rather than in C: `calcBonuses` shadows the field with a parameter of the same name and then rebinds it to a fresh
state, so the flag was read from one state while the result was written into another. `flags` now takes the state to
consult as an argument, which makes the two provably the same object. That divergence is deliberate and better than C at
the call sites that build a hypothetical state to ask "what would my numbers be if I wore this?" — C answers the bravery
test from the real player there, the port from the state actually being filled.

### The stat scale is two-speed, and only walking it point by point gets that right

`modify_stat_value` applies a bonus or penalty to a stat held in the game's odd scale: 3 to 18 one point at a time, then
in tens, so 18/10 is stored as 28. The port matched C statement for statement, including the loop that applies one point
at a time — which is not laziness in the original, because a bonus crossing 18 is worth different amounts in its two
halves and no single arithmetic step gets both. Nothing needed changing; the work was proving it, with a transliteration
of the C body compared against the port across every stat value and modifier a character could carry. The awkward corner
is the branch C comments "Prevent weirdness": a value between 19 and 27, which the scale should never hold, snaps back
to a clean 18 and spends a whole point of the penalty doing so.

### Sixty-one tests for two small methods, most of them about boundaries

The `flags` set is *replaced*, not added to, which is the opposite of its neighbour `flagsTimed` despite the
near-identical signature — both C call sites happen to pass an empty set, so only a test holds the port to it. The
bravery rule is a conjunction of a class flag and a level, and each half is tested alone because dropping either leaves
the common cases passing. For the stat scale the boundary is crossed from both sides and from within, since the step
changes *after* 18 going up but snaps *to* 18 coming down, and the sweep against the transliterated C covers what the
hand-written cases do not.

### Embodiment turned out to be one line, after three attempts at the copy underneath it

C's `player_embody` copies the race's body template into the player and allocates a fresh, empty slot array, so that a
character's equipment cannot end up in the shared template every player of that race reads from. The port's first
attempts rebuilt the slots in place on a body borrowed from the registry, which meant the registry's own body was being
renamed and re-slotted, and a `Cloneable` version was worse still — `super.clone()` copies a final field by reference,
so the "copy" and the original shared one list and clearing it emptied both. The answer was a plain `copy()` built
through the constructor, which made embodiment a single assignment. Worth carrying forward that `Object.clone` buys
nothing when every field needs handling of its own, and costs a checked exception at every call site.

### `calcBonuses` got as far as the equipment loop, and needed four things built first

The first forty-five lines of C's longest function are in: the locals, the reset, the defaults, race and class skills
and resistances, the base player flags and the innate object flags. Getting there needed a body to read equipment slots
from, a state whose wipe zeroes scalars as C's `memset` does, a stat lookup that answers zero rather than throwing on a
fresh state, and `flags` taking the state to consult as an argument. The last of those is a real divergence from C and
an improvement on it: at the call sites that build a hypothetical state, C answers the bravery test from the real player
while filling a scratch state. The next block is "analyze equipment", a hundred lines that will want `el_info` dense
before the vulnerability pass decrements an entry nothing wrote.

### Three tests broke on decisions taken today, which is the suite doing its job

`PlayerRaceReader`'s body test asserted identity between the registry's body and the race's, which stopped being true
the moment the registry started handing out copies; it now checks the layout matches and the object does not. Two others
built a body with no slots, which the constructor has since started refusing. All three were assertions about decisions
rather than about behaviour, and each one is now pinned the right way round. The `ItemObject` fixture also had to seed
the registry itself, since constructing a
`Player` now reads it for a default body and race — a real coupling, and one that made the suite order-dependent until
it was made explicit.

**Suite: 2236 tests, 0 failures. Build green.**

## Things not to drop

- `GameWorld.decreaseTimeouts` and the curse timeout loop have no tests; both are private and need a live cave, an
  equipped body and the monster subsystem to reach, so they rest on the line-by-line comparison against
  `game-world.c:280-365` and nothing else.
- `PlayerUpkeep.getRedrawFlags` and `clearRedrawFlags` have no callers yet — `redrawStuff` is still a stub — so the
  tests are the only thing exercising the contract they were designed around.
- `PlayerTimedEffect.getGrade` still hands out the live list where the flag accessors were narrowed to views.
- The port's grade list has no equivalent of C's implicit zero grade, so `TimedGrade.Grade` runs one lower than C's
  numbering throughout; `timedGradeEq` no longer cares, but `player_set_timed` compares grade numbers and will.
- `docs/Chapter_3_Roadmap.md:194` still says `Flag<PlayerUpkeepEnum>` after the rename to `PlayerUpdateEnum`.
- A `TimedEffectData.java` was staged as a new file at some point today and does not exist on disk; worth checking what
  is staged for it before committing.
- `setTimed`, `incTimed`, `clearTimed`, `updateStuff`, `redrawStuff` and `noticeStuff` are all still stubs, which is why
  the timed-effect tests reach the counter reflectively.
- `Flag.onDbg` duplicates `on` exactly and carries no Javadoc. C's `flag_has_dbg` differs from `flag_has` only by a
  bounds check on `size`, which catches passing a flag of one family with the size of another — impossible in
  `Flag<E>`, where the family is the type parameter and there is no `size` argument to disagree with anything. The
  deprecation-note treatment given to `next` may be the honest answer.
- `flagsTimed` has no callers yet: `calc_bonuses` is not ported, so its tests are the only thing exercising it.
- `PlayerState.wipe` calls `clear()` on its two flag sets, but `Flag.clear` is a varargs method taking the flags to
  clear, so a no-argument call clears nothing. Nothing calls `wipe` yet; `calcBonuses` will.
- `flags` has no callers yet either, for the same reason `flagsTimed` does not: `calc_bonuses` is not ported.
- `modifyStatValue` is the only non-static member of `PlayerUtils`, whose class doc says the file is static methods over
  a passed-in player; its tests have to construct an instance to reach it.
- `Player`'s constructor reads `PlayerRegistry` for a default body and race and throws if races are not loaded, so any
  test that builds a `Player` must seed the registry first.
- `PlayerBody.setName` has no callers now that `embody` replaces the whole object.
- `calcBonuses` stops at "analyze equipment" and has no Javadoc; `state` and `knownState` are still null on a new
  `Player`, which `hasPlayerFlag` and `hasObjectFlag` will trip on.
- The reply-format rule set today is in memory: short bullets with blank lines between them, one idea each, no
  paragraphs under a bullet.
