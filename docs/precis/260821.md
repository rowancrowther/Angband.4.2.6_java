# Precis — 2026-08-21

## Key points from the day

### The request/response boundary was settled on a correlation id

Porting the drop confirmation exposed the one message shape the channel design had never had to carry: the core asks the
UI a question and waits for the answer, where every message so far has been one-way and unanswered. That matters to the
existing code because the core's inbox is shared — a queued command or a forwarded window-close can arrive ahead of the
reply, so a plain receive cannot be trusted to return the thing being waited for. The decision is a correlation id on
the request and reply records only, with non-matching messages buffered in front of the receiver and stale replies
discarded. Going forward every interactive getter follows this one route, swapped in behind the existing input boundary
rather than reached from any call site, and the window-close case is the exception that must be answered during the wait
rather than buffered.

### The notice chain was coded from end to end, and needs a second pass

The whole of `noticeStuff` and the two functions below it were written today, along with the object helpers they lean
on — the ignore filter, the mergeable test, the stackable test and the inscription counter. That is the first time a
complete `PN_*` path exists in the port, and it reaches from the notice flags down to the point where two stacks would
actually be merged. Tracing it against the original found the drop half essentially complete and the combine half
missing its whole tail, its partial-stack branch and the second of its two absorbs. The shape is right and the gaps are
all additions rather than corrections, so the next pass is filling in rather than unpicking.

### The known-object absorb is where the port stops resembling the C

C merges two stacks by calling the same absorb function twice — once on the pair of knowledge shadows and once on the
pair of real objects — because in the original a shadow *is* another object of the same type. The port's knowledge type
is a dozen fields rather than a whole object, so the doubled call has nothing to bind to and the absorb was left empty.
Nothing was decided today beyond identifying it. It is the first place the flattened knowledge object costs something
rather than saving something, and the answer needs settling before the combine path can work at all.

## Things not to drop

- The reply record settled today carries a boolean, so the getters that can also abort need a payload shape that
  distinguishes "aborted" from "answered" before they can use the same route.
- The primer menu entry still describes the four options without recording which one was chosen.
- `ItemObject.checkForInscription` returns a boolean where the original returns a count of overlapping matches, which
  the repeated-confirmation call sites rely on.
- The inscription helper that reads a trailing integer, used by the auto-pickup limit, has no port yet.
- `Player.ignoreDrop`'s shop test and ignore filter are now correct; what remains of it is listed below.
- `noticeStuff` is missing its third block, the monster-message dump, and its Javadoc still calls the whole method a
  stub.
- `combinePack` never breaks out of the inner scan after a merge, so an absorbed stack would be offered for merging
  again.
- `combinePack` sets both of its message flags and reads neither, so the pack-combined message, the repeat-disable and
  the two gear redraw signals are all absent.
- `combinePack` has no partial-stack branch, which in the original is the larger half of the function.
- `combinePack` iterates the gear with a for-each while the absorb it calls will remove from that same list.
- The inner loop bound in `combinePack` is one past the end, reachable only if an item is missing from the gear it came
  from.
- `mergeable` applies the quiver limit outside the store exemption, where the original nests it inside, and takes its
  stack limit and ammo test from the wrong one of the two objects.
- `objectStackable` tests its two inscriptions for non-null where the original tests for null, inverting the whole
  compatibility rule.
- `ItemObject.setNote` does not exist, so the refusal path in `ignoreDrop` cannot compile, and appending to a null note
  would read as the word "null" followed by the inscription.
- `ignoreDrop` returns from the whole method when the drop command is missing, skipping the two flags the original
  always reaches.

## Appendix — pointers in `object_absorb`, from the day's questions

**Yes — everything in that call is a pointer**

- The signature is `void object_absorb(struct object *obj1, struct object *obj2)`. The `*` makes both parameters
  pointers; C has no reference types, so passing a whole struct would have meant copying every byte.
- At the call site `object_absorb(obj2->known, obj1->known)`, `known` is itself a `struct object *`
  field, so the arguments are already pointer values. Nothing is dereferenced by the call.
- `->` is the pointer form of `.`: `obj2->known` means "follow the pointer `obj2`, then take its
  `known` field".

**One detail of the first line**

- It reads `struct object *known = obj2->known;` — from **obj2**, the stack being absorbed, not obj1. The function keeps
  a handle on the second object's shadow so it can delete it after the merge.
- Watch the argument flip at the call site: the caller's `obj2` becomes the function's `obj1`, so the caller's *first*
  argument survives and its second is destroyed.

**Pointers are passed by value, and that matters here**

- `obj1` inside the function is a **copy** of the caller's pointer. Reassigning `obj1 = something`
  would change nothing for the caller.
- Writing *through* it does: `obj1->number = MIN(...)` modifies the object the caller can also see. That is the whole
  reason pointers are used.
- Hence `object_delete(cave, player->cave, &obj2)` takes the **address of** the parameter —
  `object_delete` nulls what it is given, but it only nulls this function's local copy. The caller's
  `obj1` is left pointing at freed memory.
- `combine_pack` is the caller coping with exactly that: it sets `obj1->known = NULL` between the two calls, because the
  shadow has just been freed and the next line would otherwise pass a dangling pointer.

**What this means for the port**

- Java has no pass-by-value struct at all — every `ItemObject` variable is already a reference, so the C pointer
  semantics come for free.
- What does **not** come free is the deletion half. `object_delete` freeing memory and nulling the handle has no Java
  equivalent; the port has to drop the object from whatever collection holds it, and the "caller must not touch it now"
  contract becomes a comment rather than a compiler concern.
- The `obj1->known = NULL` line is not bookkeeping you can skip — it is the port's cue that the two absorbs are ordered
  and the shadow must be detached between them.
