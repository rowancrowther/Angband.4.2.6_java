## 1. `KnownObject` replaces `ItemObject` as `p->obj_k`

**The decision, and why it is safe.** C types `p->obj_k` as a whole `struct object`, allocated by
`object_new()` in `init_player`. That is not a design choice so much as C having nowhere else to hang a bag of learned
properties. Grepping every `obj_k->` dereference in the 4.2.6 tree, the fields it ever touches are exactly twelve:

```
flags  modifiers[]  el_info[].res_level  brands[]  slays[]  curses[].power
to_h   to_d         to_a                 ac        dd       ds
```

Everything else on `struct object` is dead weight on an obj_k — kind, ego, artifact, grid, weight, timeout, origin, and
worst of the set a `known` pointer back to a "known version" of the knowledge itself. `KnownObject` carries the twelve
and nothing more.

**The acceptance test that settled it:** `player_knows_rune` (`obj-knowledge.c:257-306`) is a seven-armed switch, each
arm reading one obj_k field. `KnownObject`'s public API covers all seven with no leftovers. That is the strongest
available evidence the shape is right.

**Representation changes, and what each buys:**

| C                                              | Java                        | Why                                                                                            |
|------------------------------------------------|-----------------------------|------------------------------------------------------------------------------------------------|
| `int16_t modifiers[]`, only ever 0/1           | `Flag<ObjectModifier>`      | Loses nothing; call sites that *multiplied* by it become conditionals                          |
| `el_info[].res_level`, only ever 0/1           | `Map<ElementEnum, Boolean>` | On the knowledge side the level is not a level                                                 |
| `bool brands[]` indexed by registry position   | `Set<Brand>`                | Membership *is* the state; drops the registry-walking init                                     |
| `bool slays[]`                                 | `Set<Slay>`                 | Same                                                                                           |
| `curse_data curses[]`, only `.power`, only 0/1 | `Map<Curse, Boolean>`       | Stays a map: pre-populated, so an unrecognised curse is distinguishable from a known-false one |
| `el_info[].flags`                              | *dropped*                   | Written and read by the savefile, never consulted by any code                                  |

**`ac` / `dd` / `ds` are not constants.** `object_new()` zeroes them; `player_outfit`
(`player-birth.c:593-596`) raises all three to 1 as part of "give the player obvious object knowledge", along with
switching on the `OFT_LIGHT` and `OFT_DIG` flags. They are then used as 0/1 *multipliers* —
`obj->known->ac = obj->ac * p->obj_k->ac` — so an unknown value is masked away rather than branched on. They were
briefly `final = 1`, which is right for every moment of play but bakes in the birth step and would have broken the
loader, which reads all three back (`load.c:1025-1030`).

## 2. The equivalence-class fan-out — the day's real bug

**Brands and slays come in groups sharing one rune.** `brand.txt` holds ten entries that are five names twice over;
`slay.txt` has three names appearing twice. Learning the rune reveals the whole group. C does the fan-out **on the
learning side**, inside `player_learn_rune`:

```c
for (j = 1; j < z_info->brand_max; j++)
    if (streq(brands[r->index].name, brands[j].name)) {
        p->obj_k->brands[j] = true;
        learned = true;
    }
```

`player_knows_brand` is then a plain index test. **Learn fans out; know stays cheap.**

The port initially marked only the brand it was handed. Since `Brand.equals` compares code, name and verb, a strong acid
brand is not equal to a weak one, so:

```
learnBrand(weak acid)  → set contains {acid}
knowsBrand(strong acid) → false        // C says true
```

That bites every brand in the game. Fixed by fanning out in `KnownObject.learnBrand` / `learnSlay`.

**The two grouping axes are different, and neither substitutes for the other:**

- Brands group by **name** (`streq`).
- Slays group by **monsters slain** (`same_monsters_slain`: race flag, then base) — *not* by name. A slay named "evil"
  with a non-null base kills a different set of monsters and belongs to its own group, so a name-keyed fan-out would
  wrongly sweep it in.

It is the same test `Rune.initRunes` de-duplicates with, so the two cannot disagree about where the boundaries fall.

## 3. `learnRune`: sealed interface earns its keep

The switch was originally over `RuneVariety.group()` followed by seven unchecked downcasts of an
`Object` returned by `getKey()`. Two problems: `RuneGroup` is the *knowledge-menu heading*, a different axis from C's
`r->variety` discriminator, and nothing enforced the link between a group value and a record type. It held only because
the two happened to be 1:1.

Now record patterns over the sealed interface:

```java
switch(rune.getVariety()){
        case RuneVariety.

ModKey(ObjectModifier key, var property) ->learned =itemKnowledge.

learnModifier(key);
    case RuneVariety.

ResistKey(ElementEnum key, var projection) ->learned =itemKnowledge.

learnResistance(key);
    ...
            }
```

Exhaustive without a `default` — the compiler proves the seven are covered — no casts, and no
`ClassCastException` possible. C reaches the same seven cases through a `switch` on `r->variety`
followed by an `int` index whose meaning changes per case, and closes with a `default` it cannot show unreachable.

**Consequence:** `RuneVariety.getKey()` and its `Object` return type are now dead across the codebase. Deleting the
abstract method and all seven overrides is outstanding.

## 4. Wrappers are not decoration

C keeps `player_learn_rune` file-`static` and routes every caller through a wrapper —
`player_learn_flag`, `player_learn_slay`, `player_learn_brand`, `player_learn_curse`, the
`equip_learn_*` family. Reaching past a wrapper skips three things:

1. the already-known guard;
2. the second `update_player_object_knowledge` call (the wrapper calls it again on top of the one
   `learn_rune` already did — C's redundancy, faithfully reproduced);
3. **the `Rune.runeIndex` overload that resolves a property to its *group representative* rune.**

(3) is the one that matters. A caller that builds its own `Rune` from the brand in hand learns one member where the game
means all of them. `learnRune` is still `public` where C is `static`; package-private is the fix. Saved to memory as
`rune-learning-wrappers`.

Curses resolve **by name**, following C's `rune_index(RUNE_VAR_CURSE, lookup_curse(curse->name))`, so a curse rebuilt
from a savefile or a parser is still recognised — identity would fail quietly.

`update_player_object_knowledge` itself (still a stub) runs `player_know_object` over four populations: level objects,
gear, **every store's stock**, and the objects hanging off the curse definitions; then autoinscribes ground and pack and
signals the inventory/equipment events. The store stock is the interesting entry — knowledge is a property of the
player, so learning a rune changes how a sword in a shop reads without the player having touched it.

## 5. Divergences found in `ItemObject` (both live, both left alone)

**`similar()` compares combat bonuses by reference.** Lines 544-546 are `this.toHit != itm2.toHit`
on `Random` objects, where C compares `int16_t` values. Two dropped +1,+1 swords with genuinely equal bonuses will not
merge unless they happen to share the instance. `ego` at line 554 is also
`!=`, which is fine — egos are registry singletons — but `toHit`/`toDam`/`toAC` are per-item parsed values and are not.*

**`getBrands()` and `getCurses()` disagree about mutability.** `getBrands()` hands out the live set; `getCurses()` wraps
its map in `Collections.unmodifiableMap`. Found by a test that asserted
`assertSame` on both and failed on curses. Both behaviours are now pinned by tests, but two neighbouring accessors
making opposite choices will catch someone out.
