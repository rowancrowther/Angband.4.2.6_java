# Precis — 2026-10-02

## Key points from the day

### `ArtifactSetData` checked against `struct artifact_set_data` and `artifact_set_data_new`

`struct artifact_set_data` in `obj-randart.h` holds what the randart generator learns from a set of artifacts, and
`artifact_set_data_new()` in `obj-randart.c` builds it zeroed, with six hand-set start and increment values.
`ArtifactSetData` is the Java form, built by `ObjectRandart.artifactSetDataNew`. All thirty members, the six defaults
and the zeroed key sets match C, but the class, fields, constructor and sixty accessors had no Javadoc. Every
declaration now carries a block naming its C member and the `obj-randart.c` function that fills it, and the new
`ArtifactSetDataTest`
pins the defaults, every getter/setter pair, single-key writes and C's `+=` idiom. The later `store_base_power` and
frequency ports can use the accessors directly, as long as every artifact is loaded before construction, because a late
artifact has no entry and its getters throw.

### `ArtifactIndex` checked against the `ART_IDX_*` enum

The `ART_IDX_*` enum in `obj-randart.h` is built from the X-macro list `list-randart-properties.h`, and names the 95
learned-probability slots in `art_probs`, sentinel included. `ArtifactIndex` matches it name for name, in order and with
the same supercharge column, but carried no Javadoc at all. Every constant now says which `obj-randart.c` tally fills it
and what floor or halving `adjust_freqs()` applies, and the new `ArtifactIndexTest` pins the order, the ordinals and the
supercharge flags. The flag is unread in C and in Java, so it only matters if a later port finds a use for it; the
item-group arrays (`art_idx_bow` and the rest) are the next piece the frequency code will need.

### `GameConstantsData` checked against the `parse_constants_*` handlers and `check_critical_levels`

`GameConstantsData` and its builder are the Java form of the `constants.txt` half of `struct angband_constants`. C fills
that half through the `parse_constants_*()` handlers in `init.c`, then `finish_parse_constants()` checks the critical
cutoffs with `check_critical_levels()`. The builder now zeroes missing constants and lets a later line overwrite an
earlier one, as C does. Three `GameConstantsReaderTest` cases that still expected missing-constant and duplicate errors
were rewritten to match. Every declaration now has Javadoc naming its `z_info` field and C handler, and the new
`GameConstantsDataTest` pins the defaults, the label-to-field wiring, the level-row checks and every
`check_critical_levels` case. The one Java-only rule, rejecting a `-1` cutoff in the middle of a level list, is
documented and pinned as a deliberate divergence. Values above 65535 are kept, where C's `uint16_t` fields would
truncate them, so that difference will show up only if a data file ever goes that high.
