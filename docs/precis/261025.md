# Precis — 2026-10-25

## Key points from the day

### ParseUtils (base 0 reading, Radix overload)

`ParseUtils` turns the integer text the grammars hand over into an `int` the way `strtol` and `strtoul` do in `parser.c`, with the fixed base 10 figures taken from `datafile.c`. It threw on `0`, `-0`, `+0`, `08`, `0x` and `0xg`, where `strtol` reads the leading `0` as a digit and gives 0, and a new `Radix` overload used by `FlavourAssembler` accepted `abc` as decimal and `g` or `8` with no prefix as hex and octal. Your edits make the prefix the deciding point: a consumed `0` or `0x` with no digits after it gives 0, text with no digit at all stops the load, and the `Radix` overload now refuses HEX without `0x` and OCTAL without a leading `0`. The class, `Radix` overload, `parseString`, `nonDigitFound` and strip-helper Javadoc now record the four ways in, the prefix rule and the clamp, and `ParseUtilsBase0Test` and `ParseUtilsRadixTest` pin each case against what `strtol` returns. Whoever calls the `Radix` overload next must choose the radix from the unsigned text, since the overload strips the sign itself.

### FlavourAssembler (storeFlavour, class)

`FlavourAssembler` turns the `flavor:` and `fixed:` records of one `kind:` block into `Flavour` objects, reading each `uint` index as `parser_parse` does and resolving the colour as `parse_flavor_flavor` does. It chose the radix from the raw index text before the sign was removed, so `+0x10` read 0 where C gives 16 and `+010` read 10 where C gives 8, and its Javadoc still described soft-error dropping that no longer happens. Your edit hands the whole reading to the five-argument `ParseUtils.parseIntString`, which skips whitespace, takes one `+` and chooses the base from the unsigned digits. The class, field, `assemble` and `storeFlavour` Javadoc now record the fatal index, the white fallback for an unknown colour or `COLOUR_SHADE`, and the unused `errors` list, `FlavourAssemblerTest` pins the sign, prefix and colour-case rows against `strtoul` and the C colour functions, and the five stale `FlavourReaderTest` cases now assert the fatal and white behaviour. The `Radix` overload of `parseIntString` has no caller left in `src/main`, so any later reader that needs a base 0 index should use the five-argument form.

### ObjectKind (setTval)

`ObjectKind.setTval` is the port of C's direct `kind->tval` write, which `parse_object_type` in `obj-init.c` and `write_book_kind` in `init.c` make as one statement among several. It had no Javadoc, and its only caller, `FlavourKindAssembler`, builds a throwaway kind to reach the sval 255 that C's `lookup_sval` miss produces once the `uint8_t` flavour sval stores its -1. The port was already a faithful bare assignment, so the `tValue` field and `setTval` Javadoc now say what it does not do (no base, no sval, no check, `null` kept) and why the caller builds the throwaway. `ObjectKindSetTvalTest` pins the round trip of every `TValue` and that base and sval are left alone, and `FlavourKindAssemblerSvalMissTest` pins 255 for a miss, the matched kind's sval for a hit and 0 for a random flavour. Whoever calls `setTval` next must set the base and sval itself, since `parse_object_type` does and the setter does not.

### AngbandDisplayCharacter (class, int code points)

`AngbandDisplayCharacter` is the glyph-and-colour pair behind every screen cell, standing in for C's `attr` and `wchar_t` couple. It held the glyph in a `char`, which cannot hold a code point above `0xFFFF`, and the first wide version left `'a'` and 97 unequal and gave every wide glyph of one colour the same hash. Your edits sort an `int` code point once in the two `int` constructors, narrow up to `0xFFFF` and wide above it, refuse anything outside `0..0x10FFFF`, and mix the wide half into `hashCode` outside the colour check. The class, field, constructor and getter Javadoc now record the split and the NUL and wide ambiguity of `getNarrowCharacter`, and 12 new `CodePoints` tests pin the boundary at `0xFFFF`, the refused ranges, equality across constructors and hashing with an unresolved colour. Callers that need the whole glyph must use `getCharacter()` or both halves, as `ObjectKind.copy` and `ItemObject.objectKindChar` now do.

### FlavourKindAssembler (assemble, class)

`FlavourKindAssembler` turns each `kind:` block of `flavor.txt` into a `FlavourKind`, resolving the tval and glyph as `parse_flavor_kind` does and each `fixed:` sval as `lookup_sval` does. It stored 255 for any sval that matched no kind, where C stores a literal number as it stands and wraps it to eight bits, and an overflowing number threw a `NumberFormatException` and a negative one stored a negative sval. Your edits parse the symbol as a number first, store a negative as 255 and anything else modulo 256, and fall back to the name lookup, which gives 255 on a miss. The class, field and `assemble` Javadoc now record the fatal tval and glyph, the number and name paths, and the accepted trailing-space deviation in `docs/Accepted_Deviations.md`, while `FlavourKindAssemblerNumericSvalTest` and `FlavourKindAssemblerBlockTest` pin the sval, tval, glyph and ordering cases against `lookup_sval`, `tval_find_idx` and `parser.c`. A modded `flavor.txt` that pins a flavour by number now loads as C does, apart from a number followed by a space or tab.

### GameConstantsAssembler (class, seventeen handlers, coerceInt)

`GameConstantsAssembler` turns the parsed lines of `constants.txt` into one `GameConstantsData`, standing in for the seventeen `parse_constants_*` handlers in `init.c`. It let a negative value into every category, took one field as the message and looked it up with `valueOf`, so `NONE` loaded and a numeric name was refused, and it refused any field after the value, where C ignores it. Your edits refuse a negative only in the nine plain categories, refuse a leading `-` (even `-0`) on the O-combat `chance` and `dice`, join the rest of a level line into the message for `MessageType.lookupByName`, and ignore fields after the value. The class, field, handler and `coerceInt` Javadoc now record each rule with the C field every label sets, and `GameConstantsReaderTest` pins them with the shipped file's values from the C original, every label, every category and the sign and message edges, while eight stale cases were rewritten for the throw. A modded `constants.txt` now loads or fails as in C, apart from an oversized integer, which is clamped where C keeps the low bits.

## Things not to drop

- `ParseUtils.java` holds dead code: the private decimal `parseString` overload and `checkRadix` have no callers, and the fixed-base `parseIntString` has a commented-out block.
- `ParseUtils.java`: the `Radix` overload of `parseIntString` now has no caller in `src/main` (`FlavourAssembler` moved to the five-argument form), and its Javadoc and `checkRadix`'s still name `FlavourAssembler` as the caller.
- `ColourEnum.java`: the `fromCode(char)` Javadoc says `'V'` is Light Purple, but `z-color.c` has `'V'` as Light Violet (Light Purple is `'P'`).
- `FlavourKind.java`: the class Javadoc says an unknown tval or bad glyph "drops the whole block" and that C "instead fails the parse"; `FlavourKindAssembler` now throws on both, as C does.
- `FlavourKind.java`: the `glyph` field Javadoc says the port holds a `char` and accepts a one-`char` string; the field is an `int` code point and the assembler accepts one code point.
- `GameConstantsReader.java`: the class and `parseWithResults` Javadoc still call an unknown category or label, a wrong field count, a non-number and an unknown message "soft" errors; `GameConstantsAssembler` now throws for all of them, so only an O-combat `chance` of 0 and the cutoff order are soft.
- `docs/Assembler_Issues.md` (the `GameConstantsAssembler` negative values entry) and `docs/grammar_issues.md` (the `GameConstantsGrammar.g4` entry): both still describe behaviour the assembler no longer has (negative values loading, an exact field count, `010` read as 10, overflow refused) and name tests that were renamed or removed.
- `docs/Accepted_Deviations.md`: nothing records that an integer past the range of an `int` in `constants.txt` is clamped by `ParseUtils` where C keeps the low bits.
