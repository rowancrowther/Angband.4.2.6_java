# Precis — 2026-09-29

## Key points from the day

### Javadoc and tests for the EVENT_MONSTERHEALTH sidebar row

Today's pass finished the port of the sidebar's monster health bar - C's `prt_health`, `prt_health_aux` and
`monster_health_attr` - covering the new `EventDataMonsterInfo` payload, `eventSignalMonInfo`, the `PR_HEALTH` arm in
`PlayerCalcs.redrawStuff`, `RedrawRouter.setMonsterHealth`, the twelve monster fields on `SidebarModel`, and the drawing
logic in `HandlersHolder`. A verify pass caught that the healthy colour at 100 per cent was `COLOUR_GREEN`
where C uses `COLOUR_L_GREEN`, and `HandlersHolderTest` still counted seventeen side-handler rows. Rowan fixed the
colour and the new `HealthBarTest` pins the star-count thresholds, colour boundaries and timed-effect override order to
C's values, with the stale row-count test updated to twenty. The row is now documented, tested and green, so the next
sidebar rows, speed and depth, inherit both the twelve-field payload pattern and its test template.

### Javadoc and tests for the UIPlayer character-sheet panels and `cnvStat`

This pass verified `UIPlayer`, the port of C's `ui-player.c` character-sheet driver - the five `getPanelX` builders, the
panel helpers, `configureCharSheet`, `displayPlayerStatInfo` and `cnv_stat`. The verify pass found that `cnvStat`'s
`len` truncation was first one character too generous and then, after a first fix, threw on every call, so it would have

### Javadoc and tests for `UIEntryAssembler`

### Javadoc and tests for `Message.message`, `messageType` and `sound`

`Message` is the outbound message channel, the port of C's `msg`, `msgt` and `sound` in `message.c`, and `messageAdd`
was already ported and stamped. The verify pass found that a pattern `String.format` rejects made both methods throw or,
once guarded, drop the message, where C's `vstrnfmt` empties the buffer and `msg`/`msgt` log, sound and signal a blank
line anyway. Rowan's fix sets the text to the empty string in the catch block so the ordinary path runs, and the class
Javadoc now records the accepted format vocabulary, the ASCII-only assumption for the 1023-character cut and the
remaining divergences. Ten new `MessageTest` tests pin the shared directives and the malformed-pattern path to C's
values, and `ItemObjectCustomMessageTest` now expects the 1023 cut, so every later caller inherits a checked channel and
must keep to the documented vocabulary.

## Things not to drop

- `Monster.setHp`/`setMaxHp`/`updateCached` still write the legacy `PlayerEventStatusUpdate` cache; they go when the
  cache-to-messages migration removes it.
- `UIEntryAssembler.parseEachEntry` has latent divergences from C that no shipped `ui_entry.txt` record reaches: on the
  override path, a `priority:` before any category sets a category's priority instead of the default, `index` on a
  non-parameterised entry gives 0 where C gives -1, and template flags are never copied.
- On the create path, the template's default priority and each template category's priority and `priority_set` are
  replaced by the record's own values, and a template's flags overwrite the record's own instead of being OR'd with
  them.
- `UIEntryAssembler` also keeps categories in insertion order where C sorts by name, throws on an out-of-range
  `priority:` where C clamps, emits one "no combiner" error per element where C emits one, and quotes `getFirst()` in
  the bad-flag message.
- The `ui_entry_renderer.txt` grammar drops three directives C parses - `combine`, `units` and `combined-renderer` - so
  a file using any of them fails closed with token errors and loses every record, and `UIEntryRendererParseRecord` has
  no fields to carry them; the shipped file uses none.
- The renderer grammar also fixes the directive order (`colors`, `labelcolors`, `symbols`, `ndigit`, `sign` after `name`
  and `code`) where C accepts any order, and it makes `code` mandatory where C leaves the backend unset and skips the
  renderer.
- C merges a repeated `name:` into the existing renderer field by field, but `UIEntryRendererAssembler` has no merge (a
  commented-out sketch only) and the grammar rejects a second `name:` block that omits `code` before the assembler sees
  it.
- `UIEntryRendererAssembler` accepts `code:NONE`, resolving it to the Java-only sentinel with empty palettes, where C
  rejects it as an unknown backend.
- A record with no `code` reaches the assembler only when it is called directly, and there `ndigit` and `sign` are not
  validated, the file's `colors`, `labelcolors` and `symbols` are dropped, and `nDigit` is fixed at 1, where C validates
  and stores them whatever the backend.
- Palette lengths count UTF-16 units where C's `text_mbstowcs` counts wide characters, so the 64-symbol cap and top-up
  index could differ for a symbol outside the basic plane; every shipped symbol is ASCII.
- `ItemObject.printCustomMessage`'s Javadoc says the Java version cannot truncate where C cuts at its 1024-byte buffer,
  but `Message.messageType` now cuts the text at 1023 characters, so the Javadoc is wrong.
- `ItemObject.printCustomMessage` hands its built text to `Message.messageType` as the format pattern where C's `msgt`
  receives it as a `"%s"` argument, so a `%` in a message template would be read as a format directive.
