# Precis — 2026-08-16

## Key points from the day

### `player_know_object` was audited block by block before anything was fixed

The port of `knowObject` and its five helpers had been written but never checked against C, so the day started with a
read-through rather than a change. Seventeen C functions were compared line for line, and the result was two documents
in
`docs/implementation` — a per-file status list and a per-function breakdown with the C comparison for each. Everything
since has been worked off those, and the shape proved worth the time: the audit found more than the tests did, because
most of the faults compiled and read plausibly.

### The audit's findings clustered into inverted conditions and wrong accessors

Of the divergences found, four were a boolean test the wrong way round and several more were the right logic reading the
wrong field — `getAc()` where C used `to_a`, the kind's to-damage dice where C wanted its damage dice. One inverted
early return made most of `knowObject` dead code for every real object in the game. All are now fixed bar the curses
block. It is the same lesson as yesterday's closing note, arriving a day later on a bigger function: this port breaks at
its predicates, not its structure.

### A closed, non-growing worklist replaced the audit prose

The two audit documents were the right record but the wrong working surface — too much reasoning to navigate while
debugging. A third document now holds one checkbox per function, needs-work items only, with the reasoning left behind
in the others. Nothing gets added to it. That has been the thing that made the day's second half work, and the same
separation is worth repeating for the next subsystem.

### `ItemObject` stopped handing out its flag set

`getKnownFlags` returned a copy while its own Javadoc promised a live set, so `equipLearnFlag`'s write was silently
discarded — the one genuine test failure of the day, and the second time this class had claimed live and delivered a
copy. The member is gone, replaced by named mutators that add, replace or set a single flag, with the getter narrowed to
a copy so no unnamed write path remains. The same treatment is now wanted for curses, and that is where the day stopped.

### The curse map is the wrong shape, and the mutators alone do not fix it

Curses are stored keyed on a record pairing the curse with its mutable data, which makes the key unstable and leaves
nowhere to record a known power that differs from the real one. Adding mutators unblocked the writes but left both
faults in place, along with a third — `CurseData` has no value equality, so stacking and full-knowledge tests are wrong
for every cursed item. The field wants to hold curse against data directly, as C's two parallel arrays do. This is the
one piece of the debug still open.

### The commenting pass ran wider than the code changes

Javadoc was written for every function and accessor the audit found correct, which turned out to be around sixty
members — most of them accessors that had never been documented at all. That is where the load-bearing decisions had
been hiding: copy versus live, modifiable versus not, which of the two knowledge stores an item's readable flags belong
to. Three separate comments were found asserting the opposite of what their code did.
