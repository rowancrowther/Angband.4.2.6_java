# Precis — 2026-10-19

## Key points from the day

### `LoreReader` checked against the lore parser in `mon-init.c`

`LoreReader` is a parked stub for `lore_parser` as a whole (`init_parse_lore`, `run_parse_lore`, `finish_parse_lore` and `cleanup_lore`): `parse` reads nothing and returns an empty list, nothing calls it, and no parser is generated from the lore grammar. The stub already matches C for a missing, empty or unreadable file, where `run_parse_lore` reports "No monster lore file found" and carries on, and it differs on purpose only for a file that holds records. The class, logger and `parse` now say which C function each stands in for, what `finish_parse_lore` does that has no Java counterpart, and that restoring the commented-out body would make a missing file throw where C does not. The new `LoreReaderStubTest` has 7 tests that pin the missing, directory, empty, one-record and shipped-file cases and a fresh modifiable list per call, and the 9 parked specs in `LoreReaderTest` stay disabled. The grammar differences (the dropped cast counts, `base:` and `drop-base:` never matching, narrow `blow:`, `flags:` and `friends:` shapes, list order, group role default) are written up in `docs/grammar_issues.md`; there is nothing for `docs/Assembler_Issues.md`.

### `RandomReader` checked against the dice-string parser in `parser.c`

`RandomReader` turns one dice-notation string into a `Random` through `Random.g4`, standing in for `parse_random` in `parser.c` and for the `$` variables of `dice_parse_string` in `z-dice.c`. The check found that a number missing after `M` or `d` (`5M`, `-1d`, `$S+dM`) escaped as a raw `NumberFormatException` where C refuses the string, which would have bypassed the assemblers' line-numbered errors. `Random.g4` now routes every number through a shared `numberOrMissing` helper that turns ANTLR's placeholder token into a marker, so those strings return `null`, and the grammar applies a leading `-` with C's range flip itself; the committed parser was regenerated. The class, logger and `parse` now say which C parser each part stands in for and where the two differ, and the new `RandomReaderTest` has 26 tests that pin the ordinary strings, `INT_MAX`, the missing-number cases and each difference, plus two sweeps of 19,607 strings against a transliteration of `parse_random`. The grammar differences (lower-case `m`, `5M3`, `$` variables, blanks, repeated `d` or `M`, signed zero, overflow throwing) are written up in `docs/grammar_issues.md`; there is nothing for `docs/Assembler_Issues.md`.

## Things not to drop

- `VisualsReader.java` (`parseFlicker`): its return type has no `@NotNull`, where `parseCycler` carries one.
- `TerrainReader.java` (`logger`): it is package-private and not `final`, where the other readers declare `private static final`.
- `Random.java` (`parseStr`): `--1` is accepted and returns -1, where `parse_random` refuses it, because only one leading `-` is stripped before the reader is called.
- `Random.g4` (header comments): they still cite old line numbers in `Random.java` and `z-dice.c` and describe the old hand-written alternatives, and the `@after` block tests `mBonusInit == -1` twice.
- `LoreGrammar.g4` and `LoreLexer.g4` (header comments): the grammar's cites old `mon-init.c` line numbers and the lexer's still describes a "file rule always returns null" bug that the `file` rule no longer has.
